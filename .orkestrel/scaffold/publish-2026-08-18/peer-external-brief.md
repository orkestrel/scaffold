# Design brief: a declared peerDependency is bundled instead of externalized

Two blind lanes, one brief. `planner` (Opus 5, subjective) and `analyst` (GPT-5.6 Sol, objective).
Neither sees the other's answer. Read-only; propose, do not implement.

## The defect, measured

A material-dist comparison across all 44 fleet targets — rebuild, `npm pack`, compare against the
published tarball — found `@orkestrel/test`'s rebuilt browser entry broken.

Published `@orkestrel/test@0.0.6`, `dist/src/browser/index.js`:

```js
import { page, userEvent } from "vitest/browser";
// …
for (const role of roles) for (const element of page.getByRole(role, { … }))
await userEvent.click(target);
```

The same file rebuilt today from unchanged source:

```js
// no import at all
for (const role of roles) for (const element of null.getByRole(role, { … }))
await null.click(target);
```

Rolldown could not resolve `vitest/browser`, so it bundled it away and left `null` at every use
site. Every browser helper the package publishes would throw on first call.

Facts, all measured:

- `/workspace/test/package.json` declares `"peerDependencies": { "vitest": "^4.1.10" }`.
- `/workspace/test/src/browser/factories.ts:2` and `helpers.ts:2` import from `vitest/browser`.
- The generated browser build's external predicate is
  `external: (id: string) => id === '@src/core' || id.startsWith('@orkestrel/')`
  (`/workspace/test/vite.config.ts:61`), so `vitest/browser` is not external.
- That predicate is a hardcoded string in scaffold's compiler,
  `/home/user/scaffold/src/core/compilers.ts:633-635` (browser) and `:656-659` (server), varying
  only on whether `core` is selected. `src/core/templates.ts` fills it through `{{external}}`.
- Three packages declare peers: `mcp` (`@orkestrel/router`, `@orkestrel/server`), `middleware`
  (`@orkestrel/database`, `@orkestrel/server`), `test` (`vitest`). The first two are already
  externalized by the `@orkestrel/` clause; only `test` is broken.
- Every runtime dependency in the fleet is an `@orkestrel/*` package. No package currently bundles a
  third-party runtime dependency.
- The published artifact is correct, so consumers are fine today. The danger is republishing: the
  next `test` release ships the broken bundle.

## The question

Rule on the correct fix, bounded to the external predicate the generated configuration emits.

Three candidate forks:

- **Fork A — externalize declared peers.** The predicate additionally externalizes every specifier
  in the workspace's `peerDependencies`. A peer is by definition supplied by the consumer, so
  bundling one defeats the declaration. Say where the peer list comes from: a new `Blueprint`
  structural fact compiled in (the shape the `setup` project used), or the generated
  `vite.config.ts` reading its own `package.json` through an import attribute the way it already
  reads `tsconfig.json`. Rule on which, and why.
- **Fork B — externalize every bare specifier.** The standard library-build posture: bundle only the
  workspace's own source, leave every non-relative, non-`@src` import external. Behaviour-preserving
  for all 44 today, since no package bundles a third-party runtime dependency. Say what it costs the
  first time a package legitimately wants to bundle one.
- **Fork C — package-specific escape.** `test` alone gets a custom external. Note before arguing
  this: `vite.config.ts` is generated, `scaffold overwrite` rewrites it, and the propagation law
  forbids editing a vendored or generated file inside a target.

## What your answer must decide

1. The fork, and the one-line reason.
2. The exact mechanism, named to the file and the line it changes.
3. Whether the predicate change belongs to the browser build alone or to core and server too. State
   what each one currently externalizes and whether the same defect is reachable there.
4. Whether rolldown silently emitting `null` for an unresolvable bare import — rather than failing
   the build — is itself something the workspace should defend against, and if so, how, bounded to
   configuration this project already owns. A build that produces a broken artifact and exits 0 is
   the reason this went unnoticed.
5. The blast radius on the other 43 targets, stated concretely: whose generated bytes move, and
   whose published artifact would move as a result.

## Constraints on any proposal

- Do not propose adding a dependency.
- Do not propose editing a generated or vendored file inside a target.
- Bound the proposal to the external predicate and the smallest supporting change.
- Preserve behaviour for the 43 packages that build correctly today.
- A rule edit must be written in the instruction-file voice `AGENTS.md` mandates.

## Output

The fork, the reason, the exact mechanism with file and line, the answer to each of the five
questions, the blast radius, and the risks your ruling accepts. No process diary.
