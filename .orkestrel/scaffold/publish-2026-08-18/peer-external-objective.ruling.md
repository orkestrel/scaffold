## Ruling

**Fork A — externalize declared peers.**

A peer is consumer-supplied, so every package-root and subpath import named by `peerDependencies` must remain external without changing how ordinary dependencies bundle.

1. **Exact mechanism**

   Change the root Vite template in [templates.ts](/home/user/scaffold/src/core/templates.ts:59) to import `./package.json` with `{ type: 'json' }`, as it already imports `tsconfig.json`. Derive the peer names at config load, reject a present non-object `peerDependencies` value, and match only:

   ```ts
   id === peer || id.startsWith(`${peer}/`)
   ```

   This prevents `react` from matching `react-dom` while covering `vitest/browser` and scoped-package subpaths.

   Apply that matcher in all library predicates:

   - Add it to the core factory in [templates.ts](/home/user/scaffold/src/core/templates.ts:91), then remove the overriding core-only predicate at [templates.ts](/home/user/scaffold/src/core/templates.ts:597).
   - Add it to the browser predicate in [compilers.ts](/home/user/scaffold/src/core/compilers.ts:633).
   - Add it to the server predicate in [compilers.ts](/home/user/scaffold/src/core/compilers.ts:656).

   Do not add a `Blueprint` field. Existing-target derivation discards non-Orkestrel peers, while `package.json` is workspace-owned after creation. Reading the manifest keeps manual peer additions and later `overwrite` runs aligned.

2. **Why not Fork B or C**

   Fork B externalizes ordinary third-party runtime dependencies as well as peers. The first package that intentionally bundles one would need an exception or allowlist. That wider policy is unnecessary for this defect.

   Fork C puts package policy into generated target bytes and loses the change on `scaffold overwrite`. It violates the propagation constraint.

3. **Affected build faces**

   Apply the rule to core, browser, and server.

   - Core externalizes `node:` and `@orkestrel/*`.
   - Browser externalizes `@orkestrel/*` and `@src/core` when core is selected.
   - Server externalizes `node:`, `@orkestrel/*`, and `@src/core` when core is selected.

   All three omit non-Orkestrel peers. The general defect is reachable from any published face that imports such a peer. In the measured fleet, only `@orkestrel/test` reaches it, from browser source through `vitest/browser`.

4. **Silent broken output**

   The measured case is not an unresolved-import fallback. The installed [vitest browser entry](/workspace/test/node_modules/vitest/browser/context.js:1) resolves successfully and exports `page` and `userEvent` as `null` placeholders for static analysis. The build therefore reports seven transformed modules and no unresolved-import warning.

   Vite 8.2.1 already throws on an actual `UNRESOLVED_IMPORT` in [node.js](/workspace/test/node_modules/vite/dist/node/chunks/node.js:33820). A custom `onLog` handler would duplicate that behavior and would not catch this incident.

   Defend at the owned configuration seam: externalize manifest-declared peers and add a real `write: false` build proof in `tests/config.test.ts` showing that a declared peer subpath remains an import. The negative control must show that a non-peer bare import is still eligible for bundling.

5. **Blast radius**

   The generated bytes change as follows:

   - All 44 root `vite.config.ts` files gain the manifest read and peer matcher.
   - The 38 targets with core builds change `configs/src/vite.core.config.ts` because the overriding predicate moves into the root core factory.
   - Browser and server leaf config files do not change.
   - No manifest changes.

   Built output changes only for `@orkestrel/test`: its browser JavaScript and source map retain `import { page, userEvent } from 'vitest/browser'` instead of embedding the null placeholders. Its core and server output remain unchanged.

   `@orkestrel/mcp` and `@orkestrel/middleware` produce identical output because their peers already match `@orkestrel/*`. The remaining 41 packages declare no peers. Their generated config bytes move, but their `dist` bytes and tarballs do not; configuration files are not packed. The `@orkestrel/scaffold` tarball also moves because it ships the compiler and template fix itself.

## Accepted risks

- Ordinary non-peer third-party dependencies remain bundleable. Fork A does not establish the wider library policy in Fork B.
- The matcher relies on package manifest keys as import roots. npm aliases still work because the manifest key is the consumer-facing specifier.
- The generated configuration gains a package-manifest read at startup. The existing Node floor and JSON import-attribute use already support that mechanism.
- This fix cannot detect a dependency that deliberately exposes a static-analysis stub unless that dependency is declared as a peer. The scoped regression proves the peer invariant, not arbitrary dependency semantics.
