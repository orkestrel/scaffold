## Blast radius

Read from the catalog table in `.claude/agents/orkestrel.md`.

- `@orkestrel/test` is `0.0.11`, layer `L0`, runtime dependencies empty.
- No catalog row lists `@orkestrel/test` in its runtime dependencies. It reaches every package only as a `devDependencies` entry.
- Under every ruling here: **no package re-pins and no package republishes.** A `@orkestrel/test` release is a development bump, which per `.agents/orchestration.md` § What a bump obliges reaches nobody — re-pin, prove gates green, commit to `main`. It becomes a cascade only if a consumer's rebuilt `dist/` differs materially from its published tarball after the re-pin, which additive test helpers do not cause.
- Every ruling is `new` or `compose` inside `@orkestrel/test` itself, so no ruling adds a runtime edge and the package stays L0. The rejected alternative — reusing `@orkestrel/workflow` — would move `@orkestrel/test` from L0 to L5 (workflow is L4) and pull in `abort`, `budget`, `contract`, `database`, `emitter`, `queue`, and `timeout` transitively.

## Drift

- **`readClasses` versus `readCascade`.** Not drift, but the names are one letter apart in meaning and the guide must say which side each reads. `guides/test.md` currently describes `readCascade` as what the stylesheets *define*; the new row must read as what the markup *carries*, and § Bounds or § Patterns must state that their difference is the intended reading.
- **`STATECHART_STATUSES` versus `TaskStatus`.** `passed`/`failed`/`running`/`pending` restate the shape of a lifecycle vocabulary `@orkestrel/workflow` already publishes under different values. This is the exact pattern § Limits refused for the hand-driven timer row: "a copy here would redeclare unversioned and hand consumers a second incompatible type". It survives that refusal only because the values differ and the subject is a harness's reported state rather than a task's derived status. Record that reasoning in the § Limits row, or the next survey re-raises it.
- **`extractEscapes` versus `@orkestrel/html`.** `guides/html.md` § Escape, resolve, and inspect publishes `attributeOf`, `sanitizeAttributes`, and `encodeAttribute`. None applies: html reads a parsed AST from a string, never a live `ParentNode`, and "escape" there means character encoding, not a styling escape hatch. The word collides; the mechanism does not. Consider whether `extractEscapes` is the clearest name given `@orkestrel/html` and `@orkestrel/console` both use `escape` for character encoding.
- No other restatement found. The published line declares no generic state machine, no scenario runner, and no live-DOM class or style reader outside `@orkestrel/test/browser`.

## Unknowns ruled on

**Is `@orkestrel/browser` the natural home for the DOM readers? No. Keep both in `@orkestrel/test/browser`.**

`guides/browser.md` opens with what that package is: "A lightweight Chrome DevTools Protocol (CDP) automation layer", core being "pure logic over an injected `CDPTransportInterface` — no `WebSocket`, no `node:*`, no filesystem". It never holds a live DOM. Its readings arrive as decoded CDP payloads: `BrowserSnapshot` "turns a captured DOM snapshot into navigable serializable data", and its one content capability, `article()`, distills through `@orkestrel/html`. Both new readers take a `ParentNode` and call `classList` and `outerHTML` on real nodes in the calling document. There is no signature `@orkestrel/browser` could give them without either accepting a host DOM type it deliberately excludes, or reshaping them into snapshot walkers — a different function answering a different question.

The brief's own distinction confirms it from the other side. A browser package reads the DOM to build or to drive a remote page; these read the in-process DOM to assert. `guides/test.md` § Surface → Browser already sets the boundary these fall inside: "The predicates, the element readers, and the describers name a node the caller already has … and each reads that node rather than acting on a target it was handed" — `extractOrphans` and `readRows` are named in that list, and both take exactly `(root: ParentNode, …)`.

What a non-test consumer would need: a DOM to read. A production consumer holding one — a component wanting its own rendered class tokens — could import from `@orkestrel/test/browser`, and that is the same position `readCascade`, `findRule`, and `style` already occupy without a second home being proposed for them. A consumer holding markup instead of nodes is served by `@orkestrel/html`, which parses a string into an AST and exposes `attributeOf` over it. Neither case argues for moving these.

**Does `@orkestrel/workflow`'s step or task runner subsume `runScenarios`? No.** Three mismatches in the guide's own vocabulary:

1. **A task's behavior is a name, not a closure.** `guides/workflow.md` § Surface: "A task's `run` is a PLAIN STRING naming a behavior in the `WorkflowOptions.functions` registry — resolved ONCE at construction into the task's `handler`." The whole definition family is "pure JSON — behavior referenced BY NAME, never inline functions — so the whole tree serializes". A `StateScenario` is three inline closures over a caller-owned `TContext`. Expressing it as a workflow means registering every scenario's closures into a function registry and referring to them by id, which is more machinery than the walk it replaces.
2. **`arrange`, `act`, `assert` are not three tasks.** A workflow's only sequencing is structural: "tasks within a phase run concurrently; phases run sequentially. A dependency is expressed STRUCTURALLY — a task that needs another's output goes in a later phase." Three ordered closures sharing one mutable context would need three phases per scenario, and phases are a workflow-level list, not a per-row construct. There is no per-task sequential step. The map does not exist.
3. **Serial scenarios are not the runner's default.** The brief requires serial execution because "a statechart's rows share a page". A workflow gives you one phase per scenario to get that, at which point the runner is contributing an await loop.

Cost of pulling it in: `@orkestrel/workflow` is `0.0.16` at layer L4 with runtime dependencies on `abort`, `budget`, `contract`, `database`, `emitter`, `queue`, and `timeout`. `@orkestrel/test` declares zero runtime dependencies and sits at L0. Adopting workflow would make the fleet's test package L5, put `@orkestrel/database` in every consumer's test graph, and — because `@orkestrel/test` is a `devDependency` everywhere including inside those same packages — create a development-time install graph in which `queue`, `workflow`, and `database` depend on a test package that depends back on them. `runScenario` and `runScenarios` are an await loop with a named-error wrap. Keep them local.

## Unknowns the guides do not settle

- **Whether `STATECHART_ATTRIBUTES` clears the § Limits mechanism test.** The rule is that a candidate ships when it is "a reusable test mechanism, has a real consumer, fits this package's environment boundaries, and duplicates no native or declared-dependency primitive", and is refused when it is "one suite's policy". The brief cites exactly one harness for these attribute names: `elements/app/browser/playgrounds/StatechartHarness.vue` and the gate polling it. `veneer` is cited for the *contract* (`tests/setup.ts`) and the runner, not for the attribute names. One harness's chosen `data-*` spelling is closer to policy than to mechanism. Settling reading: whether `veneer`'s harness, or any second workspace's, polls the same attribute names. Nothing in `guides/` can answer this; it needs a read of the sibling checkouts, which this dispatch excludes.
- **Whether the published `runScenarios` signature serves `veneer`.** The brief records two incompatible existing signatures — `elements` `runScenarios(scenarios, build)` and `veneer` `runScenarios(label, create, scenarios)`, the latter registering `describe`/`it.each` itself — and rules the walking form published on the ground that "a package helper registers no test". That ruling is sound against `.claude/rules/tests.md`, but it makes `veneer` a consumer that must rewrite its call sites rather than adopt an export. The guides do not settle whether that rewrite is in scope for this wave. Settling reading: the actual `veneer/tests/setupBrowser.ts` call sites and their count.
- **Whether `extractEscapes` should also report a `<style>` element's own `outerHTML` when the element is `root` itself.** The brief says root is included "when it is an `Element`" for the style-attribute population and states the `<style>` population without that qualifier. `guides/test.md` fixes no convention for the pair, and `extractOrphans` does not settle it because a root can carry the child class. Settling reading: the implementation `elements`' and `terrain`'s consumers actually need — `terrain/tests/app/browser/styles/tokens.test.ts` is the named caller.
