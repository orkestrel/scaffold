# Design — the rulings, per question

## 1. mcp backpressure and error surfacing

**Lead with the real defect: the discarded boolean is not it.** `StdioServerTransport` subscribes `#input` to `error` (`StdioServerTransport.ts:96`) and leaves `#output` unsubscribed. A caller-owned writable that faults — `EPIPE` when the MCP client dies holding the other end of the pipe, the common production case for a stdio server — emits `error` with no listener, which Node raises as an uncaught exception in the host process. The transport that exists to keep a fault contained crashes the process instead. The write's return value is a secondary, weaker question.

**The ruling.**

- **The boolean gets nothing, because it is the wrong instrument.** `write`'s `false` says the internal buffer passed its high-water mark; it does not say the write failed, and Node's own guidance is that a write error may not reach the callback and is only reliably observed on `error`. Awaiting the write's completion callback is strictly stronger than reading the boolean, and it delivers backpressure as a side effect: `send` resolves after that frame is flushed, so `sendStream` (`mcp/src/core/helpers.ts:1062`) stops producing faster than stdout drains. State that in the TSDoc rather than leaving a reader to wonder why no `drain` listener exists.
- **`send` awaits the write and rejects on its error.** Extract the promise-shaped write as `writeLine(output, line)` in `mcp/src/server/helpers.ts` beside `extractLines` and `dispatchLines`, barrel it, and document it. It is a pure leaf, independently testable, and inlining the `new Promise` in `send` buys nothing but an untestable one.
- **`start()` subscribes `#output` to `error` with the existing `#failure` handler; `#release()` removes it.** One handler, one channel, exact symmetry with the input side, and the caller-owned stream is left as found — no `destroy`, no `end`, no blanket clear. The class TSDoc already promises that ownership discipline for the input; the output now earns the same sentence.
- **The rejection has a live consumer already.** `bindServer` catches a `send` rejection and routes it to `server.emitter`'s `error` without letting it escape (`mcp/src/core/helpers.ts:1162-1172`). So the stronger contract needs no new machinery downstream — the package's own pump was written for it.
- **The siblings do not move; the contract states why they differ.** Pin the rule on `MCPClientTransportInterface.send`: *every transport reports a channel-level fault on `error`; a transport whose channel confirms the write and whose replies arrive out-of-band also rejects, and a transport whose exchange already reports through the emitter resolves.* Stdio client (`StdioClientTransport.ts:180`) and stdio server are the confirming pair; HTTP client emits and resolves because the reply path is the emitter; WebSocket and `MessagePort` cannot confirm a write at all and no-op on a closed channel. That sentence makes the family ruled-consistent instead of merely varied, and every existing behavior stays put.
- **No new option.** No `delivery` bound on `StdioServerOptions`. The write's callback is the confirmation, the stream is the caller's, and a bound with no first consumer is speculation the minimal-API law refuses.

**Executed pins** (in `mcp/tests/src/server/transports/StdioServerTransport.test.ts`, all with real `node:stream` writables — an injected minimal real implementation, not a fake): a writable whose `_write` calls back with an error makes `send` reject with that error; a writable that emits `error` outside any write makes the transport emit its domain `error` and the host survive; after `close()` the output stream carries none of this transport's listeners; a writable with `highWaterMark: 1` that defers its callbacks resolves sequential `send` calls in order, asserted as the ordering property rather than as a duration; `sendStream` over that writable delivers its lines in order.

**Surface movement.** `dist/src` moves. mcp bumps, probe re-pins and bumps (`probe/package.json:97`). The cascade ends at probe.

## 2. brief constants

**Name.** `INTERPRETATION_MEMBERS`, in `brief/src/core/constants.ts`. `{QUALIFIER}_{NOUN}` with the entity as qualifier, matching `TASK_OPERATIONS`, `TASK_DOMAINS`, `OUTPUT_FORMATS`, `RISK_SEVERITIES` already in that file.

**Declaration.**

```ts
export const INTERPRETATION_MEMBERS: readonly (keyof Interpretation)[] = Object.freeze([...])
```

The annotation carries the compile-time half that is worth having: a member that `@orkestrel/interpret` renames or removes reds at `check`. Completeness — a member interpret *adds* — is not expressible cast-free in an array declaration, and the shapes that reach it are worse than the drift they guard. A `Readonly<Record<keyof Interpretation, true>>` is compile-time complete and is a decorative sentinel table standing in for a list; `Object.keys` over such a record hands back `string[]` and buys nothing; `satisfies` with `as const` splits the declaration's contract across two mechanisms for one fact. Take the array, and put completeness where it can be measured.

**The completeness pin is a run, not a type.** `brief/tests/setup.ts` already builds a real `@orkestrel/interpret` engine through `createInterpret` with a documented `extractor` seam (`buildInterpret`, `setup.ts:86-109`). Drive it on matched input and assert set equality between that result's own keys and `INTERPRETATION_MEMBERS`. The exemplar is produced by the owning package, so it is a second mechanism that can disagree — a member added upstream appears in the engine's output and reddens. Carry the control in the same case: the same comparison against a shortened list must not hold.

**Where the pin lives.** Not in a `constants.test.ts` — `.claude/rules/tests.md` forbids a test file created solely for `constants.ts`. The new export obliges a guide row and a runnable example in `brief/guides/brief.md`, and `tests/guides.test.ts` transcribes that fence. That transcription is the completeness pin's home. Add one case in `tests/src/core/BriefCompiler.test.ts` proving the accessor-carried interpretation is captured with every member present, which is the behavior the constant exists for.

**Consumers.** `BriefCompiler.ts:284-299` deletes the literal and imports the constant; `#own(..., INTERPRETATION_MEMBERS)` at `:304` and `captureValue(live, INTERPRETATION_MEMBERS)` at `:327` take it directly. `#read`'s signature is unchanged.

**Write the TSDoc without a count.** The sibling entries in that file open "The twelve `TaskOperation` values" and "The eight `TaskDomain` values", which the writing law bans; the new entry does not copy them. Correcting the existing ones is recorded, not done here.

`dist/src` moves. brief bumps, and its zero runtime dependents make that a leaf release.

## 3. process assertions and proof placement

**The weak assertion.** The negative branch at `ProcessManager.test.ts:200-206` cannot be strengthened from the filesystem: on POSIX the destroy race's `SIGTERM` lands before the child's interpreter reaches its first line, so no marker the child writes can prove the spawn, and no grace value fixes that — a default `SIGTERM` kills the child whether or not the cooperative window is open. The evidence exists only on the parent side, in a `Process` the refusal never returns.

**The seam is missing, so add it.** `launch` constructs the child, discovers the registry is being destroyed, tears the child down, and throws `createProtocolError(id)` (`ProcessManager.ts:116-124`). It holds a live `ProcessInterface` whose `pid` is "fixed when construction returns" (`process/src/core/types.ts:204-205`). Carry it: add `readonly pid?: number` to `ProcessErrorContext` (`types.ts:573-584`), and have the mid-construction refusal build its `protocol` error with `{ id, pid }`. This is a product fix, not a test convenience — a consumer that loses this race today receives a `protocol` error that never discloses that a child was spawned and reaped, and cannot audit its own host.

**The test then collapses to one shape on every platform**: the thrown error is `protocol`, its `context.pid` is a positive number (the spawn happened), `process.kill(pid, 0)` stops succeeding within a budget (the child was terminated), and `manager.count` is `0`. The `win32`/POSIX fork, the `announce` fixture, the scratch directory, and the marker file all leave the case. That is the design win: the platform fork existed only because the evidence was being read out of the filesystem.

**The placement row closes as retained, with evidence.** `.claude/rules/tests.md` § Expensive proofs isolates a spawning proof "where the workspace has a gate that can hold it"; the fixed isolated projects are `distribution` and `service`, and a spawn proof is neither. The mirror rule places `tests/src/server/Process.test.ts` against `src/server/Process.ts` and is not optional. A package whose entire subject is spawning cannot move its spawning proofs out of `test` without removing its central claim from its own gate. So the rules place that proof exactly where it sits. What the row actually owes is the clause nobody applied: size every spawn-suite budget from a full contended run rather than an isolated one, and record the ruling in `process/guides/process.md` where a reader meets it. No rule file changes — `.claude/rules/*` is vendored from scaffold's `dist/host`, and editing one would force a scaffold bump and a fleet re-propagation for a sentence the existing conditional already covers.

# Alternatives

**For the process spawn evidence: assert only what the current test can see.** Rename the case to what it proves, drop the claim about spawning, and record the gap where a reader meets it, per the irreducible-gap rule. Cost: the ROADMAP row asks for an assertion that the spawn happened, and this does not deliver one — it closes the row by narrowing it, and it leaves a real consumer of the refusal path unable to learn that a child was spawned and reaped. The `context.pid` design wins because it makes the fact observable to consumers rather than to the test alone, and it deletes the platform fork as a side effect.

**For html entity membership: pin a content digest over `NAMED_ENTITIES` instead of vendoring the upstream set.** Cost: a digest recorded from the table is the table asserting itself — it detects change but proves nothing about correctness, and the first legitimate refresh turns it into a value someone updates to match whatever the table now says. The vendored fixture is a declaration that can disagree, and it costs nothing in published surface.
