**F1. `src/core/templates.ts:1912-1915` — the require drive passes vacuously for a reachable entry class.**
What is wrong: `selectDrivers(entry, 'commonjs')` can return `[]` while the test is running. Every driver's `commonjs` condition set includes `require`, so `selectEntries` (`:1447-1451`) demands `entry.commonjs`, which is `required && resolvesCommonJS(...)` (`:1664`). An entry whose `require` condition resolves to a `.mjs` target has `required === true` and `commonjs === false`, and if its `types` condition resolves a `.d.cts` it also passes the `entry.declaration.commonjs === undefined` throw at `:1904`. It then drives the runtime and compares nothing: `expect(reported).toStrictEqual([])` over an empty flatMap.
Why it matters: `.claude/rules/tests.md` § Discovery and adequacy audit requires an assertion to "fail rather than pass when its population is empty." Before this change the drive compared `driveRuntime(...)` against `readDeclaredExports(entry.declaration.commonjs)` unconditionally, so this entry class was compared. The comment at `:1908-1911` defers the case to "the untypable set's question", but `selectUntypable` (`:1466-1474`) keys on `declaresCommonJS`, a declaration-side predicate, while the gap is created by `resolvesCommonJS`, a runtime-target predicate — so the deferral does not cover the class. The import drive guards exactly this at `:1892` and the browser drive at `:2047`; the require drive alone does not.
What right looks like: give the require drive the same non-empty guard the import drive has, or partition the empty case into a reported set the way `undeclared` and `untypable` are partitioned, so the subpath is named rather than silently dropped.

**F2. `src/core/templates.ts:1563, 1574, 1496` — scratch project filenames collide across surfaces.**
What is wrong: `checkSurface` builds `name = \`surface.${driver.label}${slug}\`` without the extension, and `writeProject` keys the project file on that `name` (`tsconfig.${name}.json`). The module filename includes the extension and the project filename does not, so one entry's `.ts` and `.cts` surfaces under one driver write the same `tsconfig.surface.<label><slug>.json` with different `files` arrays — as do the browser face and the Node import face of one entry under `bundler`, which additionally share the same `surface.bundler<slug>.ts` module path with different key literals.
Why it matters: it is benign only because Vitest runs a file's tests sequentially and each write immediately precedes its own check. Any future `describe.concurrent`, `it.concurrent`, or file-level parallelism turns it into a check reading another surface's project or key list — a silent wrong answer, not a failure. This ships to every target.
What right looks like: include `surface.extension` in `name` so each surface owns its own project file.
