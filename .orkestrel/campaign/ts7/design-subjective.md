# Unit ts7-design — subjective lane

Returned by Workflow wf_61ea54af-596 node ts7-design:subjective on 2026-09-05; captured verbatim by the Orchestrator.

## Plan

I held the **subjective** lane: the shape of the migration, its units and order, what each package edits, and how the JavaScript-API retirement is phased.

**The ruling: split the move into a bridge step and a version step, and never run them together.** Swap every in-process `typescript` import to `@typescript/typescript6` while the line still installs `typescript` 6.0.3, prove the tree green, then re-pin `typescript` to `^7.0.2` as a one-line change. The bridge is Microsoft's own 6.x JavaScript API published under a scoped name; the dts probe measured it reporting compiler version 6.0.3 with `createSourceFile`, `transpileModule`, `forEachChild`, and `sys` all present (`orchestrator-measurements.md:95`), so the swap is a rename with no behaviour delta. Splitting the steps makes each failure legible: an import swap that reds is a bridge defect, a re-pin that reds is a `tsc` 7 defect. Fusing them produces one red with two candidate causes across the whole fleet.

**The bridge needs the owner's explicit confirmation by name before unit ts7-u1 starts.** `AGENTS.md` § Non-negotiable rules refuses an npm package the owner did not request. The owner's ask requests the move and asks for the alternative, which names the class but not the package. `@typescript/typescript6` at 6.0.2 is the package (`orchestrator-measurements.md:79`), and `unplugin-dts` names it in its own failure text (`orchestrator-measurements.md:74-76`).

**The whole fleet move is a development bump, not a cascade.** `typescript` is a development dependency everywhere, and `.agents/orchestration.md` § What a bump obliges rules that such a bump reaches nobody: re-pin, prove the gates, commit to `main`, do not publish. The one thing that could turn it into a runtime cascade is a moved `dist/`, and the declaration emitter does not change engine — `unplugin-dts` resolves the bridge itself and api-extractor analyses with its own bundled 5.9.3 (`orchestrator-measurements.md:93`; `ts7-absorb.result.md` row 6). Two packages publish on their own account: `scaffold`, because its vendored bytes move, and `probe`, because its shipped `src/server` code changes.

**ts7-u7 — `probe`.** Role `implementer`, engine Opus 5. Owned files: `src/server/stages/TypeStage.ts` and `src/server/helpers.ts` (`:399-407`). **ts7-r1 — retire the AST-shaped policy rules to the oxlint plugin.** Role `implementer`, engine Opus 5. `.claude/rules/workspace.md` § Policy instruments already assigns "the rules a single file's AST decides" to `configs/policy.ts` and leaves the sweep "the rules that are path- or text-shaped, and every rule whose subject is suppression itself." The placement rules `.claude/rules/architecture.md` § What the policy sweep proves enumerates — declaration kind against file name, the exported-declaration rule, the class-in-file rule, the `constants.ts` shape rule — are single-file AST decisions, so this phase is a law-conformance repair that happens to delete the compiler dependency, not a workaround built to dodge it. What stays in the sweep: the suppression-directive rule, the rule-map check, the path- and text-shaped portability rules, and the Markdown sweep. The pair still closes, because the sweep refuses every `eslint-disable` and `oxlint-disable` directive, so no plugin rule can be silently suppressed. Both files are vendored (`src/core/constants.ts:139`, `:143`), so this phase is a second scaffold release with a per-target `repair` and gate run.

**ts7-r2 — retire fence transpile to `node:module`.** Role `implementer`, engine Opus 5. Sites: `tests/guides.test.ts:334-337`, `tests/distribution.test.ts:430-431`, `tests/src/core/templates.test.ts:338-339`, and the generated proof's template. The Orchestrator measured `stripTypeScriptTypes` in transform mode returning stripped output on Node v22.22.2 (`orchestrator-measurements.md:44`). It is experimental, so its warning must be expected rather than suppressed, and this phase does not start until ts7-u0 reports the Node minor floor.

**ts7-r3 — retire checker-level work to `typescript/unstable/sync`.** Role `implementer`, engine Opus 5, one unit per subject. Subjects: the generated distribution proof (`src/core/templates.ts:1478-1516`), `database`'s `tests/setupServer.ts`, `probe`'s `TypeStage`, and the documentation proposal's control path. The Orchestrator measured the whole round trip over scaffold's core project at 61 ms, returning statements the `unstable/ast` guards recognise, node-level JSDoc tags, and `Symbol.getDocumentationComment(checker)` text (`orchestrator-measurements.md:53-68`). Treat every `unstable/*` import as a preview dependency: Microsoft's 7.0 post states 7.0 ships without an API and that 7.1 ships a new and different one (`ts7-research-report.md` row 1), so each of these units carries a stated re-read obligation at 7.1 and none of them is a migration prerequisite.

**What stays on the bridge until 7.1 is read.** The declaration build, because `unplugin-dts` resolves the bridge itself and needs no edit from us (`orchestrator-measurements.md:99`); api-extractor, which analyses with its own bundled 5.9.3 whatever the project pins (`ts7-absorb.result.md` row 6); `tests/src/core/templates.test.ts`, which parses generated config and proof text, and text parsing has no in-process counterpart in 7.0.2 (`orchestrator-measurements.md:34`); `lsp`'s `tests/setupConformance.ts`, for the same reason; and every site reaching `canHaveModifiers`, `getModifiers`, `flattenDiagnosticMessageText`, `ts.sys`, or `ScriptSnapshot`, none of which the 7.0.2 tarball carries (`ts7-absorb.result.md` row 9).

### The engines floor

**Hold `engines` at `>=22.12.0` across the line, and record the development-time Node floor in the guide instead.** `process.execve` needs Node 22.15.0 or later (`ts7-research-report.md` row 8), and `stripTypeScriptTypes` is experimental in Node 22. Neither is reachable from shipped code: the 7.0.2 `tsc` launcher falls back to `execFileSync` where `execve` is unavailable (`ts7-absorb.result.md` row 9, `lib/tsc.js:6-19`), and `stripTypeScriptTypes` enters only in test files under ts7-r2. `package.json:119-120` describes the runtime a consumer needs, and raising it would move a published constraint in every package for a tooling reason, turning a development bump into a fleet-wide publish. `.claude/rules/workspace.md` § Tooling requires `engines`, bundler targets, scoped configs, tests, and documentation to stay aligned, so the guide's § Dependency floors carries the development floor as its own row, named as such.

### `vue-tsc` and the browser environments

`vue-tsc` has no TypeScript 7 support (`ts7-research-report.md` row 5, vuejs/language-tools issue 5381, open since 2026-05-26). It does not block this migration. No fleet `package.json` names it, and scaffold's scripts run `tsc` alone (`ts7-absorb.result.md` row 3); it appears only in the script `blueprintToScripts` emits for a workspace that selects an `app/browser` environment (`src/core/compilers.ts:289-313`), and no fleet package holds an `app/browser/main.ts` file. Browser test projects are unaffected: Playwright and `@vitest/browser-playwright` carry no `typescript` dependency (`ts7-research-report.md` row 5). The ruling: raise the floor line-wide and record the limit in `guides/scaffold.md` — a generated workspace selecting `app/browser` pins `typescript` at 6 until `@vue/language-tools` supports 7 — with the fork implemented in `blueprintToDevDependencies` only when a workspace actually asks for that environment.

### The fleet order by edge class

The order is scaffold release, then targets, and the targets do not run in publish-layer order, because nothing here is a runtime edge. Classes, each named by what it edits beyond the shared pair: the shared-pair class edits `tests/guides.test.ts` and `tests/distribution.test.ts` only; the declaration-emitter class adds nothing, because `repair` writes the bridge range and `unplugin-dts` finds it; `database` adds its two server-setup files; `lsp` adds its conformance setup; `probe` adds shipped `src/server` code and is the only target of the group that bumps and publishes. Run `probe` first among the extras, because its release is the one a later target could need, and run the shared-pair class in slices that report as they finish, per `.agents/orchestration.md` § Writing concurrency.

### What the documentation proposal changes

**Option 3 keeps its mechanism and loses one sentence.** Its instruments read comment text through `sourceCode.getAllComments()` and the sweep's Markdown pass (`PROPOSAL.md:969-978`, `:991-994`), neither of which imports `typescript`. `PROPOSAL.md:1029` reads "The dependency delta is none. oxfmt `0.65.0`, oxlint `1.80.0`, and `typescript` `6.0.3` are all declared already" — that pin is wrong after ts7-u2 and the sentence takes the bridge's name. One design ruling follows: implement the summary-equality pairing (`PROPOSAL.md:1015-1019`) text-only inside the sweep, so the vendored file does not acquire a permanent compiler dependency of any generation.

**Option 1's control path re-homes and loses a member.** `PROPOSAL.md:409-411` names `ts.getJSDocTags`, `ts.getJSDocCommentsAndTags`, and `Symbol.getDocumentationComment` as the control the text-only scanner is measured against. Under 7.0.2 the control becomes `typescript/unstable/ast`'s `getJSDocTags` plus `typescript/unstable/sync`'s `Symbol.getDocumentationComment(checker)`; `getJSDocCommentsAndTags` is gone (`orchestrator-measurements.md:34`, `:58`). The control still runs and still holds outside the shipped edge, so Option 1's constraint that a `scaffold` verb never imports `typescript` is untouched. The probe surfaced one substantive detail for the amended `.claude/rules/documentation.md:35` rule: the checker renders `{@link Blueprint}` as bare `Blueprint`, and a `{@link}` inside a `@throws` tag splits into a `throws` part and a `link` part (`orchestrator-measurements.md:68`). The amended rule states the row is the sentence with each `{@link X}` rendered as `` `X` ``, so the scanner and the control must both add the backticks, and the pairing must be measured against the scanner's output rather than the checker's raw text.

## Claims

**C1. Swapping the specifier to `@typescript/typescript6` changes no member and no behaviour at any of the sites named in ts7-u1 and ts7-u5 through ts7-u7.** Refuted by any site whose gate reds after the swap with `typescript` still at 6.0.3, or by a member absent from the bridge that `ts7-absorb.result.md` rows 1 and 2 list as in use. The bridge probe read `version 6.0.3 createSourceFile function transpileModule function forEachChild function sys object` (`orchestrator-measurements.md:95`).

**C2. Moving `typescript` to `^7.0.2` needs no tsconfig edit, no script edit, and no template edit anywhere in the line.** Refuted by any target whose `tsc --noEmit -p` reddens under 7.0.2 where it passed under 6.0.3, or by a tsconfig in the fleet declaring `baseUrl`, `moduleResolution` `node`, `node10`, or `classic`, `module` `amd`, `umd`, `systemjs`, or `none`, `target es5`, `downlevelIteration`, `esModuleInterop: false`, or `outFile` (`ts7-research-report.md` row 2). Scaffold's own configs declare none of them (`ts7-absorb.result.md` row 4) and every scaffold project exits 0 under 7.0.2 (`orchestrator-measurements.md:22-23`). ts7-u0 extends the reading to the fleet.

**C3. The declaration build produces the same published bytes under 7.0.2 with the bridge declared as it does under 6.0.3.** Refuted by a material diff between a target's rebuilt `dist/` and its published tarball, excluding sourcemaps and whitespace, in the comparison ts7-u4 reports. The emit engine does not change: `unplugin-dts` resolves the bridge when the project's `typescript` lacks `createProgram` (`ts7-absorb.result.md` row 5), the rollup runs on api-extractor's bundled 5.9.3 in both states (`orchestrator-measurements.md:93`), and the bridge reports compiler version 6.0.3 against the current `^6.0.3` pin.

**C4. The fleet move publishes only `scaffold` and `probe`.** Refuted by a material `dist/` diff at any other target, by a target whose `engines` must rise, or by a target whose shipped `src/` imports `typescript`. `ts7-absorb.result.md` row 2 finds shipped compiler use in `probe` alone; every other site is a test or setup file. `.agents/orchestration.md` § What a bump obliges fixes the rule that decides this.

**C5. Retiring the AST-shaped policy rules to `configs/policy.ts` narrows no rule's coverage and adds no suppressible seam.** Refuted by a placement violation the sweep reports today and the plugin does not, by a rule whose subject is suppression landing in the plugin, or by a plugin rule that a file-level directive can silence while the sweep no longer refuses that directive. Each moved rule ships a `PolicyControl` entry whose negative control is drawn from outside its membership rule, per `.claude/rules/quality.md` § Instruments, and the paired form is what `.claude/rules/workspace.md` § Policy instruments already prescribes.

## Open questions

- **What is the lowest Node minor carrying `stripTypeScriptTypes`?** The measurement proves v22.22.2 has it (`orchestrator-measurements.md:44`) and proves nothing lower. ts7-r2 cannot state a development floor until a probe reads the version that added it. Settle before ts7-r2, not before ts7-u1.
- **Is every fleet `tests/setupPolicy.ts` byte-identical to scaffold's?** `ts7-absorb.result.md` names this unmeasured and reports matching headers on the sampled targets. A drifted copy means `repair` reports content drift and restores it, which changes ts7-u4 from a swap into a drift reconciliation for that target. Settle before ts7-u4.
- **Does each target's `tsc --noEmit` exit 0 under 7.0.2?** Proven for scaffold only. A target carrying a removed 6.0 option turns its unit from a re-pin into a config repair. Settle before ts7-u2, because a widespread failure would move the version step behind a config-repair unit.
- **Does any target's rebuilt `dist/` move materially under the bridge?** This decides C4 and therefore how many packages publish. Take one representative publishing target in ts7-u0 rather than discovering it target by target.
- **Does `@typescript/typescript6` track 6.x forward, and under what release cadence?** The line would inherit a frozen compiler if it does not. No source reached in this campaign states its policy, and the answer decides whether ts7-r1 through ts7-r3 are optional improvements or a deadline.
- **Does the owner confirm `@typescript/typescript6` by name?** No unit starts without it.
