## Evidence

### 1. The language server

- **Start command and flags.** `microsoft/typescript-go` (now merged into `microsoft/TypeScript` at path `tsc/`, per PR merged 2026-08-20 — see Row 4/merge note) defines the LSP entry in `cmd/tsgo/lsp.go`'s `runLSP` function: flags `stdio` (bool, "use stdio for communication"), `pipe` (string), `socket` (string), `pprofDir` (string), and `clientProcessId` (int, "use the given PID for the parent process watchdog"). The function refuses to start unless `stdio` is true, printing "only stdio is supported" and returning exit code `1` otherwise (github.com/microsoft/typescript-go/blob/main/cmd/tsgo/lsp.go, per WebFetch summary of that file). **There is no `--project` flag for LSP mode.** The invocation is `node node_modules/typescript/bin/tsc --lsp --stdio`, where `bin/tsc` (`/home/user/scaffold/node_modules/typescript/bin/tsc:1-2`) delegates to `lib/tsc.js`, whose flag-forwarding is described in Row 3.
- **`initialize` capabilities.** The merged repository's `tsc/internal/lsp/server.go` builds `InitializeResult.Capabilities` with `TextDocumentSync` (`OpenClose: true`, `Change: Incremental`, `Save: true`) and `DiagnosticProvider: &DiagnosticOptions{Identifier: "typescript", InterFileDependencies: true}` — the LSP 3.17 pull-diagnostics registration (`textDocument/diagnostic`) (raw.githubusercontent.com/microsoft/TypeScript/main/tsc/internal/lsp/server.go, WebFetch quote, lines cited by the fetch as ~2258-2336; I could not independently re-open the exact line numbers, so treat the line numbers as the fetch tool's report rather than a verified byte offset). The fetch found **no separate `publishDiagnostics` field** in `ServerCapabilities`; push diagnostics are sent through the `PublishDiagnostics` method (same file, ~line 1608) and gated by `s.initializationOptions.DisablePushDiagnostics` (default unset ⇒ push diagnostics run by default, alongside the always-registered pull capability) (same fetch, ~lines 2371-2373). Independently, github.com/microsoft/typescript-go/issues/2362 (closed "not planned") reports a real client (Emacs eglot) not receiving `publishDiagnostics` from tsgo, consistent with pull being the primary/expected model and push being conditional on client capability negotiation.
- **Overlay `didOpen` with no file on disk.** The merged repo's `tsc/internal/project/overlayfs.go` (raw.githubusercontent.com/microsoft/TypeScript/main/tsc/internal/project/overlayfs.go, WebFetch quote) defines `type overlayFS struct { … overlays map[tspath.Path]*Overlay }`; its file-read path checks the in-memory overlay map first and only falls back to the backing `vfs.FS` if no overlay exists, so an overlay opened via `didOpen`/`didChange` does not require a corresponding disk file. `internal/lsp/server.go`'s `handleDidOpen` calls `s.session.DidOpenFile(ctx, params.TextDocument.Uri, …)` (WebFetch quote of the same file, ~lines 2431-2433).
- **Project selection with several `tsconfig` files.** DeepWiki's paraphrase of `internal/project/snapshot.go:82-84` (secondary source, not independently re-fetched at that exact path) states the server resolves a file's owning project by checking the existing `ProjectCollection` for a configured project already covering the file, then falling back to searching ancestor directories for the nearest config file, and finally to an `InferredProject` if none is found. This is **not independently confirmed against the raw source** — my direct fetch of `snapshot.go` returned only the `Snapshot.GetDefaultProject` wrapper delegating to `ProjectCollection.GetDefaultProject`, whose body I could not retrieve (GitHub code search required authentication). Treat the ancestor-search claim as secondary until the `ProjectCollection` body is read directly.
- **`initializationOptions` naming a project.** Neither the WebFetch of `server.go`'s initialize handling nor any search result names an `initializationOptions` field for pinning a specific `tsconfig` path; the only documented `initializationOptions` field found is `DisablePushDiagnostics`. This is a **gap**, not a confirmed absence — I did not exhaustively enumerate the `InitializationOptions` struct.

### 2. The `--api` surface

- **Package shape.** `typescript` 7.0.2's `package.json` (`/home/user/scaffold/node_modules/typescript/package.json:37-51`) exports only `./unstable/sync`, `./unstable/async`, `./unstable/fs`, `./unstable/proto`, and AST subpaths from `.`; the bare `.` export is `./lib/version.cjs` (version info only). No stable in-process compiler API ships.
- **`updateSnapshot` and overlays.** `dist/api/sync/api.d.ts:39` (`/home/user/scaffold/node_modules/typescript/dist/api/sync/api.d.ts:39`) types `updateSnapshot(params?: UpdateSnapshotParams): Snapshot`. `UpdateSnapshotParams`/`LSPUpdateSnapshotParams` (`dist/api/proto.d.ts:51-97`) carry `openProjects`, `openFiles`, `closeFiles`, and `fileChanges: FileChanges` (`{changed, created, deleted}` or `{invalidateAll: true}`) — file identity only, no inline text payload on `updateSnapshot` itself.
- **In-memory content is supplied at client construction, not per `updateSnapshot` call**, through `ClientSpawnOptions.fs?: FileSystem` (`dist/api/options.d.ts:9-16`). `createVirtualFileSystem(files: Record<string,string>)` (`dist/api/fs.d.ts:22`, implemented `dist/api/fs.js:4-108`) returns a `FileSystem` whose `readFile` returns the in-memory string for a path that need not exist on disk, `fileExists`/`directoryExists`/`getAccessibleEntries` reflect only the virtual tree, and it exposes `writeFile`/`removeFile` to mutate that in-memory content later. `dist/api/fs.d.ts:9-15`'s `FileSystem.readFile` doc states: "Return the file content as a `string`… Return `null` to indicate the file does not exist (without falling back to the real FS). Return `undefined` to fall back to the real filesystem" — a genuine overlay-over-disk semantic.
- **Wiring to the spawned process.** `dist/api/sync/client.js:9-53` shows `Client`'s constructor spawning `tsserverPath` (default resolved by `getExePath()`, `dist/api/options.js:8-10`) with args `["--api", "--cwd", cwd]` plus `--callbacks=<names>` for whichever `fs` methods were supplied, then registering each supplied `fs[name]` as an RPC callback the child invokes over the wire (`dist/api/sync/client.js:38-53`). The transport is `SyncRpcChannel` (`dist/api/syncChannel.js:62-156`), which on POSIX does `spawn(exe, args, {stdio:["pipe","pipe","inherit"]})` (`dist/api/syncChannel.js:126-128`) and communicates over the child's stdin/stdout with a MessagePack tuple protocol read/written via `fs.readSync`/`writeSync` on the raw pipe fds — **not through `process.execve`** (see Row 3).
- **Diagnostics carry file, position, and text.** `dist/api/sync/types.d.ts:288-303` defines `Diagnostic { fileName?: string; pos: number; end: number; code: number; category: DiagnosticCategory; text: string; … }`, and `Program.getSemanticDiagnostics(file?: DocumentIdentifier): readonly Diagnostic[]` (`dist/api/sync/api.d.ts:183`) returns these. `pos`/`end` are character offsets, not line/column — the API does not itself convert to `{line, character}`.
- **Official stability framing.** The TypeScript 7.0 devblog ("Announcing TypeScript 7.0", devblogs.microsoft.com/typescript/announcing-typescript-7-0) states verbatim (per WebFetch quote): *"While TypeScript 7.0 is here, it does not ship with an API. We expect TypeScript 7.1 to ship with a new (and different) API"* and *"With TypeScript 7.1 on the horizon, we hope to bridge any gaps…"* — no committed date or scope for 7.1's API is given in that quote. This is a **secondary-search reconciliation, not a contradiction**: the shipped `unstable/*` subpaths in the installed 7.0.2 package are Microsoft's own preview of that surface, explicitly namespaced `unstable`, and multiple secondary sources (WebSearch aggregation citing the `typescript-eslint`/`nx` breakage threads and an InfoQ/windowsforum-class writeup) describe `unstable/sync`/`unstable/async` as pre-existing, not-yet-stable scaffolding for the 7.1 API rather than a second, contradictory claim. I did not find a primary Microsoft statement reconciling "does not ship with an API" against the shipped `unstable/*` exports directly; treat that reconciliation as inference, not a quoted fact.

### 3. Node

- Node's own docs (nodejs.org/docs/latest-v22.x/api/process.html, WebFetch quote, page shows Node v22.23.2) state `process.execve(file[, args[, env]])` — "Added in: v22.15.0", "Stability: 1 - Experimental" — replaces the current process image via the POSIX `execve` call, preserving only stdin/stdout/stderr file descriptors, and **"is not available on Windows or IBM i."** Node 22.22.2 (named in the brief) sits between the `v22.15.0` introduction and the `v22.23.2` docs snapshot I fetched, with no deprecation or removal noted in that window, so `process.execve` is present and experimental there. I did not run `node --version` on this host — no Bash tool is in my allowlist — so the installed Node version is **taken from the brief, not independently verified here**.
- `typescript` 7.0.2's CLI launcher `lib/tsc.js` (`/home/user/scaffold/node_modules/typescript/lib/tsc.js:1-28`) is the only file in the installed package matching `execve` (confirmed by `Grep` over `node_modules/typescript`). On non-Windows with `typeof process.execve === "function"`, it calls `process.execve(exe, [exe, ...process.argv.slice(2)])` inside a `try/catch` that silently falls back; the fallback is `execFileSync(exe, process.argv.slice(2), {stdio: "inherit"})` (`lib/tsc.js:18-28`). Both branches preserve the current process's stdio: `execve` by POSIX definition (per the Node doc quote above), and `execFileSync(..., {stdio:"inherit"})` by inheriting whatever stdio the launching Node process already had. **This launcher path is unrelated to the `--api` client**, which spawns the native binary directly with `node:child_process.spawn` and explicit `stdio: ["pipe","pipe","inherit"]` (`dist/api/syncChannel.js:126-128`) — it never goes through `bin/tsc`/`lib/tsc.js` or `process.execve` at all. So a program driving `tsc --lsp --stdio` as a child (piped, not inherited) via `node node_modules/typescript/bin/tsc --lsp --stdio` gets its stdio correctly threaded through either the `execve` replace-in-place (fds preserved across the swap) or the `execFileSync` inherit fallback; a program using `typescript/unstable/sync` never touches this code path because it spawns the native binary itself.

### 4. Prior art

- **oxlint / `tsgolint`.** The oxc project's own blog ("Oxlint Type-Aware Preview", oxc.rs/blog/2025-08-17-oxlint-type-aware.html, WebFetch quote) states verbatim: *"tsgolint does not communicate with typescript-go via public APIs. Instead, it compiles typescript-go by shimming its internal APIs to make them public"* and *"All type-aware rules are written directly against these shimmed APIs,"* adding *"While this isn't the recommended approach for accessing internals, it works!"* `tsgolint` is a Go binary (oxlint, Rust, is the CLI frontend; `tsgolint`, Go, is the backend, per WebSearch synthesis of oxc.rs/docs/guide/usage/linter/type-aware.html and github.com/oxc-project/tsgolint) — it does not use the JS `unstable/sync|async` API or the LSP at all, and is not a reusable pattern for a Node.js consumer such as `@orkestrel/probe`.
- **VS Code "TypeScript Native Preview" extension.** WebSearch synthesis of devblogs.microsoft.com/typescript/announcing-typescript-native-previews states the extension and `tsgo` "speak native LSP instead of the old tsserver protocol," confirming the LSP surface (Row 1) as the route real editor tooling already takes against `tsgo`/TypeScript 7.
- **Vitest's typecheck mode.** No primary Vitest maintainer statement was directly fetched (a `WebFetch` of Vitest's own docs/GitHub was not attempted after the first search); the evidence here is secondary — a Medium article ("I Tested 15 Popular Libraries With TypeScript 7 Toolchain") and corroborating GitHub issues (`fi3ework/vite-plugin-checker#516` "Support TypeScript Native (`tsgo`)", `get-convex/convex-js#177`) — reporting that Vitest's `--typecheck` mode calls `tsc --noEmit`/`vue-tsc` directly and needs `typescript@6` in scope, so the ecosystem's recommended pattern is a **side-by-side install**: pin `typescript` to `6.x` for tools that need the Strada API/CLI parsing, and run `tsgo --noEmit` separately purely for fast checking. This is the opposite choice from rebuilding the tool's type stage on 7.x: Vitest did not adopt `unstable/sync`, the LSP, or `tsgo` internals for its typecheck feature at the time these sources were written.

## Distillate

1. **The language server** — holds as a workable diagnostics transport. `tsc --lsp --stdio` starts a real LSP server (primary source: `cmd/tsgo/lsp.go`), it announces LSP 3.17 pull diagnostics (`DiagnosticProvider`) plus opt-out-able push diagnostics (`PublishDiagnostics`, gated by `DisablePushDiagnostics`), and it serves `didOpen` overlays with no backing disk file (primary source: `tsc/internal/project/overlayfs.go`). **Does not hold**: there is no `--project`/`--lsp-config`-style flag and no confirmed `initializationOptions` field for pinning a project — project selection is implicit (existing configured project, then, per a secondary source only, ancestor-directory tsconfig search, then an inferred project). A workspace with several sibling `tsconfig` files (`configs/src/tsconfig.core.json`, `tsconfig.server.json`, root `tsconfig.json`) would need `openProjects`/workspace-folder configuration to make each project explicit rather than relying on directory inference, and that mechanism is unconfirmed from primary source here.
2. **The `--api` surface** — holds for the concrete mechanics: `updateSnapshot`, `Program.getSemanticDiagnostics`, and `Diagnostic{fileName, pos, end, code, category, text}` are real, typed, and installed in 7.0.2. In-memory, not-on-disk type-checking is supported through `ClientSpawnOptions.fs` + `createVirtualFileSystem`, which is a genuine analog of the current 6.x `LanguageServiceHost` overlay pattern (`/home/user/scaffold/node_modules/@orkestrel/probe/dist/src/server/index.js:1958-1997` shows the exact same overlay-over-`typescript.sys` shape used today). **Does not fully hold as "stable"**: Microsoft's own devblog frames 7.0 as shipping no API and defers "a new (and different) API" to 7.1, so building on `unstable/sync` today means building on a surface Microsoft has not committed to keep. Whether the virtual filesystem's `writeFile`/mutate-then-`updateSnapshot({fileChanges})` pattern supports repeated candidate-draft edits without respawning the child process is **not directly documented** — it is a plausible reading of the API shape, not a cited fact.
3. **Node** — holds. `process.execve` exists and is documented stable-enough-to-rely-on (experimental but not removed) from Node 22.15.0 onward, so it is present at the brief's named 22.22.2. It is irrelevant to the `--api`/LSP client path, which never uses it; it only matters if something spawns `node node_modules/typescript/bin/tsc --lsp --stdio` as an external CLI rather than driving `typescript/unstable/sync|async` directly — and in that case, stdio inheritance is correct on this host either through the `execve` process-image swap or its `execFileSync(..., {stdio:"inherit"})` fallback.
4. **Prior art** — mixed signal, not a clean precedent either way. The tool actually built for TypeScript 7 (`tsgolint`) bypasses both the LSP and the public `unstable/*` API by shimming Go internals — a path unavailable to a Node.js consumer. The tool with an equivalent job to `@orkestrel/probe`'s type stage (Vitest's typecheck mode), per secondary sources, chose *not* to move onto `tsgo`/TypeScript 7 for its checking API and instead kept `typescript@6` for that purpose, running `tsgo` only as a separate, faster, non-integrated check. No located prior art demonstrates a Node.js tool driving `typescript/unstable/sync` (or the LSP) in-process for candidate-draft type-checking the way `@orkestrel/probe` does today with the 6.x `LanguageService`.
