### Row 3 — `rolldown-plugin-dts` and `tsdown`

- Latest registry versions today: `rolldown-plugin-dts@0.28.5` and `tsdown@0.23.0` (both `dist-tags.latest` on `registry.npmjs.org`).
- `rolldown-plugin-dts@0.28.5`'s `package.json` (`unpkg.com/rolldown-plugin-dts@0.28.5/package.json`) lists `@typescript/native-preview: "*"` and `typescript: "^5.0.0 || ^6.0.0 || ~7.0.0"` as optional peers, and pins `@typescript/native-preview: npm:typescript@^7.0.2` in `devDependencies` — confirming the plugin is developed and tested against `typescript@7.0.2` itself.
- The plugin's README (`raw.githubusercontent.com/sxzz/rolldown-plugin-dts/main/README.md`) states the `generator` option takes `tsc`, `oxc`, or `tsgo`, and auto-selects: "`oxc` when `compilerOptions.isolatedDeclarations` is enabled. `tsgo` when TypeScript 7 is installed as `typescript`. `tsc` otherwise." It further states `tsgo` requires "TypeScript 7 or `@typescript/native-preview`," is "experimental and requires a `tsconfig.json`," and "does not support custom languages." The document does not explicitly state whether `tsgo` mode drives the `tsgo` binary directly or bundles its `--declaration` output; this is unresolved in the primary source.
- The README also warns generally (independent of `tsgo`): "Declaration bundling requires an ESM Rolldown output... Syntax such as `export =` or `import x = require('x')` may not bundle correctly. If it comes from a dependency, mark that dependency as external." This is evidence against, not for, faithful re-export/`declare module` preservation for CommonJS-style TypeScript syntax; no comparison of its output shape (re-exports, `declare module`, preserved TSDoc) against `api-extractor`'s rollup was found in either project's documentation.
- `tsdown`'s own docs (`tsdown.dev/options/dts`) do not mention `tsgo` at all in the content retrieved; they describe only the `isolatedDeclarations` → `oxc-transform` fast path versus the plain TypeScript-compiler fallback. `tsgo` support is documented at the `rolldown-plugin-dts` layer, which `tsdown` uses internally, not at the `tsdown` option-surface layer per what this task could fetch.
- **Vite 8 (rolldown-based) usage:** the plugin is usable as a Vite plugin under rolldown-vite, but is not fully baked in — `github.com/sxzz/rolldown-plugin-dts/issues/201`, "Cannot use in Vite 8 with `tsgo: true` without `enforce: pre`" (closed), documents a real user needing to manually patch plugin ordering (`plugin.name.endsWith('fake-js') ? { ...plugin, enforce: 'pre' } : plugin`) to make `tsgo: true` work inside a Vite 8 config, and the reporter explicitly notes awareness "that the plugin wasn't officially supported in Vite 8 yet." Separately, Vite's own repository (`github.com/vitejs/vite/commit/449d7f30a85ae70eb0037fdab0b1ebf2e4927a24`) adopted `rolldown-plugin-dts@^0.13.3` only as a devDependency to build Vite's own `.d.ts` files — that commit does not ship `rolldown-plugin-dts` to Vite's consumers; a project must add the plugin itself.

### Row 4 — `tsc` 7 declaration emit

- `typescript@7.0.2` is confirmed as the registry's current latest version (`unpkg.com/typescript/package.json` and `unpkg.com/typescript@7.0.2/package.json` both report `"version": "7.0.2"`, `"bin": {"tsc": "./bin/tsc"}`).
- The TypeScript 7.0 general-availability announcement (`devblogs.microsoft.com/typescript/announcing-typescript-7-0/`) gives the GA release as `7.0.0` (2026-07-08) and states plainly that TypeScript 7 lacks a stable programmatic API until 7.1, so "workflows that use Vue, MDX, Astro, Svelte, and others will likely not yet be able to leverage TypeScript 7" — directly explaining why `createProgram`-dependent tools (row 1, row 2) cannot yet target it.
- The `microsoft/typescript-go` README (`raw.githubusercontent.com/microsoft/typescript-go/main/README.md`) carries the feature-parity table cited in the brief. It marks "Declaration emit | done | -", "Commandline and `tsconfig.json` parsing | done", and "Build mode / project references | done" — so `--declaration --emitDeclarationOnly -p configs/src/tsconfig.core.json` is a supported invocation shape per the matrix. The same document separately states: "Declaration emit differs greatly, intentionally, to be closer to TS declarations."
- `github.com/microsoft/typescript-go/issues/1952`, "Declaration emit crash" (closed, fixed by PR #2512), documents that a real production monorepo hit a `panic: Unknown parent for parameter: KindArrowFunction` during declaration emit — evidence that "differs greatly, intentionally" is not purely cosmetic; declaration-emit crashes on real code have occurred and been patched individually.
- `github.com/microsoft/typescript-go/issues/972`, "tsgo cannot emit declaration when error, but tsc can," is a second concrete difference a consumer would see: unlike classic `tsc`, `tsgo`/`tsc` 7's declaration emit does not proceed past type errors the way TypeScript 6.x's did.

### Row 5 — Fence transpile: `node:module` `stripTypeScriptTypes` and default type stripping in Node 22

- Node's current 22.x LTS line, per `nodejs.org/dist/index.json`, has moved past the brief's cited `22.22.2` (dated 2026-03-24): the most recent entries are `22.23.2` (2026-08-26), `22.23.1` (2026-06-22), `22.23.0` (2026-06-17), and `22.22.3` (2026-05-13). `22.22.2` is three patch releases behind the current LTS tip as of 2026-09-05.
- `module.stripTypeScriptTypes(code[, options])` (`nodejs.org/docs/latest-v22.x/api/module.html`): added in v22.13.0, stability "1.2 - Release candidate."
  - `mode: 'strip'` (default): "Only strip type annotations without performing the transformation of TypeScript features," and "will throw an error if the code contains TypeScript features that require transformation such as `Enums`."
  - `mode: 'transform'`: "Strip type annotations and transform TypeScript features to JavaScript," demonstrated on a `namespace` containing runtime code (`namespace MathUtil { export const add = ... }`), which strip mode alone rejects.
  - `sourceMap` (boolean, default `false`): usable "only when `mode` is `'transform'`"; "When mode is `'strip'`, source maps are not generated, because locations are preserved. If `sourceMap` is provided, when mode is `'strip'`, an error will be thrown."
  - `sourceUrl` (string): appended as a `//# sourceURL=...` comment to the output in either mode.
  - General warning: "The output of this function should not be considered stable across Node.js versions, due to changes in the TypeScript parser."
  - The doc states the function "can be used to strip type annotations from TypeScript code before running it with `vm.runInContext()` or `vm.compileFunction()`" — confirming the `vm` use case is documented, though no worked example combining the two was found in the fetched page content.
- `nodejs.org/docs/latest-v22.x/api/typescript.html` (current content is versioned "v22.23.2" per the page's own history block):
  - Default execution: "By default Node.js will execute only files that contain no TypeScript features that require transformation, such as enums. Node.js will replace inline type annotations with whitespace, and no type checking is performed." Type stripping became default-on at `v22.18.0` ("Type stripping is enabled by default"); `--experimental-strip-types` itself was "Added in: v22.6.0," stability "1.2 - Release candidate."
  - The four named features "that require transformation" (that is, need `mode: 'transform'` or `--experimental-transform-types`) are: `Enum` declarations, `namespace` with runtime code, parameter properties, and import aliases. A `namespace` exporting only types (no runtime code) is explicitly supported in default strip mode.
  - `--experimental-transform-types` (added v22.7.0, stability 1.2) "Enables the transformation of TypeScript-only syntax into JavaScript code. Implies `--enable-source-maps`."
  - Decorators are unsupported even under transform mode and produce a parser error, because they remain a TC39 Stage 3 proposal Node does not polyfill.
  - The fetched page did not contain the literal strings `import x = require`, `export =`, or `data:`, so **no primary-source Node.js documentation directly names `import x = require()` or `export =` handling**. A secondary source (`WebSearch` summary citing `dev.to`/other guides, not independently fetched here) states that `import x = require(...)` is left untouched by strip-only mode and causes a runtime `SyntaxError` because it is not erasable type syntax; it is plausible (inference, not confirmed against Node's own docs) that this is the concrete case the docs' "import aliases" transform-required item refers to, but the Node documentation itself does not use that phrase, so this mapping is unverified.
  - ESM `data:` URL imports are a separately documented general Node feature (`import 'data:text/javascript,...'`, per search results referencing `nodejs.org/docs/latest-v24.x/api/esm.html`), and combining `stripTypeScriptTypes` output with a constructed `data:` URL `import()` is a composition of two independently documented features rather than an example Node's own docs show together.

## Distillate

**Declarations:** no bridge-free `createProgram`-based emit-and-rollup path exists for a TypeScript-7-only fleet today. `vite-plugin-dts@5.1.0`/`unplugin-dts@1.1.0` and `@microsoft/api-extractor@7.59.0` both still require a 5.x/6.x `typescript` package with the legacy Compiler API (`ts.sys`, `createProgram`) present at their package root; TypeScript 7.0.2 does not expose that API, and no release, PR, or maintainer statement in either project's public tracker commits to `tsgo`/TypeScript-7 support (`unplugin-dts` issue #465 is an open question with no captured maintainer answer; `microsoft/rushstack` has no TypeScript 7 issue at all). `api-extractor` additionally ships its own pinned `typescript@5.9.3` as a hard dependency, so using it at all installs a 5.x compiler regardless of what builds the fleet's source. The one component with real, primary-sourced TypeScript 7/`tsgo` support is `rolldown-plugin-dts@0.28.5` (a documented `generator: 'tsgo'` mode, auto-selected when `typescript` resolves to version 7), but it is Rolldown/`tsdown`-native, its Vite 8 integration with `tsgo: true` needed a manual plugin-ordering patch as of a still-referenced GitHub issue, and its own README warns that `export =` and `import x = require(...)` "may not bundle correctly." `tsc` 7.0.2 itself lists declaration emit as "done" in its feature matrix and can run `--declaration --emitDeclarationOnly -p <tsconfig>` directly, but the same source warns declaration emit "differs greatly, intentionally," with at least one now-fixed crash on real code. Net: emitting declarations with `tsc` 7 is supported; rolling several such `.d.ts` files into one bundled `index.d.ts` without a 5.x/6.x-compiler-carrying tool is not yet available from any tool this research reached, `rolldown-plugin-dts`'s `tsgo` mode being the closest and still short of drop-in.

**Fences:** `node:module`'s `stripTypeScriptTypes({mode: 'transform'})` is the direct, no-bridge, no-5.x/6.x-compiler replacement for the fleet's current 6.x `transpileModule` fence transpile, available and default-on since Node 22.18.0 (stability "release candidate," not yet 2.0/stable). It transforms `enum` and runtime-bearing `namespace` bodies (both rejected by default `mode: 'strip'`), supports `sourceMap`/`sourceUrl` for transform-mode output, and its output is documented as runnable through `vm.runInContext()`/`vm.compileFunction()`. Its two open gaps are: no Node-documented statement on `import x = require()`/`export =` handling (secondary sources say strip-only mode leaves these unhandled and produces a runtime `SyntaxError`, unconfirmed against Node's own docs), and no worked example combining transformed output with an ESM `data:`-URL `import()` (each half is separately documented, not the combination). For running a `.ts` fence directly rather than through the `node:module` API, plain `node file.ts` already default-strips since Node 22.18.0 and errors on the same four transform-requiring constructs unless `--experimental-transform-types` is also passed.
