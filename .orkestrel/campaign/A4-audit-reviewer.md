## Findings outside the claims

**F1. `PageServerInterface.destroy` breaks the lifecycle verb of the twin it is named for.** `src/browser/types.ts:118-121` declares `ScopeServerInterface.stop` with the remark "it is idempotent, and it ends this handle's lifetime permanently"; `src/browser/types.ts:198-204` declares `PageServerInterface.destroy` with the same sentence, in the same file, for the same action. The guide (`guides/mcp.md` § Browser transport), the factory TSDoc (`src/browser/factories.ts:531-533`), and the type doc all call `createPageServer` the page twin of `createScopeServer`. Every other lifecycle terminal this package publishes on a returned handle is `stop` — `src/server/types.ts:511`, `src/core/types.ts:837`, `:1875`, `:1951`, `src/core/MCPProgressReporter.ts:129`, `MCPStreamController.ts:144`, `MCPTextStreamController.ts:101` — and `close` is reserved for transports, matching the platform's own word. `D1-design-planner.md:119-126` specified `stop()` for this interface; the unit changed it with no recorded reason. Why it matters: "one concept, one term" is what lets a consumer who learned `createScopeServer` use `createPageServer` without reading it, and the two sit side by side in one barrel and one guide section. What right looks like: rename `PageServerInterface.destroy` to `stop`, and update the Methods table row, the guide fence at `guides/mcp.md:3954-3960`, the factory TSDoc, and the browser tests in the same change. Bound on the fix: do not touch `ModelContextInterface.destroy` (`src/browser/types.ts:496`). That one is correct — the bridge owns an `Emitter`, calls `emitter.destroy()` last, and publishes `emitter.destroyed`, which is the fleet's vocabulary for an emitter-owning entity.

**F2. A name this handle already registered is never reconciled, so `publish` silently serves a stale descriptor.** `src/browser/ModelContext.ts:130` skips any descriptor whose name is already in `#controllers`, and `#prune` (`:164-171`) keeps any name `tools.tool(name)` still answers, so a second `publish` can only add and remove — never replace. Two reachable vectors, both through the package's own API and both silent:
- Replace a definition. `tools.add(createTool({ name: 'search', description: 'A', parameters: SCHEMA_V1, … }))`, `await bridge.publish(tools)`, then `tools.add(createTool({ name: 'search', description: 'B', parameters: SCHEMA_V2, … }))` — the installed `ToolManagerInterface` overwrites by name in place — then `await bridge.publish(tools)`. The registry still advertises description A and SCHEMA_V1, while `#run` is bound to `(tools, 'search')` (`:150`) and resolves the name at call time, so it executes the V2 tool. A foreign agent then sends arguments matching the advertised schema and receives an argument-validation rejection for arguments the registry told it were valid.
- Publish from a second manager. `publish(managerA)` then `publish(managerB)`: a name present in both keeps A's binding forever, because `#run` captured `tools` at registration while `#prune` reads the current call's manager. Nothing in the type or the TSDoc says the handle is bound to one manager, and `createPageServer({ tools })` and `createScopeServer({ tools })` both take theirs at creation, so the per-call parameter invites exactly this.
The documented workaround makes it worse rather than closing it. `guides/mcp.md:3967-3976` and the `publish` TSDoc tell the consumer to remove the name from the manager, publish, add the replacement, and publish again — which means mutating the live registry the sibling face is serving. The composition this guide promotes is `createPageServer({ tools })` beside `createModelContext().publish(tools)` over one manager, so the prescribed dance takes the tool off the MCP wire while it runs. What right looks like: retain the projected descriptor beside its controller, and on a later `publish` compare the freshly projected descriptor with the retained one — identical leaves the registration untouched, different aborts the old controller and registers the new descriptor. Bound on the fix: an identical projection must not re-register, or every `publish` churns the registry and fires spurious `toolchange`; the handle must still abort only its own controllers. The existing test `leaves a name it already registered alone on a second call` keeps its intent under that rule and needs no change; add one for the replaced definition.

**F3. "the chromestatus record read on 2026-08-12" misdates the reading, in the guide, in published source, and in the tests.** `G5c-webmcp-idl.md` § 7 records the fetch as `2026-09-15` and the JSON's own `updated.when` as `2026-08-12`, so 2026-08-12 is when chromestatus last changed the record, not when this project read it. The guide asserts both readings within one feature: `guides/mcp.md:4620` says `G5c` was "taken from the WebMCP specification on 2026-09-15", while `:4654` and `:5005` both say "the chromestatus record read on 2026-08-12". The same false phrase ships in `src/browser/factories.ts:417` and in the `src/browser/types.ts` WebMCP banner, and is repeated in `tests/fixtures/modelContext.ts` and the comments of `tests/src/browser/ModelContext.test.ts` and `factories.test.ts`. Why it matters: this is the provenance a reader uses to judge how stale the shipping-status claim is, and `.claude/rules/writing.md` § Claims and time requires a date the reader can check attached to the event it names. What right looks like: write "the chromestatus record, read 2026-09-15 and last updated 2026-08-12, reports `Proposed` with `"flag": false` and `"origintrial": false`" at each site, or drop the update timestamp where only the read date carries the claim.

**F4. `PageServerOptions.client` restates `MCPClientOptions` and loses two of its members.** `src/browser/types.ts:178-182` declares the group as an anonymous object literal carrying `identity`, `capabilities`, `version`, and `timeout`, while `src/core/types.ts:2675-2691` declares `MCPClientOptions` with those plus `on` and `error`. The factory spreads the group into `createMCPClient` (`src/browser/factories.ts:384-387`), so the omission is purely a type-level one. Consequences, both concrete: a consumer of `createPageServer` can never supply the client's listener-error handler, which `MCPClientOptions.error` documents as where a listener throw routes instead of to a domain event, and there is no post-construction way to set it; and a member added to `MCPClientOptions` later becomes silently unreachable through this factory, with the barrel type test (`toEqualTypeOf<PageServerOptions>`) passing throughout. ## Attacked and held

- **Claim 6, the destroy-during-publish interleaving.** I tried to leave a registration alive past `destroy` by racing it against an in-flight `registerTool`. The controller is in the map before the suspension, so `destroy` aborts it, and the resumed loop re-reads the flag. Adjacent behaviour that looks like the defect and is correct: after `destroy` the `#register` catch path still deletes, aborts, and rethrows, so a caller can receive a rejection from a publish that was cancelled rather than failed — that rejection is honest, and the queue's `.catch` keeps it from poisoning a later call.
- **Claim 9, the double's divergences.** The double omits the IDL's `ontoolchange` attribute and resolves `executeTool` to a non-string against an IDL that types `Promise<DOMString>`. Both are correct as shipped: the bridge subscribes through `EventTarget`, which the IDL gives it, and `WebMCPRegistryInterface` declares only the members the bridge touches, exactly as `ScopeInterface` does; and coercing the result either way would encode the contradiction `G5c` § 1 records as open. The double also invents a `fromOrigins` semantic the IDL leaves undefined (a filter that excludes the fixture's own origin returns nothing), and the test named for it limits itself correctly to "forwards the origins option".
- **`change` firing for this handle's own registrations.** Every `publish` produces one `change` per tool, so a consumer following the documented "re-read `adopt`" pattern re-reads once per tool it just published. This mirrors the registry faithfully and the matrix row states the bare-signal design, so I did not treat it as a defect.
- **`adopt` returning this page's own published tools.** Faithful to `getTools`, and the guide does not claim otherwise. A consumer that adopts into the manager it publishes from would wrap its own tools; that is consumer misuse rather than a package defect, and nothing in the guide invites it.
- **`WEBMCP_CHANGE_EVENT` beside the `'toolchange'` literal in `WebMCPRegistryInterface`.** The event name has two homes, which is the drift the `src/browser/constants.ts` comment warns about for the member list. It is not substantiated as a defect — the literal is a parameter type the constant cannot express without a `typeof` reference — but a successor round could rule on it.
- **`isWebMCPDocument`'s TSDoc offering a pre-check.** "published so a consumer can run it before deciding to build a bridge at all" reintroduces, in prose, the `supported` flag the design deliberately removed. The guard must be exported and the sentence is defensible for a consumer holding a `Document` it is not yet ready to bridge, so I left it.
