## The constraints every design must satisfy

- No added npm package; no second source-language analyzer; `@orkestrel/guide` stays text-only and I/O-free (`Source.ts:24-28`), and `vite`'s `parseSync` is at most a development-edge control the scanner is measured against, never an import from any `src/**`.
- The projection lives in `@orkestrel/guide` as a `render`-class direction beside `Guide` and `Source`, invoked by a package's `docs` script and its `tests/guides.test.ts`; no `scaffold` verb.
- The guide's checked structure survives: Methods under `## Methods`, one table per interface, readonly data properties in the Surface row, the executed fences at `tests/guides.test.ts` (scaffold `:212-361`) keep running; mirrors stay fetched bytes.
- Symmetry is the invariant: the gate refuses the tree when a guide row, a guide example, or a TSDoc block disagrees with its partner, and names both sites; any tool that writes one side from the other is a propagation the developer invokes in either direction, never the gate's own action and never a generator that makes one side authoritative.
- The prose law (`AGENTS.md` § Writing, `.claude/rules/writing.md`) binds both sides through the voice gate, so a term or a voice that fails on one side fails on the other.
- Reuse the declared ecosystem: `@orkestrel/markdown` (`createMarkdown`, `renderMarkdown`, `parseProvenance`), `@orkestrel/template` (`fillTemplate`), `@orkestrel/contract` guards; `@orkestrel/guide`'s own `Guide`, `Source`, `SourceManager`, and helpers extend rather than duplicate.
- Publishing is the owner's decision; the plan names which packages bump (a `@orkestrel/guide` development bump re-pinned fleet-wide; a `@orkestrel/scaffold` release for vendored bytes and seeds) without publishing anything.

## Decisions the plan must take, each with its rationale and its cost

1. **The normalized form.** What a Surface row, a Methods row, and a TSDoc block each project into so they can be compared byte for byte: the sentence form (third-person `-s` on both sides after the amendment, or a stated transform), `{@link X}` to a code token, the Returns column against `@returns` where the table carries one, `@param` against nothing or against a Parameters table, `@remarks` against the guide's narrative or against nothing. Name what is compared, what is deliberately outside the comparison, and where the H1 tagline sits.
2. **The guide structure that carries it.** Whether the fleet's table headers converge on one form per kind (Surface, Methods) or the reader accepts the variants by column role; whether marker-bounded regions are needed at all under an equality gate (they were Option 1's generator seams) or the table's own rows are the region; how a guide names the symbol a row describes so the reader pairs it with its TSDoc without a compiler (the backticked name in column 0 against `Source`'s export grammar); how examples are paired — a fence titled by the symbol, a marker, or the `@example` title — and what "handled nicely" means concretely: the fence and the `@example` body are the same code, or one is the executed transcription of the other with a stated relation.
3. **The readers, on both sides, in `@orkestrel/guide`.** The TSDoc reader (first sentence, `@param`, `@returns`, `@remarks`, `@example` bodies with titles, `{@link}`) extended from the `jsdoc` spans and the `@example` chain; the guide reader extended to the summary, Returns, and Behavior cells and the fence bodies with their pairing key; `parseSync` comments (`ParseResult.comments`, not `Program`) as the control the text reader is measured against. Name the interface changes (`SurfaceSymbol` gains a summary? a new `SurfaceRow`? `GuideInterface.examples()`?) under the single-word entity API laws.
4. **The projection and the equality gate.** `render` in `@orkestrel/guide`: from a `Source` to the guide's table and example form, and from a `Guide` to the TSDoc form, or one canonical form both render into; the gate in each package's `tests/guides.test.ts` compares the two renders and names each disagreeing row or example with both `file:line` sites; the propagation tool (`npm run docs -- --to guide` and `--to tsdoc`, or one command with a direction) rewrites the chosen side in place and is never run by the gate. Decide whether the gate compares whole tables (byte currency) or rows (per-symbol), and what a row missing on one side reports.
5. **The voice gate.** `policy/tsdoc-voice` and `policy/prose` as oxlint plugin rules reading comment text through `getAllComments` and `context.filename` (the plugin context gains `sourceCode`); the Markdown term sweep in the vendored policy sweep; oxfmt's `jsdoc` option only after a measured diff. Name the rule set each side gets and the shared substitution table they read.
6. **`src/bin` and the README.** What the bijection excludes today and whether parity reaches it; what the README head regions become under symmetry (a guide passage and a README paragraph compared, or the README left as an authored index with a link check).
7. **Order and units.** `@orkestrel/guide` readers and `render` first (with their own guide and tests, in the `guide` checkout); then scaffold's vendored parity test, the `docs` script seed, the `.claude/rules/documentation.md` amendment and the `typescript.md` voice line, the policy rules, and scaffold's own guide converged and green; then the fleet, one package per checkout, converging each guide and each TSDoc to the normalized form, in a wave that rides the head-start pattern the fleet campaign uses. Every nontrivial unit is audited by the subjective and objective lanes on falsifiable claims. State the exit criterion as enumerated capabilities.
8. **The probes before the first unit.** Restate `PROPOSAL.md:1261-1279` under symmetry and add what the ruling needs: the text reader's first-sentence miss rate against `ParseResult.comments` by range; the first equality run over scaffold's own guide (how many rows and examples disagree today, as a value the plan sizes the convergence by); `oxfmt --check` stability of a rendered table; the `jsdoc` rewrite's effect on a first sentence; an oxlint rule reporting on a comment; the `@example` body against the executed fence for `createBlueprint`, `Materializer`, and `Compiler`.
