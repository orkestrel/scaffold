Question: What is the method-memoization pattern Zod 4.5 describes, and which of the article's claims are verified against the primary source?

Mechanism: Zod schema classes define behavioral methods (`parse`, `optional`, and similar) as getters on the class prototype rather than as own instance properties. On first access, the getter runs, builds the bound method implementation, and assigns it as an own property directly onto the instance (a self-overwriting getter), replacing the getter for that property on that instance going forward. Every later access reads the own property and never re-invokes the getter. The bound method is a closure over the instance, so `const { parse } = z.string(); parse("data")` keeps working after destructuring — the article states methods "remain auto-bound," but it gives no code sample showing whether the mechanism is `Object.defineProperty(this, name, { value })`, a plain `this[name] = value` inside the getter, or a `WeakMap` (VERIFIED, article prose; UNVERIFIED, exact JavaScript form — see Unknowns). A method never called is never materialized, so it costs no heap. Six properties stay eager, own properties from construction rather than memoized getters: `_zod`, `def`, `type`, `format`, `minLength`, `maxLength` (VERIFIED, https://zod.dev/blog/reducing-memory-footprint — table of own properties before/after). Before 4.5, a `z.string()` instance carried 49 own properties (40 methods bound eagerly at construction plus 9 data properties); after 4.5 it carries 6 eager own properties plus 86 methods reachable through the prototype (VERIFIED, same source). The article states no behavior for a frozen instance (`Object.freeze`): whether the self-overwriting assignment then throws (as a plain assignment to a frozen object does in strict mode) or silently no-ops is not addressed anywhere in the fetched text (UNVERIFIED — searched the full article text for "freeze"; not present).
