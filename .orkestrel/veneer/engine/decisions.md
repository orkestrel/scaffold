## E7 — R10's sanitizer is the `SanitizerConfig` dictionary; the public declarations reference no `Sanitizer` global (2026-09-23)

The J-TYPES landing chain failed `build:src:browser`: the declaration rollup's API Extractor 7.59.2 bundles TypeScript 5.9.3, whose DOM library declares no `Sanitizer`, so a public declaration referencing that global cannot be rolled up on this toolchain (`units/j-types-landing-gates.log.txt`). The Orchestrator's probe (`units/j-types-3-probe-sanitizer.test.ts`, log beside it) shows Chromium 153's `setHTML` honours the HTML standard's `SanitizerConfig` dictionary as its `sanitizer` option with the same element, attribute, and `dataAttributes` semantics the constructed object gave in terrain probe 2. Ruling: R10 reads "a `SanitizerConfig` dictionary built from Bootstrap's allowlist" in place of "a `Sanitizer` built from" it; `SetHTMLOptions.sanitizer` is typed by a structural `SanitizerConfig` mirror declared in `src/browser/types.ts`; no engine file constructs or names the `Sanitizer` global; the `aria-*` expansion and `dataAttributes: false` stand as R10 states them. The fleet-level fact, carried to the user: any public declaration in any target that references a DOM type newer than TypeScript 5.9.3's library breaks the vendored rollup the same way.

Addendum (2026-09-23, after the user asked that `@orkestrel/html` be weighed for the sanitizing job): R14's third ground against `@orkestrel/html`, "a `node:` reference in its built entry", was a misreading. `grep` over `node_modules/@orkestrel/html/dist/src/core/index.js` (0.0.10, installed in Veneer through `@orkestrel/markdown`, a development dependency) finds no `node:` module import; the earlier hits were `node: {` object keys. Its other grounds stand as measured: the core entry is 138,896 bytes, and its `sanitize` runs a string-to-AST-to-string pass whose floor unwraps an unlisted safe element to its children and refuses every `data:` URL, where Bootstrap's allowlist removes an unlisted element with its content and admits `data:` (its `SAFE_URL_PATTERN` refuses `javascript:` alone). A second Orchestrator probe (`units/j-types-3-probe-sanitizer-2.log.txt`) shows the platform's dictionary path honours per-element attribute entries (`{ name: 'a', attributes: ['href'] }`), keeps `data:` URLs, removes an unlisted element with its content, and offers `replaceWithChildrenElements` and `removeElements`. The capability and defect matrix is put to the user in the report of 2026-09-23; E7 stands unless the user rules for the package.

## E12 — Two delegate routes conflict only when both would construct an engine on the same host element (2026-09-23)

The J-COLLAPSE round-1 audit asked when the delegate's collapse route and its button route conflict on one click. Ruling: a route conflict is a click that would have two routes construct an engine on the same host element; two routes that read the same click and drive different hosts (a `[data-bs-toggle="collapse"]` trigger that is also a button engine's host drives the panel through the collapse route and the trigger through the button route) do not conflict, and the per-click mark `Delegate` keeps is keyed on the element a route drives, never on the trigger that was clicked. J-COLLAPSE round 2 (`units/j-collapse-brief-2.md`, C2) keys the collapse mark on the panel inside the containment check, so an outer delegate whose root contains a panel an inner delegate declined still drives it.

Amended 2026-09-24 (the J-COLLAPSE round-2 audit, both lanes): the letter of the conflict and its refusal. A click is a conflict when its button host (the closest button trigger inside the root) is one of the panels its collapse trigger names inside the root and neither `Button.find` nor `Collapse.find` returns an engine on that element, so both routes would construct one there; R5 as amended refuses that click before either route runs, with no mark, no route, and no default action prevented. Where one route finds an engine a consumer constructed on that element, only the other route constructs, and both drive it once. The conflict is the same host element only; an ancestor or a descendant of a named panel is a different host. J-COLLAPSE round 3 (`units/j-collapse-brief-3.md`, D2) implements the refusal, and the guide's § Delegation and `#### Collapse` state it.

Amended again 2026-09-24 (the round-3 audit's referral R1, reproduced in `units/j-collapse-probe-cross-delegate.log.txt`): the refusal is scoped to one delegate, as R5's letter states. Each delegate rules on the engines present on the element when it hears the click; an inner delegate whose root holds the button host but not the collapse trigger finds no conflict inside its root and constructs the button engine, and an outer delegate whose root holds both then finds that engine present and constructs the collapse engine, so two engines can come to sit on one element across two delegates the consumer nested that way. That is the consumer's configuration, not a defect: a delegate never reads a trigger outside its root, and the alternative, a cross-delegate mark for a conflict no single delegate saw, would make one delegate's refusal depend on another's vocabulary. The guide's sentences say "inside the root" and mean it per delegate.

## E15 — a change is in flight from its pre-change dispatch when the entity has one direction (2026-09-24)

## E18 — the Tooltip's door mechanism: one guarded step, an undo rule, and the contract on the interface (2026-09-24)

Three audit rounds found the same class of defect in `Tooltip.ts` through a new door each: a write the change performs after consumer code ran with no lifetime, identity, or container read between them. Under `.claude/rules/quality.md` § Rounds and verdicts the fourth round is a ruling, taken with a design round's adversarial pass (`units/j-tooltip-doors-verdict.md`, reconciling the `planner` and `analyst` lanes on `units/j-tooltip-doors-brief.md`).

**Invariant.** A change performs no write, dispatch, element move, or sanitizer call after consumer code has run unless it has since read that the tooltip is live, that the change is still its own, and, from the tip's insertion until its removal, that the tip it holds is in the container it went into and carries the `shown` token exactly when the change expects it.

**Constraint.** The tooltip never moves back, removes, or repositions a tip or an element that other code moved; it undoes a move only while the node is still where the tooltip put it. Through destruction it keeps restoring the attributes it wrote and returning the content still in its slots. It adds no read before a step, no observer, and no inerting, and it does not defend against the E13 re-entry.

**Interface.** `TooltipInterface.show` and `hide` remarks, `TooltipEventMap.inserted`, `shown`, `hidden`, and `hide` carry the sentences the verdict fixes; the `hide` sentence states the E17 re-promotion exception (O1 of the round-3 audit).

**Mechanism.** The siblings' idiom: `#apply(change, shown, write)` runs one write and reads `#holds(change, shown: boolean | undefined)` after it; every platform write, dispatch, element move, and sanitizer call inside `show`, `#conceal`, `#build`, and `#occupy` is one step; `#holding` goes; the build resolves every content value before its first write; `#discard(): boolean` reads the container before removing and reports whether the tip left the document; completion reads the full door before releasing the change and dispatching. A relocation inside the platform's `beforetoggle` dispatch is reachable through the `inserted` event and is repaired, not documented. `Placement`, `helpers.ts`, and `HostSnapshot` are unchanged by the ruling; J-POPOVER inherits the mechanism through the R12 seam. Round 4 of J-TOOLTIP implements it (`units/j-tooltip-brief-4.md`).
