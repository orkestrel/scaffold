## The questions each lane answers

1. **The leaf list.** For each candidate the terrain names, rule extract, keep as a method, or fold, by the leaf test, and say why in one sentence each. A candidate that reads a `#` vocabulary table becomes a helper taking that table as an argument only where the table's shape is already a declared type (`{Entity}SelectorMap`, `AttributeMap<'target'>`); otherwise it stays a method.
2. **The shapes and their names.** For each repeated shape, one helper: its name under `C:/Users/mikes/WebstormProjects/scaffold/.claude/rules/names.md` (a registered prefix and a noun; the fleet-name check against the claimed names), its full signature with readonly returns and `undefined` absence, its contract (includes self or not, root-bounded or not, the direction order, the guard), and every site that routes through it. Reject a helper that would be a one-line rename of a platform call (the wrapper test), and say which platform call it wraps.
3. **The disabled reading.** Every site that reads a disabled state by hand (the ScrollSpy link reading among them) routes through `isDisabled` per E16, or the lane states the semantic difference that keeps it separate.
4. **The cross-package position.** Rule on where shared DOM traversal leaves belong, with the cost of each option: (a) Veneer's own `helpers.ts` with no new dependency; (b) adopting `@orkestrel/elements` for its `traversals.ts` (a new dependency the user has not authorized, a Vue-oriented package, predicate-based and `null`-returning contracts); (c) a new small fleet package for DOM traversal leaves consumed by Veneer, `elements`, and `mailbox` (a cross-package extraction under the align-packages skill, needing the user's ruling and a release sequence). Recommend one for this campaign and name what would change the recommendation.
5. **The test-side ledger.** For each `tests/setupBrowser.ts` export whose job an installed `@orkestrel/test` export carries, rule reuse, keep with the stated difference, or move upstream into `@orkestrel/test` (with the evidence that it is general), and for each production leaf whose job a test-package export carries, state that the two stay separate because `src/` never imports `@orkestrel/test`, or propose the upstream home if one exists.
6. **The unit plan.** The implementation units in order (one writer per checkout), each with owned files, the tests it adds under `tests/src/browser/helpers.test.ts`, the guide rows it adds, and the falsifiable acceptance criteria; name the risks (a helper that changes a route's semantics, a guard that widens, a name that collides).
