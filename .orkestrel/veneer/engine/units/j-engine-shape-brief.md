## The questions

Answer each with a proposal, a types-first sketch in a `ts` fence, the Bootstrap or platform evidence, and the verdict ruling it amends.

1. **The override shape.** How does a consumer replace a class token, a data attribute name, or a selector the engine reads or writes, per entity and for `Delegate`'s routing table, while Bootstrap's values stay the defaults? Consider at least: a per-entity `classes` and `attributes` group on `{Entity}Options` (single-word keys, typed from a declared default table); one shared vocabulary object the delegate and every class receive; a package-level default a consumer replaces once. Rule under the design laws (mechanism not product policy; minimal public API; group by noun) and name the default table's home (`constants.ts` per R13) and how the styles' parity bounds the *default* values without binding the *option*. State what `Delegate` routes by when a consumer renames `data-bs-toggle`, and how `parse{Entity}Attributes` reads renamed attributes.
2. **Wire event names.** The verdict's R2 and R3 dispatch Bootstrap's names (`show.bs.collapse`) because "the outside is Bootstrap's"; E9 narrows that to the styles. The seed's Button dispatches `toggle.vn.button`. Argue whether every engine event takes the `{verb}.vn.{entity}` form with the event-map keys unchanged, or keeps `.bs.`, or takes a consumer-overridable suffix; weigh a consumer's existing `show.bs.collapse` listeners against one vocabulary owned by this package, and rule which reading E9's text supports. The Orchestrator puts the choice to the user with both proposals, so state the cost of each side plainly.
3. **The sanitizer port.** Replace R10's Bootstrap-shaped `SanitizeOptions { enabled, allow, filter }` with a port: one adapter contract the tip content passes through (name it under the naming law; consider `SanitizerInterface` with one method that writes sanitized markup into an element, or one that returns sanitized markup, and say which the native `setHTML` path can implement without a second parse), the browser-native adapter as the engine's default (built on the `SanitizerConfig` and `SanitizerElementNamespaceWithAttributes` mirrors already declared, with Bootstrap's allowlist as the default configuration), how `TooltipOptions` names the adapter (one option, absence meaning the native default), how a consumer plugs an `@orkestrel/html`-backed adapter in later without a shim, and what "cheap enough to add now as a placeholder" is: which declarations J-TYPES round 5 lands now and which class lands with J-TOOLTIP. State the departure from Bootstrap's `sanitize: false` and `sanitizeFn` and where the guide records it.
4. **Options that survive only because Bootstrap had them.** Walk every `{Entity}Options` key in `types.ts` and name each that exists only to mirror a Bootstrap option a consumer of an Orkestrel-native engine would not ask for, or whose shape is Bootstrap's rather than the design laws' (a string-or-element union, a `'hover'`-style literal turned boolean, a `data-bs-config` JSON path). Rule keep, reshape, or remove with the law that decides it, and keep the list short: the default answer is keep.
5. **The verdict edits.** List, by ruling number, every sentence of R1 to R18 the amendments replace, with the replacement sentence, so the Orchestrator can fold them into the verdict in one edit.
