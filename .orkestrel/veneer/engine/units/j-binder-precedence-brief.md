## The edits

- **P1, the first-saved precedence.** Each record a snapshot saves carries a save-order stamp from a class-static counter taken at `save` (the first save of that target by that snapshot); a taken pending entry passes its stamp on, because a taken value is the older value; `#publish` replaces a pending entry, and its owner, when the incoming stamp is earlier, and keeps the earlier one otherwise; the `classed` record's stamp is that of the element's first token save by that snapshot, or of the taken `classed` entry; withdraw-after-write, the self-take, the owner comparison in `#writeBack` and `#withdraw`, and the captured-list `finally` stay. The `class`-attribute removal is judged after the token writes of the restoration that writes it (R8: state in the report whether an overlapping restoration's later token write can reintroduce a token after the removal, and what the code does about it). The sentence at every site becomes: where two restorations overlap on one target, the restoration whose snapshot saved that target first writes it back, because that snapshot recorded the value the target carried before either engine wrote it (the `HostSnapshotInterface.restore` remark per `j-collapse-precedence.diff`, the class remark, the `#publish` comment, the guide's § Ownership and restoration sentence). Proofs, red first: the landed overlap case in `HostSnapshot.test.ts` flips to end at `original` and is retitled for what a consumer sees ("restores a target two snapshots saved to the value the snapshot that saved it first recorded, whichever restoration started first"); a `classed` case (two snapshots saving tokens on one element, the later-saved restoring first and a reaction inside its token write restoring the earlier-saved; the element ends without a `class` attribute it never had); the round-7 presence-instead-of-owner mutations and a stamp-ignored mutation each redden.
- **P2, the `style` attribute record.** A property's first save on an element records whether the element carried a `style` attribute, the way a token's first save records the `class` attribute; restoring removes each `style` attribute the snapshot recorded as absent that the property writes left empty, in the write order's property step; `HostSnapshotInterface.restore`'s remark, the class remark, and the guide say so. Proofs, red first: an engine's property write on a host without `style` leaves no `style` attribute after restore; a host with `style=""` before the first save keeps it; a host with an unrelated property keeps that property and its attribute.
- **P3, an overridden attribute stays unparsed.** `resolveOptions` parses an attribute only for a key the constructor's options leave `undefined`, so an invalid attribute under an overridden key throws nothing and the override wins; its TSDoc says so. Proof, red first: an element carrying an invalid value for a key the options supply resolves to the supplied value without throwing; an invalid value for a key the options leave undefined still throws the code.
