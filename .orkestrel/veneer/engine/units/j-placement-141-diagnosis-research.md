## Cause or causes, ranked by the evidence

**1. Remembered scroll offset applied to the dropdown's sizing path but not the tooltip's/popover's (inferred, moderate confidence).**
Chrome 135 shipped a "remembered scroll offset" mechanism for anchor positioning: "when a positioned element has a default anchor and is tethered to this anchor at one edge and against the original containing block at the other edge, the scroll offset is taken into account when sizing the element." The remembered value is updated only at an "anchor recalculation point" — "when the positioned element is initially displayed or when a different position-try-fallbacks option is chosen" — never on an ordinary scroll. (Source: [CSS anchor positioning remembered scroll offset](https://chromestatus.com/feature/4710507824807936), snippet quoted from [Chrome 135 release notes](https://developer.chrome.google.cn/release-notes/135).)
This mechanism only activates for a positioned element tethered to its anchor on one edge and to the containing block on the other. If `Dropdown.ts`'s inset/`position-area` configuration puts the menu in that tethered-plus-containing-block shape while `Tooltip.ts`'s and `Popover.ts`'s configurations do not, the dropdown's margin would freeze at whatever it read at the "initially displayed" recalculation point and never update on subsequent scroll — matching `top: 2` reading identically before and after the scroll in the 141 log. The tooltip and popover, not tethered that way, would keep resolving against the live scroll offset and move, matching their rows. **This is inference**: I found no Chromium source confirming the mechanism froze position rather than only size on 141, and confirming or refuting it requires reading which of `position-area`/`position-try-fallbacks` values `Dropdown.ts` passes versus `Tooltip.ts` — that is the objective lane's evidence, not mine.

**2. Popover scroll-offset-at-open bug, Chromium issue 419711773 (documented, low fit).**
"[css-anchor-position] popover with position-area: span-all incorrect with scroll" — a popover using `span-all` in `position-area` did not include the scroll offset in the calculation at the time it opened; the reporter noted that "scrolling while the target is showing keeps it at the same distance from the anchor, but re-opening it moves it again," and that once opened, popovers otherwise move properly with scroll. Filed 2025-05-23, appears fixed in Chrome 145. (Source: [issues.chromium.org/issues/419711773](https://issues.chromium.org/issues/419711773).)
This bug is specific to `position-area: span-all` and to the moment of opening, and by its own description does not freeze position on every subsequent scroll — it only mispositions relative to scroll present at open time. It does not fit a reading where `top` is identical before and after a scroll performed while the menu is already open, unless `V.clip.dropdown`/`V.partial` open the menu, scroll, and re-read without closing and reopening — check that sequence against the fixture before relying on this cause. Ranked below cause 1 because the described symptom (offset-by-a-constant, not literally invariant) fits less precisely.

**3. Transform-unaware anchor resolution, fixed in Chrome 144 (documented, low fit unless the scroller or an ancestor carries a `transform`).**
Before Chrome 144, an anchor-positioned element resolved its position against the anchor's *untransformed* bounding box; a `transform` on the anchor or a transformed ancestor produced a stale reference frame. Chrome 144 made anchor resolution transform-aware, resolving against the transformed anchor's actual bounding box. (Source: [Anchor Positioning is transform-aware in Chrome 144+](https://www.bram.us/2025/11/20/anchor-positioning-is-transform-aware-in-chrome-144/).) This fits only if the dropdown's scroller, toggle, or an ancestor Placement or `_dropdown.scss` puts under a `transform` (for example, a stacking-context or clip trick) while the tooltip's/popover's path does not. The brief already directs the objective lane to check `transform` in the SCSS files; if that check finds no `transform` on any dropdown ancestor, strike this cause.

## Fix per cause

- **Cause 1:** Change the inset/`position-area` shape `Dropdown.ts` gives `Placement` so the menu is not tethered to both the anchor and the containing block simultaneously — the shape that invokes the remembered-scroll-offset sizing path — matching whatever shape `Tooltip.ts` already uses successfully. This holds on 153 as well as 141 because it avoids the mechanism instead of depending on version-specific corrections to it.
- **Cause 2:** Not applicable unless the dropdown's `position-area` uses `span-all` and the reading sequence is open-then-scroll-then-read without a reopen; if so, no code fix is needed on 153 (Chrome fixed it upstream), but 141 has no workaround documented in the bug thread beyond upgrading.
- **Cause 3:** Remove any `transform` from the dropdown's scroller or toggle ancestor chain, or, where the transform is load-bearing, keep it and rely on Chrome 144's fix (no 141 workaround is documented).

## The deciding probe row

Add a probe row that opens the dropdown menu, reads `top` once immediately after open, scrolls the scroller, and reads `top` again — a second immediate-post-open reading before any scroll. Cause 1 (remembered scroll offset, frozen at the initial recalculation point) predicts the post-open reading before any scroll already equals the frozen value seen after scrolling. Cause 2 (span-all scroll-offset-at-open) predicts the pre-scroll reading is correct only if the scroller was at its zero-offset when the menu opened, and predicts a different value if the menu is closed and reopened at a new scroll position. Run the existing `runBoth` control/candidate pair with the scroller pre-scrolled before the menu opens, then scrolled further after — a value that reads correctly once at open but which then freezes selects cause 1; a value that is off by exactly the scroll delta present at open time and self-corrects on reopen selects cause 2.

## Unknowns

- Which of `position-area`, `position-try-fallbacks`, or the inset/margin shape `Dropdown.ts` passes to `Placement` differs from what `Tooltip.ts` and `Popover.ts` pass — this is the objective lane's reading, not verified here.
- Whether any ancestor in the dropdown's scroller chain or `_dropdown.scss` carries a `transform`, `contain`, or `container-type` that `_tooltip.scss` lacks — also the objective lane's reading.
- Whether `V.clip.dropdown`/`V.partial` open the menu before or after the initial scroll position is set, which decides whether cause 1 or cause 2 is even reachable from the fixture as written.
- No Chromium source found states plainly that the remembered-scroll-offset mechanism can freeze *position* (as opposed to only *size*) for a tethered anchor case; that inference is unverified and needs either a Chromium source I did not find or the deciding probe's result.
- I could not fetch the full text of Chromium issue tracker pages or `chromestatus.com` feature pages directly (both render through JavaScript and returned only static shells to `WebFetch`); every claim about them here is a `WebSearch` snippet, which I treat as a paraphrase of the source rather than the source itself.

DIAGNOSIS: the dropdown's inset/`position-area` shape ties its menu to Chromium's remembered-scroll-offset sizing path — frozen at the anchor recalculation point on open and never updated by an ordinary scroll — while the tooltip's and popover's shapes do not invoke that path.
