Parse an integration point's markup in an HTML context on the sanitizer's walk

Chromium 141 has no `setHTML`, so every sanitizer write there takes the walk, which parsed the markup in a copy of the target; for an `annotation-xml` target whose `encoding` is `text/html`, that build parsed `<a>` as a MathML `a`, which the configuration drops, and the styles session read `expected '' to be '<a>kept</a>'`. The walk now parses markup written into an HTML integration point (an `annotation-xml` whose `encoding` attribute in no namespace names `text/html` or `application/xhtml+xml` in any ASCII case, or an SVG `foreignObject`, `desc`, or `title`) inside an HTML `div` of the inert document: for such a context the fragment parser resets to "in body", so the tree is the one a `div` context builds, whatever the build does with a foreign context. A MathML text integration point keeps the copy, because an HTML context cannot keep `mglyph` and `malignmark` as MathML. The walk reads the attribute in no namespace, as the parser does, which closed a second defect this host did show red: a namespaced `encoding` was taken as HTML.
