# J-ELEMENTS design round — the subjective lane's proposal (planner on Opus 5.5, native; retained from its notification, 2026-09-24)

Lane held: subjective (the Elements feel, interaction design fit, the consumer's markup contract). Veneer read on `main` at `C:/Users/mikes/WebstormProjects/veneer`; Elements read at `C:/Users/mikes/WebstormProjects/elements`. No dispatch defect.

## Design

The engine writes no new Elements mechanism: refuse the tab indicator, the toast swipe, and the menu flip cap; measure `position-visibility: anchors-visible` first and, on a green reading, adopt it as a cascade rule the styles session owns, with the engine adding only proofs. The deciding reading: in Elements the look the user values lives in the cascade, not in these engine writes; no Elements stylesheet reads the indicator variables or the menu flip variable, and Elements carries `anchors-visible` in its cascade with no factory writing it.

1. **Tab indicator geometry (`--set-tabs-indicator-x`, `-y`, `-width`, `-height`): REFUSE.** Elements writes four inline custom properties on the tablist when a tab shows and at construction, never repainting on resize (`elements/src/browser/factories/createTabs.ts:52-64`, calls `:82`, `:133`, read). No Elements stylesheet reads them; a whole-repository search finds them only in `createTabs.ts`, its test, `demo/showcase.html`, and `app/browser/pages/UseTabsPage.vue` (read). Elements' tab look tried an underline indicator and dropped it for a background tint, a `color` and `background-color` transition on `[aria-selected='true']` (`elements/src/styles/components/_nav.scss:357-369`, `:384-399`, read). Reasons: the variables drive nothing in Elements; a sliding indicator is not a Bootstrap `.nav` feature (E11); Veneer's `Tab` owns one control and the tablist is shared by every control's instance (`veneer/src/browser/Tab.ts:62-73`, `:256-262`, read), so a list-level property would be another multi-writer target (inferred). The identity worth keeping, the tint transition, is cascade on `.nav-link.active` or `[aria-selected="true"]`, which the engine already writes (`Tab.ts:191`, `:364-377`, read); no engine write. Carrier: none.
2. **Toast swipe offset and opacity (`--set-toast-swipe-offset`, `--set-toast-swipe-opacity`): REFUSE for this campaign; the widen question goes to the user.** Elements tracks a primary-button pointer of any type (mouse included), locks the axis at 6px, caps the offset at the threshold, tapers opacity from 1 to 0.4, commits the hide at the bound and flies the toast off by `±innerWidth`, else snaps back, with a `data-toast-swiping` attribute gating the transition (`elements/src/browser/factories/createToast.ts:316-428`, read); the cascade consumes it through `translate`, `opacity`, and `touch-action: pan-y` (`elements/src/styles/composables/_toast.scss:97-132`, read). Reasons: Bootstrap's toast has no gesture dismissal, and E11 reads "scoped to the elements, components, and utilities native to bootstrap for now"; Elements dismisses on a mouse drag, where a Bootstrap toast's mouse drag selects text and a `data-bs-autohide="false"` toast carrying a required action could be dismissed by accident; Veneer's toast cascade states "each state is a class, so no rule here reads an inline style" (`veneer/src/styles/components/_toast.scss:2-4`, read); Veneer's `Swipe` reads touch and pen only and reports at release (`veneer/src/browser/Swipe.ts:87-101`, read), so adoption needs a new per-move mechanism (inferred). The adoption shape if the user widens: touch and pen only; a per-move report added to `Swipe`; `Toast` writes a signed offset variable and a state token; `.toast` reads `translate` and a multiplied opacity (the `.toast.showing` and `:not(.show)` rules still win by specificity); the cascade adds `touch-action: pan-y` on the `pointer-event` token. Carrier: the Orchestrator's question to the user.
3. **Menu flip cap (inline `max-block-size` plus `--set-menu-flip`): REFUSE.** Elements writes an inline cap of `flip × 2.25rem` and the variable, and its comment says the write is inline only because Elements' surfaces layer beats its components layer (`elements/src/browser/factories/createMenu.ts:57-81`; `elements/src/styles/components/_menu.scss:464-470`, read); no Elements stylesheet reads `--set-menu-flip` (read). Reasons: Veneer has no such layer conflict (its `_dropdown.scss` declares no `max-block-size` or `max-height`, read); a Bootstrap menu grows with its items, and a cap of about five rows makes a longer menu scroll, changing the visual contract; an inline declaration beats every non-`!important` consumer class ("Preserve direct control through classes", `veneer/ROADMAP.md:38-39`). The engine's half of the recipe is taken: `Placement` writes `position-try-fallbacks` and `position-try-order: normal` (`veneer/src/browser/Placement.ts:160-171`, read), matching Elements' reasoning (`elements/src/styles/surfaces/_anchor-position.scss:137-148`, read). A capped menu height, if the styles session wants Elements' look, is a declaration on `.dropdown-menu` that reads no engine write. Carrier: none.
4. **`position-visibility: anchors-visible`: MEASURE first; on a green reading ADOPT as a styles-session cascade rule; the engine writes nothing.** Elements declares it on every anchored popover in its cascade (`elements/src/styles/surfaces/_anchor-position.scss:242-246`, read); no factory writes it. `Placement` promotes the menu or tip into the top layer with `position: fixed` (`Placement.ts:113-118`, `:152`, read), so it escapes every clip from its overflow ancestors; Bootstrap leaves the dropdown menu in place (`bootstrap/js/src/dropdown.js:225-241`, read), so a Bootstrap menu clips with its toggle (inferred); Veneer's menu instead stays open when its toggle scrolls out of a nested scroller, pointing at nothing, and `anchors-visible` restores Bootstrap's visual result for the dropdown and matches Elements; Bootstrap appends tooltips to `body` (`tooltip.js:62`, `:208-211`, `:559`, read), so for the tooltip and popover hiding is a small departure toward Elements. The cascade rule, requested of the styles session under § Pending shared changes: `:where(.dropdown-menu, .tooltip, .popover):popover-open { position-visibility: anchors-visible }` in `_dropdown.scss`, `_tooltip.scss`, `_popover.scss` (specificity of `:popover-open` only, so a consumer class overrides it; it matches no static navbar menu). The Bootstrap markup contract is unchanged. The probe rows for J-NATIVE-PROBE round 2 (`V.*`, on 153 and 141): `V.support` (`CSS.supports('position-visibility', 'anchors-visible')`); `V.clip.dropdown` (a 200px `overflow: auto` scroller with 600px of content, a real `Dropdown` shown, with and without a test-local rule as control, scrolled until the toggle is clipped, two frames, then the hit test at the menu's centre, `:popover-open`, computed `visibility`, `checkVisibility()` and `checkVisibility({ visibilityProperty: true })`, `dropdown.shown`, `data-popper-placement`, then scrolled back and hit-tested again); `V.partial` (the toggle half clipped); `V.viewport` (the page scrolls the toggle out); `V.focus` (the first `.dropdown-item` focused, the toggle clipped, `document.activeElement` after two frames and after scrolling back); `V.events` (every `hide.vn.dropdown`, `hidden.vn.dropdown`, `beforetoggle`, and `toggle` during `V.clip`); `V.tooltip` (`V.clip` with a real `Tooltip`). Adoption bar: on both hosts `V.support` true, `V.clip.dropdown` and `V.tooltip` hidden with the rule and visible in the control, scrolling back restores the hit, `V.events` records no engine event, `V.focus` recorded (if focus falls to `body` the guide states the limit); a red reading on either host is recorded as a refusal.

## Alternatives

Adopt all four as engine writes behind default-off options (`indicator`, `swipe`, `cap`): options with no first consumer, inline writes that beat consumer classes, a break of the toast cascade's stated rule, a widen of E11 without the user, and a variable Elements never reads; rejected. Write `position-visibility` inline from `Placement`: one home for the anchoring declarations, but an inline value beats consumer classes and a fixed visual rule belongs in the cascade, as Elements places it; rejected on "Preserve direct control through classes" and "Mechanism, not product policy".

## Tensions

E11's reading for the toast swipe (features, not only components); cascade versus engine for `anchors-visible` (one home against consumer override); refusing the flip cap leaves Elements' capped height to the styles session, carried by no unit; readings not supplied: the `V.*` rows on both hosts, whether a clipped anchor under the top layer counts as hidden, whether the harness can drive a trusted touch drag.

## Risks

Focus loss under `anchors-visible` (`V.focus`); `Placement.side` checks visibility with default options (`Placement.ts:192`) and may report a hidden menu visible (the `checkVisibility` pair); a long uncapped menu that fits on neither side stays on its preferred side where Popper's `preventOverflow` would shift it (a J-ORACLE recording near the viewport's bottom edge); refusing the tab indicator could read as ignoring the tenet (the `_nav.scss:357-369` comment settles it).

PROPOSAL: Refuse the tab indicator, the toast swipe (sending the widen question to the user), and the menu flip cap as engine writes; measure `position-visibility: anchors-visible` on both hosts through J-NATIVE-PROBE round 2, and on green readings have the styles session add it to the cascade while J-ANCHOR-VISIBLE (`opus` on Opus 5.5) proves it against the shipped cascade.
