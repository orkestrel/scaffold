## 1

`BrowserMCPServer` builds the protocol server from `@orkestrel/mcp` and the stdio carrier from `@orkestrel/mcp/server`.

- `createMCPServer` (`node_modules/@orkestrel/mcp/dist/src/core/index.d.ts:648`, implementation `node_modules/@orkestrel/mcp/dist/src/core/index.js:5082`) is the modern dispatcher. `BrowserMCPServer` passes `identity: { name: 'browse', version }`, `tools: this.#tools`, and `execution: this.#execute.bind(this)` (`src/server/BrowserMCPServer.ts:114-118`). `version` is this package's `package.json` (`src/server/BrowserMCPServer.ts:24`).
- `createMCPLegacy` (`node_modules/@orkestrel/mcp/dist/src/core/index.d.ts:574`, `node_modules/@orkestrel/mcp/dist/src/core/index.js:4716`) wraps that dispatcher and is what `createStdioServer` receives (`src/server/BrowserMCPServer.ts:119`).
- `createStdioServer` (`node_modules/@orkestrel/mcp/dist/src/server/index.d.ts:404`, `node_modules/@orkestrel/mcp/dist/src/server/index.js:1912-1923`) constructs `StdioServerTransport` on `options.input` / `options.output`, defaulting to `process.stdin` and `process.stdout` (`node_modules/@orkestrel/mcp/dist/src/server/index.js:1913`), and pipes it with `bindServer` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:2125`). `StdioServerTransport.duplex` is `true` (`node_modules/@orkestrel/mcp/dist/src/server/index.js:1447-1448`). `send` writes one newline-terminated JSON line (`node_modules/@orkestrel/mcp/dist/src/server/index.js:1472-1477`). The handle returned to browse is only `{ start, stop }` (`node_modules/@orkestrel/mcp/dist/src/server/index.js:1915-1922`).
- `src/bin/main.ts:22-29` constructs that server from `BROWSE_ROOT`, `BROWSE_HEADLESS`, `BROWSE_EXECUTABLE`, and `BROWSE_READONLY`, then calls `start()`. `start()` calls `transport.start()`, then listens for stdin `end`, `SIGINT`, and `SIGTERM` (`src/server/BrowserMCPServer.ts:131-138`). It does not launch Chromium.

`initialize` is answered inside `MCPLegacy.#legacy`, before the modern dispatcher runs (`node_modules/@orkestrel/mcp/dist/src/core/index.js:4745-4756`). A request whose `id` is present and whose message passes `parseJSONRPCMessage` hits `case "initialize"` and returns `buildJSONRPCResult(id, buildInitializeResult(...))` in that same turn. The handler reads `params.protocolVersion` when it is a string and does not await a caller-supplied promise. `MCPServerOptions` declares `on` only for `MCPServerEventMap` (`node_modules/@orkestrel/mcp/dist/src/core/index.d.ts:4889-4890`). That map is `request` and `error` (`node_modules/@orkestrel/mcp/dist/src/core/index.d.ts:4710-4752`). `request` is emitted at the top of `MCPServer.#dispatch` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:5140-5141`). Legacy `initialize` returns from `MCPLegacy` and does not enter that method, so those listeners do not run for it. `notifications/initialized` has no `id`; `#legacy` returns `undefined` before the method switch (`node_modules/@orkestrel/mcp/dist/src/core/index.js:4746`), and `bindServer` writes nothing when `handle` returns `undefined` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:2143-2144`).

`buildInitializeResult` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:1530-1538`) sets `protocolVersion` to the requested version when `isMCPLegacyVersion` accepts it, otherwise `MCP_HANDSHAKE_VERSION`, which is `'2025-11-25'` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:16`). The other accepted legacy revision is `'2025-06-18'` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:21-37`). The result's `capabilities` is `{ tools: {} }`. The comment on that function says this advertises tools with no list-changed sub-option (`node_modules/@orkestrel/mcp/dist/src/core/index.js:1522-1523`). `serverInfo` is `{ name, version }`. A requested version outside the legacy list is still a successful result carrying `2025-11-25`.

A well-formed `initialize` request is answered with that result. These are the error paths around it:

- A message over the dispatcher's byte bound, or a legacy invocation that fails `parseJSONRPCMessage`, becomes a JSON-RPC error with no `id`, code `-32600`, message `Invalid Request` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:4738`, `4748-4751`; code `node_modules/@orkestrel/mcp/dist/src/core/index.js:228`).
- An `initialize` with no `id` is treated as a notification and produces no reply (`node_modules/@orkestrel/mcp/dist/src/core/index.js:4746`).
- There is no registered way for browse to replace the `initialize` case. `initialize` is not in `MCPMethodManager`.

`start()` begins reading. The first inbound line is handled whenever it arrives. Nothing in browse delays that reply until Chromium is up.

A tool failure on the browse path becomes a successful `tools/call` result with `isError: true`:

- Each dispatcher is `this.#forward.bind(this, name)` (`src/server/BrowserMCPServer.ts:110`). `#forward` throws `BrowserError` when `toolset.tools.execute` returns `success: false` (`src/server/BrowserMCPServer.ts:190-193`).

A missing tool returns `success: false` with `tool not found: ${name}` (`node_modules/@orkestrel/tool/dist/src/core/index.js:261-266`). An already-aborted signal returns `success: false` with the reason, or `"aborted"` (`node_modules/@orkestrel/tool/dist/src/core/index.js:269-276`).
- `BrowserMCPServer.#execute` returns that `ToolResult` unchanged when `success` is false or `value` is not a string (`src/server/BrowserMCPServer.ts:171-177`). A string success is rewritten to `{ resultType: 'complete', content: [{ type: 'text', text }] }`.

- A throw from the execution handler itself, outside the tool manager, is caught by `MCPServer.#execute` and answered as JSON-RPC code `-32603`, message `Server error`, after `emitter.emit('error', error)` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:5446-5447`, `5780-5782`; code `node_modules/@orkestrel/mcp/dist/src/core/index.js:243`). The wire message is the fixed string `Server error`.

`notifications/message` is not sent by `MCPServer` or by `BrowserMCPServer`. The modern method table is `server/discover`, `tools/list`, `tools/call`, `subscriptions/listen`, and optional resources, prompts, completion, and tasks (`node_modules/@orkestrel/mcp/dist/src/core/index.js:5159-5182`). `logging/setLevel` is not among them. `parseRequestContext` reads `_meta['io.modelcontextprotocol/logLevel']` and returns `undefined` when the value is present and is not one of `debug`, `info`, `notice`, `warning`, `error`, `critical`, `alert`, `emergency` (`node_modules/@orkestrel/mcp/dist/src/core/index.js:525-526`, `2308-2309`). - A `Browser` from `#launcher`, default `createBrowser`, with `headless`, `profile`, `cdp: { discover: false }`, `signal: this.#abort.signal`, optional `executable`, and on Linux as uid 0 also `args: ['--no-sandbox']` (`src/server/BrowserMCPServer.ts:222-231`).

- `createBrowserToolset(page, { context, journeys: { store: createFileBrowserJourneyStore({ root }), runs: createFileBrowserRunStore({ root }), readonly } })` (`src/server/BrowserMCPServer.ts:236-243`, `src/core/factories.ts:155-159`).

A throw in that `try` unmirrors, clears `#browser` and `#profile` when they still point at this attempt, destroys the toolset and browser, removes the profile directory with `rm(..., { recursive: true, force: true, maxRetries: 5 })`, and rethrows (`src/server/BrowserMCPServer.ts:251-258`). `#open` forgets a rejected `#session` so the next call launches again (`src/server/BrowserMCPServer.ts:205-207`). `connect()` with `discover: false` probes the CDP port, then launches (`src/server/Browser.ts:320-325`). The launch creates a non-temporary profile result for the caller-supplied directory (`src/server/helpers.ts:174-177`), spawns Chromium (`src/server/Browser.ts:629-635`), reads the DevTools websocket from stderr, connects a `CDPClient`, takes ownership of the process serving the endpoint, and emits `launch` then `connect` (`src/server/Browser.ts:645-662`). `isolate()` registers a `BrowserContext`. `create()` opens one page in it.

The toolset holds, on that one instance (`src/core/BrowserToolset.ts:191-248`):

- The view, the origin page, `#page` (the current page), and `#context`.
- Its own `ToolManager`, native tools, the optional `dialog` tool, `tabs` and `switch` when a context was passed, and a `BrowserJourneyToolset` when `journeys` was passed (`src/core/BrowserToolset.ts:318-324`).

The journey toolset holds the store, the optional run store, `readonly`, the recorder, the recording name, the last saved name, the replaying name, and the replay promise (`src/core/BrowserJourneyToolset.ts:77-89`). `destroy()` aborts the active replay and waits for it (`src/core/BrowserJourneyToolset.ts:603`). Journeys persist as `<root>/<name>/journey.json` plus a `revision` file (`src/server/stores/FileBrowserJourneyStore.ts:98-100`, `src/server/constants.ts:214-215`). Runs persist under the same root (`src/server/stores/FileBrowserRunStore.ts:24-30`). A new toolset gets new store objects on the same root. The recorder, the in-flight replay, the retained reading, the turn chain, the adopted tools, and the page registry are on the toolset and the page, and `#teardown` drops them (`src/core/BrowserToolset.ts:2075-2091`).

The dispatchers registered in the constructor are bound to the server, `this.#forward.bind(this, name)` (`src/server/BrowserMCPServer.ts:106-112`). Each call awaits `#open()` and then `toolset.tools.execute` (`src/server/BrowserMCPServer.ts:190-191`). They are not closed over a toolset instance. Mirrored page tools use the same bind (`src/server/BrowserMCPServer.ts:265-266`). After a successful `#launch`, `#session` stays that promise. `#select` assigns `#page` to another page and follows that page's registry (`src/core/BrowserToolset.ts:1923-1945`). `switch` chooses an index in `this.#context.pages()` and calls `#select` (`src/core/BrowserToolset.ts:1203-1225`). `#context` and the origin page are fixed in the constructor (`src/core/BrowserToolset.ts:264-270`). There is no method that replaces the context or the browser. A second browser is a second `createBrowserToolset`. The server's fulfilled `#session` is not pointed at that new toolset.

## 3

`Browser` events for a dead or dropped connection are `error`, then `disconnect`, then `idle`, with `status` set to `'disconnected'` when the loss happened while `status` was `'connected'`. `BrowserContext` emits `page` and `close` only (`src/core/types.ts:1617-1620`). It has no crash event. `BrowserPage` emits `crash` with an empty argument list (`src/core/types.ts:1084`) and `close` with an empty argument list (`src/core/types.ts:1090`). The toolset watches `dialog`, `popup`, and `close` (`src/core/BrowserToolset.ts:2053-2055`). It does not subscribe to `crash`.

Owned-process exit. The spawned `ChildProcess` gets `once('exit', #handleProcessExit)` (`src/server/Browser.ts:499`). Node's `exit` callback receives a code and a signal; `#handleProcessExit` declares no parameters and does not read them (`src/server/Browser.ts:388`). If the instance was connected, `status` becomes `'disconnected'`, then the emitter fires `error` with `new BrowserConnectionError('The browser process exited unexpectedly', { cause: 'process-exit' })` (`src/server/Browser.ts:407-414`, cause constant `src/server/constants.ts:95`), then `disconnect`, then `idle` (`src/server/Browser.ts:416-418`). The handler clears `#process`, `#servingPid`, `#client`, `#contexts`, `#connection`, `#owned`, and `#endpoint`. Cleanup destroys the contexts and closes the client, then calls `#releaseProfile` when termination reports success (`src/server/Browser.ts:999-1011`). For the MCP profile, `temporary` is false, so `removeBrowserProfile` returns without deleting (`src/server/helpers.ts:190-191`). The MCP server still holds `#profile` and removes it only in its own `destroy` or failed `#launch`.

Dropped socket. `WebSocketCDPTransport` listens to the `@orkestrel/websocket` `close` event, which carries `[code, reason]` (`node_modules/@orkestrel/websocket/dist/src/server/index.d.ts:276`), and emits its own `close` with no arguments (`src/server/transports/WebSocketCDPTransport.ts:275-277`). The CDP transport map is `{ message, close, error }` with empty `close` (`src/core/types.ts:23-27`). `Browser` binds both transport `close` and transport `error` to `#handleTransportLoss` (`src/server/Browser.ts:97-98`, `478-482`). If `status` is not `'connected'`, that handler returns (`src/server/Browser.ts:423`). If an owned process is still `#alive()`, it waits `BROWSER_TRANSPORT_LOSS_DEFER_MS` (50) and then confirms (`src/server/Browser.ts:441`, `src/server/constants.ts:89`). Confirmation sets `status` to `'disconnected'`, destroys the context list, closes the client, emits `error` with `BrowserConnectionError('The CDP transport connection was lost', { cause: 'transport-loss' })` (`src/server/Browser.ts:468-472`, cause `src/server/constants.ts:101`), then `disconnect` and `idle`. When `owned` was true, `#owned` and `#endpoint` stay, which is the reconnect path described on `BrowserInterface` (`src/server/types.ts:267-271`). When the process is already dead, the same close is diagnosed as process exit instead (`src/server/Browser.ts:430-432`).

`CDPClient.#onClose` sets `#connected` and `#active` false, rejects every pending request with `CDPConnectionError('CDP connection closed', { method })`, code `BROWSER_CDP_CONNECTION_ERROR` (`src/core/CDPClient.ts:288-298`, `src/core/errors.ts:118-122`), and emits `drop` with no payload when the close was not requested (`src/core/CDPClient.ts:298`). An expected `close()` emits `close` and does not emit `drop` (`src/core/CDPClient.ts:251-257`). `BrowserPage.#track` clears its held-page and discovery-report maps on client `connect`, `close`, and `drop` (`src/core/BrowserPage.ts:1948-1952`). A transport `error` also rejects pending requests with `CDPConnectionError('CDP connection failed: ...', { method, error })` and emits client `error` (`src/core/CDPClient.ts:301-311`).

`Inspector.targetCrashed`. The page subscribes on its session (`src/core/BrowserPage.ts:368`). `#handleCrash` takes no parameters and emits `crash` (`src/core/BrowserPage.ts:1904-1906`). It does not set `#closed` and does not emit `close`. No other subscriber in `src/core` or `src/server` handles that event.

`Target.targetDestroyed`. The page subscribes without a session id, so it receives browser-session events (`src/core/BrowserPage.ts:361`). `#handleDestroy` returns unless `params.targetId` is a string equal to this page's target (`src/core/BrowserPage.ts:1639-1641`). On a match it sets `#closed` and calls `#release`, which unsubscribes, emits `close`, and destroys the page emitter (`src/core/BrowserPage.ts:978-1030`). No other field of the payload is read. A second, static subscription deletes a waiting discovery report when `params.targetId` is a string (`src/core/BrowserPage.ts:1945-1946`). The context then drops that page from `#pages` on `close` (`src/core/BrowserContext.ts:584-586`). `Browser.status` is unchanged by this event. `context.destroy()` destroys each page and then emits context `close` (`src/core/BrowserContext.ts:352-362`).

A command that never answers. `CDPClient.send` arms `setTimeout` for `options.timeout` or the client default, which is `BROWSER_DEFAULT_TIMEOUT_MS` (30000) (`src/core/constants.ts:96`, `src/core/CDPClient.ts:134-145`). On expiry it rejects that one request with `CDPTimeoutError`, code `BROWSER_CDP_TIMEOUT_ERROR`, context `{ method, timeout }` (`src/core/errors.ts:129-133`). `#connected` stays true. `Browser` does not listen for this rejection and does not change `status`. There is no separate hung-browser event.

`BrowserMCPServer` does not subscribe to `Browser` `error`, `disconnect`, `crash`, or `drop`.

## 4

These are installed under `node_modules/@orkestrel` and are the primitives named in the map. Browse's own turn chain is `#tail` on the toolset, not `@orkestrel/queue`.

- `@orkestrel/queue` 0.0.15, `createQueue` (`node_modules/@orkestrel/queue/dist/src/core/index.d.ts:115`). A FIFO engine with bounded concurrency, a handler, a per-entry abort signal, and a per-attempt timeout. Defaults are concurrency 1, retries 0, timeout 0 (deadline disabled) (`node_modules/@orkestrel/queue/dist/src/core/index.d.ts:90-92`, `602-609`). `enqueue` settles when the entry completes, fails after its retries, or is aborted. The `retry` loop increments attempts and runs the next attempt in the same loop with no delay (`node_modules/@orkestrel/queue/dist/src/core/index.js:666-680`). An optional store (`createMemoryQueueStore`, `createDatabaseQueueStore`) keeps outstanding entries for `restore()` (`node_modules/@orkestrel/queue/dist/src/core/index.d.ts:44`, `72`, `610-611`).
- `@orkestrel/timeout` 0.0.12, `createTimeout` (`node_modules/@orkestrel/timeout/dist/src/core/index.d.ts:36`). A `setTimeout` wrapper over an `AbortController`. `start()` arms the deadline, expiry aborts `signal`, `clear()` cancels without aborting. `ms` is an integer from 0 through `2147483647`. A parent signal clears the timeout without aborting the timeout's own signal.
- `@orkestrel/abort` 0.0.12, `createAbort` / `Abort` (`node_modules/@orkestrel/abort/dist/src/core/index.d.ts:28`, `120`). An owned `AbortController` with a trace `id`. `options.signal` exposes `AbortSignal.any` of the owned signal and the parent. `abort(reason)` is idempotent; the first reason sticks.
- `@orkestrel/emitter` 0.0.11, `createEmitter` / `Emitter` (`node_modules/@orkestrel/emitter/dist/src/core/index.d.ts:30`, `67`). A synchronous typed emitter with `on`, `once`, `off`, `emit`, `clear`, and `destroy`. A listener throw goes to the `error` option and does not escape `emit` (`node_modules/@orkestrel/emitter/dist/src/core/index.d.ts:81-89`).
- `@orkestrel/process` 0.0.14, server entry `node_modules/@orkestrel/process/dist/src/server/index.d.ts`. `createProcess` and `createProcessManager` spawn and track children. `Supervisor` (`index.d.ts:975`) spawns one child, captures a bounded stderr tail, writes stdin through `deliver`, and stops the tree with `stop` / `destroy`. `execute` / `executeSync` run one command to completion. `killProcess`, `killTree`, `stopChild`, `waitForExit`, and `waitForClose` are the termination helpers (`index.d.ts:367`, `388`, `925`, `1277`, `1291`). `detach` spawns without waiting (`index.d.ts:234`). `@orkestrel/mcp`'s stdio client transport is built on this supervisor; the browse server spawns Chromium with `node:child_process` `spawn` (`src/server/helpers.ts:368`).

No installed `@orkestrel/*` declaration exports a backoff scheduler. Queue retries are immediate extra attempts.

## 5
