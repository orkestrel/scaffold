## The user's decisions (2026-10-03)

- D1. `browse` launches Chromium at server start, the highest point upstream, never inside a tool call.
- D2. `browse` recovers a crashed browser.
- D3. After D1 and D2, a warm spare browser that starts outside every tool call, so no call pays a startup. Its value is measured before it is kept.
- D4. A broken tool shows at the onset, before a session depends on it.
- D5. Performance changes are measured under a realistic heavy load, with no micro optimization, and no figure is fixed in advance; the case decides each number.
- D6. The browsers form a small, simple pool that balances work across them: the user expects two, three at most, because the hosts these tools run on do not take heavy load well. The pool is no scheduler for many browsers and never grows on demand past its configured size.
- D7. Every browser in the pool is launched when the owner decides, never by a caller's demand; it is tracked and known (its process, endpoint, profile, and state); the pool tracks every browser's liveness at all times, so it knows which browsers are alive and answering before it hands one work; the pool decides which work goes to which browser, and a lease the pool records from assignment to release (the user, 2026-10-03: close to the intent) tells it who holds each browser; and each browser is warm before work that needs it arrives.
- D8. Setup has one place and teardown has one place. Setup runs as early and as eagerly as possible. Teardown runs as late as it needs to and leaves nothing behind: every process, profile, port, and listener the pool created is released, including after a crash.
- D10 (the user, after the synthesis, 2026-10-03). Balancing means failover for now; parallel holders follow once the machinery is proven, as a roadmap item. Liveness is events plus a `ping` at hand-out and before every call, with no timer. The handshake waits for the first warm browser; spares finish warming beside it, and a spare that fails retires and is reported. The pool ships with a size of 1 until the spare's failover gain is measured against its idle cost on this host. The synthesis's other recommendations stand: document Codex's `startup_timeout_sec` if the onset passes 10 s; reclaim a killed server's browsers at the next start in the same root; leave bare `.profiles/<uuid>` directories from earlier versions in place and name a one-time removal in the guide.
- D11 (the user, 2026-10-03, after `../resource/ruling.md`). The resource lifecycle is built now in `@orkestrel/pool` 0.0.14 as a bounded expansion: `min` (a warm floor), `start()` (fills it), `watch(value, signal)` (settles when a record is lost; the signal aborts when its disposal begins), `PoolToken.destroy()` (the holder declares its record lost), and a required refill bound whenever `min` is set; no holder field and no event payloads, because nothing reads them yet. Under `min` the pool never creates for a waiter, and a leased loss always gets one refill attempt. A record whose destroy hook rejects stays counted and is not replaced, so the pool runs short and never over its ceiling beside a resource that may still live (the Orchestrator's correction to the ruling's V1, from the synthesis's pool objection 2). `browse` composes `Pool<BrowserSlot>` and keeps its policy (the profile sweep, the handshake gate, the loss text, the per-call ping, the size variable); probe item 1 builds on the same floor. This is the user's explicit request to add `@orkestrel/pool` as a runtime dependency of `@orkestrel/browser`, and of `@orkestrel/probe` at its item 1 (`AGENTS.md` § Non-negotiable rules). Release order: `@orkestrel/mcp` 0.0.36 and `@orkestrel/pool` 0.0.14 (re-pinned to `@orkestrel/contract` `^0.0.19`), then `@orkestrel/browser`; the eager `browse` release waits for both.
- D12 (the user, 2026-10-03, superseding D11's placement). Start in `browse`, so the lifecycle can be used and shaped before it becomes shared API, and keep `@orkestrel/pool` thin: no pool API change in this campaign. `browse` still pulls in `@orkestrel/pool` (D11's explicit dependency request stands) and builds the resource lifecycle on it: `Pool` keeps what it already does (records, the ceiling, leases, validation at hand-out, the one teardown barrier), and a `browse`-side layer adds the warm floor, the `watch` on each browser, the owner-driven refill, the refill bound, and the rule that a browser whose teardown fails still counts against the ceiling. Write that layer's parts as the members a later pool expansion would take (`min`, `start()`, `watch(value, signal)`, a token `destroy()`, a refill bound), so moving them into `@orkestrel/pool` is a move, and name the trigger for that move: `probe` ROADMAP item 1's design round, or a second consumer that needs the same parts. A `@orkestrel/pool` release that only re-pins `@orkestrel/contract` to `^0.0.19` (no API change) avoids a second contract copy under `@orkestrel/browser`; rule whether it is needed from how `PoolError` and the contract guards cross the two copies.
- D13 (the user, 2026-10-03, after the design of record showed what the browse-side layer costs). Apply the move to `@orkestrel/pool` now, with its `@orkestrel/contract` bump to `^0.0.19`: pool 0.0.14 gains `min`, `start()`, `watch(value, signal)`, `PoolToken.destroy()`, and a required `restarts` bound, and under `min` a record whose destroy hook rejects stays counted. `browse` composes the expanded pool and keeps only its policy; the browse-side layer of `revision-3.md` (W1 to W8) is not built. D12's "start in `browse`" is fulfilled by `browse` being the first consumer in the same campaign.

## Settle each question, with a ruling and the reasoning

1. **Where the launch starts and what the handshake does meanwhile.** The point in `src/bin/main.ts`, the server constructor, or `start()`; whether `initialize` answers at once or waits for the launch; how a failed launch shows at the onset (an `initialize` error, a process exit, a coded error on every call with a relaunch, a logging notification). Weigh each client's startup timeout from the map.
2. **Crash detection.** Owned-process exit, a dropped socket, a renderer crash, and a browser that stops answering, each from an event, never a poll.
3. **Recovery.** What is relaunched and rebuilt (browser, context, page, toolset, journey toolset, retained readings, tabs); what is lost and how the agent learns it (the in-flight call's coded error, the next receipt); whether the last address is restored; how a crash loop ends, with the bound reasoned from the case; profile cleanup, including profiles a killed server left behind.
4. **The pool.** The shape that meets D6 and D7: each browser's states (for example warming, ready, busy, recovering, retired); liveness, meaning how the pool knows each browser is alive and answering, from events (process exit, dropped socket, crash) and from command deadlines, and whether a browser that is alive but stops answering can be detected without a periodic poll (`AGENTS.md` § Design laws, no polling architecture), with the reasoning if a check must run on a schedule; what happens to work in flight on a browser that dies; the lease (what a holder receives, how it is released, what happens to a lease whose holder fails or whose browser dies); and the balancing rule that decides which browser serves which work. A second process or a second context, and why; what a spare serves (instant failover, isolated or parallel replays, anything else the code supports); when each browser starts and how a promoted or crashed one is replaced; its idle cost and how to measure it. Keep the pool small and simple: no feature beyond what D6 and D7 ask.
5. **Placement.** What belongs in the library (a supervised browser or a pool in `src/server`, reusable by tests) and what in the `browse` server and its `BROWSE_*` variables; the public type changes in `src/server/types.ts` with single-word names; how a host turns the eager start off, if it can.
6. **Proof.** How each claim is proved with a real Chromium (killing the process to cause a crash) and no mocks, and which service tests change; whether `tests/service/browser.test.ts`'s launch per test moves to a shared browser in this change or later.
7. **Tests outside `browse`.** Whether the same supervised browser could serve a warm test browser through `PLAYWRIGHT_WS_ENDPOINT` (a Playwright browser server) or a CDP endpoint, as far as the map shows; the `ws-endpoint-probe` unit settles the facts.
8. **Probe.** Which parts of the shape carry over to `@orkestrel/probe`'s server start (probe `ROADMAP.md` item 1); note them, design nothing there.
