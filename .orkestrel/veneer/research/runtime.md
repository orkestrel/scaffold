# Runtime dependency and browser research

Research date: 2026-09-19. Actual Cursor Grok 4.6 inspected repository manifests, public entries, representative factories and adapters, and Contract's installed surface. Native primary-source research supplied the following browser and Vue references. These are source findings, not a Veneer implementation or browser-support proof. The [plan](../plan.md) records the current decision and supersedes earlier absolute bans on Orkestrel runtime packages.

## Repository findings

| Subject                 | Observed source and consequence                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Veneer                  | `package.json` declares Bootstrap `^5.3.8` and Popper `^2.11.8` as runtime dependencies. Public exports point at source CSS. `app/browser/helpers.ts` imports Bootstrap Tooltip and Popover. There is no owned browser runtime to accept yet. Move official runtimes into isolated development oracles as the owned component work lands.                                                  |
| Mailbox and Elements    | Their manifests declare `@vue/reactivity ^3.5.35` at runtime and Vue `^3.5.35` in development. Factories import reactivity; public browser types import Vue `Ref`; browser barrels also export composables that value-import Vue. Their intended factory/adapter split is not a Vue-free public runtime boundary.                                                                          |
| Representative behavior | Mailbox `src/browser/factories/createModal.ts` owns Bootstrap classes, focus, scroll, events, and reactive state. Its `composables/useModal.ts` adapts the factory to Vue lifecycle. Elements `factories/createDialog.ts` uses native dialog methods and still coordinates cancellable component events and cleanup. Reuse behavioral knowledge without copying the reactivity dependency. |
| Contract                | Scaffold declares `@orkestrel/contract ^0.0.17`; its lock and installed package read `0.0.17`. The installed manifest has no runtime dependencies. The sibling source also declares `0.0.17`; matching version text does not establish identical artifacts.                                                                                                                                |
| Contract reuse          | The public core surface exposes `Result`, `Guard`, `Parser`, `ContractShape`, `Infer`, runtime validators/parsers, `attempt`, and compiled contract operations. Scaffold's `src/core/compilers.ts` consumes Contract at runtime. Type-only contracts do not validate input; validators and parsers execute.                                                                                |
| Duplicated prior art    | Elements and Mailbox carry local core contract machinery. Elements' theme factory uses its local `attempt`. Veneer must consume matching Orkestrel primitives when needed rather than inherit this local copy.                                                                                                                                                                             |
| Adapter packaging       | Scaffold's generated JavaScript environments are core, browser, and server. No generated Vue entry or existing Vue companion package was established by this reading. A custom `./vue` export needs toolchain work; it is not an already-supported convention.                                                                                                                             |

## Platform mechanisms

| Mechanism                 | Verified semantics and implementation limit                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Popover                   | The platform supplies top-layer placement, lifecycle events, and automatic light dismissal in auto mode. Manual mode has different dismissal behavior. Popovers do not supply modal inertness or menu keyboard navigation. Chrome/Edge shipped the API at 114. [WHATWG](https://html.spec.whatwg.org/multipage/popover.html#the-popover-attribute), [Chrome introduction](https://developer.chrome.com/blog/introducing-popover-api).                                                              |
| Dialog                    | `showModal()` requires a dialog host; a Bootstrap `.modal` div is not such a host. `requestClose()` requests cancellable closure; `close()` closes directly. `closedby` light dismissal arrived in Chrome 134. Treat each method and lifecycle feature separately. [WHATWG](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element), [Chrome 134](https://developer.chrome.com/release-notes/134).                                                                    |
| Focus and inertness       | Native modal inertness does not establish the intended initial focus or Bootstrap event contract. Own those decisions and test their visible effects. [WHATWG dialog and focusing](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element).                                                                                                                                                                                                                           |
| Anchor positioning        | Chrome 125 introduced the feature; current syntax changed later. `position-try-fallbacks` arrived at 128 and `position-area` at 129. Prove the actual syntax and collision behavior used by the component. [Chrome syntax changes](https://developer.chrome.com/blog/anchor-syntax-changes), [CSS specification](https://drafts.csswg.org/css-anchor-position-1/).                                                                                                                                 |
| Top-layer motion          | Chrome documents `@starting-style`, discrete transitions, and `overlay` support at 117. Entry, exit, interruption, and cancellation still require rendered measurements. [Chrome CSS review](https://developer.chrome.com/blog/css-wrapped-2023), [CSS Transitions](https://drafts.csswg.org/css-transitions-2/#starting-style).                                                                                                                                                                   |
| Listener lifecycle        | Native EventTarget and AbortSignal can own listener cleanup. They do not release unrelated observers, animations, generated nodes, or scroll state automatically. [DOM Standard](https://dom.spec.whatwg.org/#interface-abortsignal), [EventTarget options](https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener).                                                                                                                                                        |
| Observation and animation | ResizeObserver, MutationObserver, IntersectionObserver, and Web Animations are platform mechanisms to evaluate at their first real consumer. Their existence does not prove component timing, placement, or teardown. [Resize Observer](https://drafts.csswg.org/resize-observer/), [DOM mutation observers](https://dom.spec.whatwg.org/#mutation-observers), [Intersection Observer](https://w3c.github.io/IntersectionObserver/), [Web Animations](https://drafts.csswg.org/web-animations-1/). |

The prior-art factories already use dialog, popover, anchor positioning, details, and intersection observation. Source comments about native focus or scroll handling are hypotheses until the supported browser and markup prove them. Prefer platform behavior where it meets the contract; do not infer Bootstrap parity from a native API name.

## Vue compatibility

Vue documents external-state integration through `shallowRef` and replacing its value, with DOM setup and cleanup bound to component lifecycle. This can adapt externally owned state without making that engine reactive through Vue. Vue-created custom elements still use the Vue runtime. [External state](https://vuejs.org/guide/extras/reactivity-in-depth.html#integration-with-external-state-systems), [composables](https://vuejs.org/guide/reusability/composables), [custom elements](https://vuejs.org/guide/extras/web-components.html).

Putting Vue in `devDependencies` does not make a shipped `import 'vue'` or bundled Vue implementation acceptable. An optional Vue peer is also a runtime relationship. Keep the concrete adapter and its actual Vue test consumer within the plan's explicit boundary. Do not expose Vue `Ref` in the vanilla engine's declarations.

## Limits

No native-API browser experiment ran during this amendment. The retained [Edge experiment](browser.md) demonstrates only its token and input-refusal observations. Documentary release milestones do not establish a complete minimum version, an installed Chrome result, or support for every Chromium distribution. Choose named browser releases and verify the actual capabilities before publishing the range.

No package was installed, built, committed, or published by this research. Refresh manifest, lock, installed, and packed evidence at implementation time.
