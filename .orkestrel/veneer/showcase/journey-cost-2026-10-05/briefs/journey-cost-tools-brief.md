## Tools

1. `run.ts`: runs one queued command. Usage: `node run.ts --folder DIR --kind journey|command --cwd DIR -- COMMAND ARGS...`. `--folder` is a run folder under tmp/units/journey-cost/runs/; refused (65) when it exists. Records start and end timestamps, the argv, the cwd, the resolved Chromium executable (read `/home/user/veneer/configs/browsers.ts` resolution the way the tests do, or record `PLAYWRIGHT_BROWSERS_PATH` and the executable the Vitest config resolves; if that cannot be read without running Vitest, record the environment variables and the version string of the chromium under `/opt/pw-browsers`), the exit code, and stdout and stderr to files in the folder. For `--kind journey` it also, after exit, copies the JSON report (the command itself passes `--reporter=json --outputFile=<folder>/report.json`, per plan-v3.md:82) and the four `tmp/journey/*.txt` artifacts (relative to `--cwd`), refusing (65) any artifact whose mtime predates the start; and runs `measure.ts` as a child sampler (via `process.execPath`) for the whole duration, stopping it with SIGTERM. Writes `manifest.json` with the SHA-256 of every file in the folder. Spawns the child bare: no shell, no nested flock (the caller wraps it in `flock /home/user/.wave/journey.lock`). Exit: the child's code; 64 usage; 65 folder exists or artifact stale.
2. `measure.ts`: Usage: `node measure.ts --interval MS --tree PID --out FILE`. Samples the cgroup of the current process: v1 `total_rss + total_shmem` from `memory.stat`, `oom_kill` from `memory.oom_control` or `memory.events`, live `memory.limit_in_bytes`; v2 `memory.stat` anon+shmem, `memory.events` oom_kill, `memory.max`. Also each Chromium renderer's RSS grouped by its browser root (from `/proc`), and the CPU time of processes outside the `--tree PID` process tree. Writes JSON lines to `--out`; on SIGTERM writes a summary (peaks, oom delta, outside-CPU band) and exits 0. Never reads or reports the cgroup usage figure (`memory.usage_in_bytes` / `memory.current`).
3. `mutations.ts`: Usage: `node mutations.ts --targets FILE --report FILE -- RUNNER ARGS...`. Each target in the JSON file carries: file, unique search string, replacement, the case title, the Vitest project. For each: check the search string occurs exactly once (else fail that target), apply, run the case through the caller's runner argv prefix with the title and project appended (the tool never hard-codes npm or vitest), expect red; restore, compare with the original by bytes, run again, expect green. Always restore on error. Writes a report. Exit 0 when every target reads red then green; 66 otherwise; 64 usage.
4. `compare.ts`: Usage: `node compare.ts --baseline DIR --candidate DIR --host-bound FILE --out FILE` (additional baseline folders may be accepted as repeated `--baseline`). The gates of verdict § 2: (a) rows gate: the multiset of `## Resolved values` rows across the four `tmp/journey/*.txt` artifacts, after removing the reading-variant prefix, equal; untouched rows keep order; (b) line gate: for each gated line name (plan-v3.md:622 list plus `390 header`) and reading variant, the multiset of stdout log lines equal after removing the `seconds`, `milliseconds`, and `host` fields; Journal entries compared as a multiset after removing timing entries; (c) failures by (title, row, cause) from the Vitest JSON reports and the `Showcase statechart failed` dumps: every candidate failure present in at least one baseline run with the same cause, and every failing title in the host-bound set; (d) registration counts. Writes a Markdown report listing every difference. Exit 0 when every gate holds, 67 otherwise, 64 usage.
