## Claims

1. **Every `exports` subpath resolves in the packed artifact.** For each of `.`, `./browser`, `./vue`, `./bootstrap`, `./bootstrap/scss`, `./tailwindcss`, `./tailwindcss/scss`, `./styles`, `./styles/scss`, `./styles/themes`, the target file, and every file it transitively needs (`@use` partials, declaration siblings, the `./composables/index.js` chunk), is inside the `files` list of `package.json`, and `tests/distribution.test.ts` proves it for the CSS and SCSS subpaths as well as the JavaScript ones.
2. **`"sideEffects": false` does not drop a consumer's stylesheet import.** A consumer bundle that writes `import '@orkestrel/veneer/bootstrap'` (or `/styles`, `/tailwindcss`) under Vite 8 and under webpack 5 emits that CSS. Name the bundler rule that keeps or drops a bare CSS import when the package declares no side effects.
3. **The SCSS subpaths compile in a consumer.** A consumer with `sass` installed that writes `@use '@orkestrel/veneer/bootstrap/scss'` (through the `pkg:` importer or a `node_modules` load path) resolves every `@use` inside the shipped tree, and its output equals the shipped `./bootstrap` CSS apart from whitespace. State what the shipped `index.ts` and `sheet.ts` entries add for a Sass consumer, given that `files` ships only `.scss`.
4. **The published faces declare no runtime import outside the package.** Every `import` in `dist/src/*/index.js` is relative or names an `@orkestrel/*` package listed under `dependencies`. Today `dependencies` is absent and `@orkestrel/contract` sits under `devDependencies`; state which build option would let a future `src/core` import of a devDependency ship as an unresolvable external, and whether any gate would catch it.
5. **The gate chain is green on the foundation.** `format:check`, `lint:check`, `check`, `build`, and `test` each exit 0 at `ec25f9e`. (Established false; rule on which reds are foundation defects and which are the expected red of a stub face, and whether a foundation may land with any red at all under `AGENTS.md` § Work loop.)
6. **`npm run check` does not depend on `npm run build`.** No file under `src/`, `app/`, `tests/`, or `configs/` imports a path under `dist/`, and every root and scoped `tsc` project resolves without a prior build.
7. **`.vue` imports typecheck in every scope that includes them.** The root `tsc` project and `check:app:vue` both accept `app/vue/main.ts`'s import of `./Example.vue`; a `.vue` module declaration exists where the root project can see it, or the root project excludes `app/vue`. Compare with how the scaffold template handles an `app/browser` Vue entry (`node_modules/@orkestrel/scaffold/dist/host/` and the scaffold checkout's `src/core/templates.ts`).
8. **Every test file is collected exactly once across the `test` chain.** No test file is included by two Vitest projects that `npm test` invokes. Attack `tests/setupBootstrap.test.ts`, `tests/setupStyles.test.ts`, `tests/setupTailwindcss.test.ts`, and `tests/setupVue.test.ts` against the root `setup` project's `tests/setup*.test.ts` include and each face wrapper's include.
9. **`src/vue` is fenced like `src/browser`.** The `.oxlintrc.json` `no-restricted-imports` blocks, the scoped `tsc` project (`configs/src/tsconfig.vue.json`), and the Vite `environmentBoundary` plugin each refuse a `src/vue` module that imports `node:*`, a server module, `app/*`, or a stylesheet. Name the one that is absent for `src/vue` and present for `src/browser`, if any, and the import it would let through.
10. **The `vue` package cannot enter the published `./vue` face.** `isVueBuildExternal` throws on `vue` and `vue/*`; `ROADMAP.md` says the composables chunk will import Vue and change this check. State the contradiction between "the consumer supplies Vue" (no dependency, no peer dependency) and a `dist/src/vue/index.js` that imports `vue` at runtime: which `package.json` field or bundler condition makes that import resolve in a consumer that has Vue installed, and what a consumer without Vue sees when it imports `@orkestrel/veneer` (the root) or `/browser`.
11. **The `bootstrap` cascade layer preserves official Bootstrap's override behaviour.** With the recreation wrapped in `@layer bootstrap { … }` and a consumer's own unlayered stylesheet loaded after it: (a) a consumer's normal declaration overrides a Bootstrap normal declaration; (b) a consumer's `!important` declaration overrides a Bootstrap `!important` utility (Bootstrap ships every utility with `!important`); (c) the relative order of two Bootstrap rules is unchanged. Rule each of (a), (b), (c) from the CSS Cascade Level 5 layer rules, and state what `ROADMAP.md`'s "the same output" and "Bootstrap wins on a shared class" mean if (b) fails.
12. **The layer order of a consumer who loads two faces is deterministic.** When a document loads `./bootstrap` (which declares `@layer bootstrap;`) and `./tailwindcss` (which declares `@layer theme, reset, base, elements, components, utilities;`), the position of `bootstrap` relative to `utilities` is the same whichever sheet the document loads first. Name the file that fixes it, or the import order that inverts it.
13. **"The same output" is a provable equality.** `ROADMAP.md` § Tenets says the Bootstrap surface recreates Bootstrap 5.3.8 "with the same output" and the proofs "compare against the exported CSS". State the comparison a test can run between `dist/src/bootstrap/index.css` (layer-wrapped, Sass-compiled through Vite, unminified) and `node_modules/bootstrap/dist/css/bootstrap.css` that would pass for a faithful recreation and fail for a one-declaration drift, and whether the foundation defines it anywhere. The current proof is `tests/src/bootstrap/index.test.ts`.
14. **The Veneer theme pack applies to Bootstrap colour-mode islands.** `src/styles/themes/_default.scss` selects `[data-vn-theme='default'][data-bs-theme='light']` and `[data-vn-theme='default'][data-bs-theme='dark']`. A document with `<html data-vn-theme="default" data-bs-theme="light">` and a nested `<section data-bs-theme="dark">` retunes the section to the dark pack. Also rule what a consumer who sets only `data-bs-theme` (Bootstrap's own contract) receives from the pack.
15. **A CSS-only consumer can load the default theme pack.** `./styles` is "built CSS without themes" and `./styles/themes` is an SCSS barrel; state what a consumer with no Sass compiler imports to get the default pack, or that none exists.
16. **`TOKEN_NAMES` is pinned to a declaration.** A test proves that every name under `TOKEN_NAMES.bootstrap` is declared by the built `./bootstrap` sheet and every name under `TOKEN_NAMES.veneer` by the built `./styles` sheet, and the reverse. Today the `./styles` sheet declares one custom property, `--orkestrel-veneer-styles`, which `TOKEN_NAMES` does not name, and none of the `--vn-*` names. Rule whether the `veneer` group has a consumer under `AGENTS.md` § Design laws ("Create or substantively expand a capability with its first real consumer") and whether the marker properties `--orkestrel-veneer-styles` and `--orkestrel-veneer-tailwindcss` are public tokens.
17. **The vendored-file edits have a durable home.** `scaffold repair` restores `configs/helpers.ts`, `tests/config.test.ts`, `tsconfig.json`, and `.oxlintrc.json` (and `.prettierignore`). After such a restore, `npm run check`, `npm run build`, and `npm test` exit as they do today. Enumerate every behaviour the five edited files carry and, for each, the scaffold change (generator input, template, or rule) that would let a generated workspace carry it without a hand edit.
18. **The `probe` project arms.** Root `vite.config.ts` composes the `probe` project (not a path string) with `tmp/probes/**/*.test.ts`, the `test:probe` and `test:bench` scripts name it, and no gate runs it.
19. **The `test` chain reaches every declared project and no project is unreachable.** Cross the `test` script's chain against the projects root `vite.config.ts` and each `configs/**/vite.*.config.ts` register; name any project no script runs and any script that runs a project twice (see claim 8). Rule whether `distribution` belongs in `prepublishOnly` alone under `.claude/rules/workspace.md` § Test project matrix.
20. **Every public export is documented with parity proof.** `guides/veneer.md` exists, `tests/guides.test.ts` exists and is registered as the `guides` project, `README.md` carries the guide's tagline, and every export of `src/core` (`TOKEN_NAMES`, `TokenMap`, `TokenName`, `TokenLeaf`) has a Surface row. Compare with the scaffold convention `demo/showcase.html` produced by a `show` script after `format`.

State any conflict between the rule file's fixed set (`_mixins`, `_tokens`, `_theme`, `index`) and the roadmap's set (`_tokens`, `_mixins`, `_reset`, `index`, `themes/`), and which wins under `AGENTS.md` § Authority and loading.

Rule each against `.claude/rules/architecture.md` § Declaration placement, § Functions and orchestration, and `.claude/rules/workspace.md` § Configuration authority, and against `.claude/rules/tests.md` § Shared test infrastructure (a duplicate helper across four setup modules is a defect: four `read*Sheet` and `load*Sheet` pairs differ only in path and script name).

State whether a tarball-identity pin (integrity or digest) exists anywhere a proof reads, as `.claude/rules/quality.md` § Instruments asks for a published-artifact baseline.
