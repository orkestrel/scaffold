## Where the brief pushed hardest

**The shared base.** The constraint is real and the form is right. `Showcase.ts:70-75` constructs all four sections as `new X(this.#main)`, and `ButtonSection` cannot take the base, so collapsing the three into direct `new SpecimenSection(this.#main, CONTENT_COPY, CONTENT_SPECIMENS)` calls would move the copy-to-table pairing into the composer and give the family two construction shapes. Composition instead of extension would make each named class write forwarding `host` and `destroy` members, which `.claude/rules/architecture.md:162` refuses. Barrelling the base is required rather than optional: `.claude/rules/architecture.md:271-276` barrels a class a consumer can construct from values they already hold, and `CONTENT_COPY` and `CONTENT_SPECIMENS` are already barrelled. Its placement in `app/browser/sections/` matches `.claude/rules/architecture.md:215`. The name `SpecimenSection` is correct and reads as "a section over specimens" — see finding 16 for the one name that did not follow it.

**The mark comparison's span.** It isolates the class's own treatment, and nothing else in the cascade can deliver that paint to a span. Grepped `highlight|surface-mark|text-mark` across all of `veneer/src`: the only rules that paint a `.mark` element are `_type.scss:42-44`.

**The two tokens.** The root scope is right. Every other mode-independent system colour sits at the same `:root` outside the theme closure — `--vn-button-face: ButtonFace`, `--vn-button-text: ButtonText`, `--vn-button-highlight: Highlight`, `--vn-button-disabled: GrayText` (`_tokens.scss:297-300`). Their names follow the registry's dominant `{aspect}-{role}` axis, which `--vn-text-code` and `--vn-surface-code` already precedent for an element-named leaf, so they read as registry vocabulary rather than as their first consumer. Folding the background into `mark-text` rather than splitting a `mark-surface` is right: `code-text`/`code-surface` are split because `pre` and `samp` take text without surface (`_pre.scss:5`, `_samp.scss:5`), and both mark consumers take the whole treatment.

## Findings

**13. The registry now carries two names for the mark highlight, and only one of them paints.** Sites: `src/core/constants.ts:133-134`, `:150-151`; caused at `src/styles/components/_type.scss:42-44`. `.mark` was the sole consumer of `--bs-highlight-color`/`--bs-highlight-bg`, which are the sole consumers of `--vn-text-highlight`/`--vn-surface-highlight` (`_mixins.scss:225, 233, 274-275`). After this unit no rule under `src/styles/**` reads any of the four. Failure scenario: a consumer retunes `--vn-surface-highlight` to move the mark highlight and nothing changes. This breaks AGENTS.md § Design laws "One concept, one term". Right: one unit owning the compatibility alias surface (`BOOTSTRAP_ROOT_VARIABLES` in `tests/setupStyles.ts`) and the guide's token table rules whether `highlight` stays as a Bootstrap-compatibility alias with no Veneer consumer or is removed. Neither is in this unit's grant. **Does not force a round**; carry it to the family's acceptance. Search bound: `highlight|surface-mark|text-mark` over all of `veneer/src`; the remaining `--vn-focus-highlight` and `--vn-button-highlight` hits are different tokens.

**14. The two new tokens are public retune points that no case reads as tokens.** Sites: `tests/src/styles/components/type.test.ts:122-140`, `tests/src/styles/elements/mark.test.ts:13-23`. Both pin the literals `rgb(0, 0, 0)` and `rgb(255, 255, 0)`, which resolve identically whether the mixin declares `var(--vn-text-mark)` or the bare `marktext` keyword. Failure scenario: an editor inlines the system keywords into `mark-text`, the retune point silently disappears, and every mark case stays green. This is the defect class the same diff asserts against elsewhere — `setupStyles.ts:752-759` and the new assertion at `setupStyles.test.ts:241-249` exist for exactly it. Right: add one case mounting a host that declares `--vn-text-mark` and `--vn-surface-mark` to values the system colours do not carry, and assert the tag and the class both read them, in the form `TYPE_HEADING_TOKEN_CASES` takes. **Does not force a round**: `dist/src/styles/index.css` shows both rules reading the tokens, so no shipped behaviour is unproved — only the retune seam is unarmed.

**15. The figure residue readings do not carry the guard the claim attributes to them.** Site: `tests/src/styles/components/image.test.ts:64-65`. `flex-direction: column` and `gap: 8px` come from the elements-layer rule (`src/styles/elements/_figure.scss:5-7`), which `.figure` does not override. Failure scenario: `.figure` is given `display: flex`; the two added lines still read `column` and `8px` and stay green, and the line that reddens is the pre-existing `display` assertion at `:63`. The added lines fail only when `_figure.scss` drops the direction or the gap. Right: keep them as the residue's pin, which is real value, and stop crediting them with the display guard. **Does not force a round.**

**16. The base's row type still carries one section's name.** Sites: `app/browser/sections/SpecimenSection.ts:29`, `app/browser/types.ts:26`, `app/browser/constants.ts:241, 363, 419`. The base's third parameter is `readonly ContentSpecimen[]`, and that type is now the shared row of all three sections, so `SpecimenSection` reads as rendering "content specimens". The base exists to give the three one vocabulary, and this is the one name that did not follow; AGENTS.md § Design laws "One concept, one term". Right: rename to `Specimen`, beside `ButtonSpecimen`, updating `types.ts`, the three `*_SPECIMENS` annotations, `SpecimenSection.ts`, and the barrel proof's type comment — every file is in this unit's owned set. **Does not force a round**; it is a rename with no behavioural effect.
