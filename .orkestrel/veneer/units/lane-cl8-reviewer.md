## Findings outside the claims

**12. `tests/setupStyles.test.ts:148-152` — an assertion that cannot fail.** `expect(entry.readings).toEqual(entry.boundary === 0 ? [375, 1401] : [entry.boundary - 1, entry.boundary, entry.boundary + 1])` re-derives the readings with the same expression that constructs them at `tests/setupStyles.ts:433-435`. Failure scenario: narrow the construction to `[boundary, boundary + 1]`, and this assertion follows the edit and stays green while `grid.test.ts` silently stops reading the inactive side of every breakpoint — the exact thing the family's proof exists to hold. `.claude/rules/tests.md` names this ("Never assert an implementation against itself"; "confirm each assertion would fail for the defect it claims to catch"). Right answer: write the reading rows as literals, the way the sibling proof at `tests/setupStyles.test.ts:356-363` already does for `BREAKPOINT_CASES`. **Forces a fix round.**

**13. `tests/setupStyles.test.ts:87` — the zero-boundary row is outside every source binding.** `GRID_BREAKPOINT_CASES.filter(({ boundary }) => boundary !== 0)` drops the `xs` row before the ramp comparison, and the compiled ramp string drops it too (`@if $width != 0`), so neither its name nor its boundary is compared with anything. A second zero-boundary entry added to the table would go unread here. The `grid.test.ts:625` reading keys the same row on `name === 'xs'` while this file keys it on `boundary === 0`, so the two consumers disagree about what identifies it. Failure scenario is bounded: renaming the ramp's zero member reddens `grid.test.ts` through a missing `.col-base-1` specimen, so the gap is caught downstream rather than here. Right answer: key both consumers on `boundary === 0`, and assert the zero row's name against the ramp's own zero key rather than filtering it out. **Does not force a round on its own.**

**14. `tests/setupStyles.test.ts:77-80` duplicates `tests/setupStyles.test.ts:156-159`.** The `compileString` call, its Sass source string, and its `loadPaths` option are now written twice in one file. `.claude/rules/tests.md` § Shared test infrastructure makes a near-duplicate helper a defect, and `AGENTS.md` § TTTDD makes consolidation a step. The unit owns both `tests/setupStyles.ts` and `tests/setupStyles.test.ts`, so the extraction target is in scope. Right answer: export one `compileBreakpointRamp()` from `tests/setupStyles.ts` and call it from both cases, adding its name to the exports assertion. **Does not force a round on its own.**

**15. `tests/app/browser/sections/LayoutSection.test.ts:40` — an existing assertion silently lost its discriminator.** `region.querySelector('[data-specimen]:not(:last-child) .' + name)` was written when `Navigation containers` was the last specimen, so `:not(:last-child)` excluded the navbar specimen and the assertion meant "this container class also appears outside the navbar". Failure scenario: delete the `Capped container` specimen and line 40 stays green for `container` — only the name list at line 18 catches it. Right answer: address the specimen by name the way lines 43-51 do, for example `[data-specimen="Responsive containers"] .container-sm`, or exclude the navbar specimen explicitly rather than by position. **Does not force a round on its own.**
