## Finding 1, the shell control's affordance (item 12)

Landed. `app/browser/styles/_shell.scss` gains a `header button` rule in the `shell` layer painting
`border: var(--vn-border-width) var(--vn-border-style) var(--vn-border-color)`, and the file's
opening comment is corrected: it claimed every paint stays with the published cascade, which the
rule makes false. It now states the rule the shell follows, that the shell paints its own chrome and
never a specimen.

Unknown settled. The affordance is a `shell`-layer rule, not a cascade class. The resolved cascade
ships one non-`.btn` treatment for a bare button, in `src/styles/elements/_button.scss`, and it
paints `border: 0` over `background-color: var(--vn-button-transparent)`; no other shipped class
paints a mode-independent affordance outside `.btn`. The selector is the header's structure rather
than a class on the control, because a class needs a name, a centralized constant beside
`BUTTON_GRID`, and therefore a new export from the application barrel, which
`tests/app/browser/index.test.ts` enumerates and the brief puts off-limits. The header carries the
shell's own chrome and the sections mount into `main`, so the selector cannot reach a specimen.

Deviation-contract call. The affordance is a border rather than an underline, because an underline
reads as a link beside the `Link` specimen in the same document. Its token is `--vn-border-color`,
the cascade's own border colour, which retunes with the mode by design; the treatment, a `1px`
`solid` border, is what reads identically in both.

Proof. `tests/app/browser/Showcase.test.ts` gains the case
`paints one affordance on the mode control in both modes`. It mounts the real showcase with the
shipped cascade, reaches and drives the control through the keyboard so neither reading is taken
while the pointer rests on it, reads `border-width`, `border-style`, `background-color`, `padding`,
and `text-decoration-line` in each mode, asserts the border is present, then asserts the two
readings are equal.

## Deviation state

One deviation, settled inside the owned scope and continued rather than stopped.

The brief's remedy for finding 2 does not reach the hover frame on its own. Staged reduced motion
alone moved `button-primary-hover--light-1280.png` from RGB(8,64,230), a smear inside the
transition, to RGB(8,65,234), the host's rest fill exactly. That is measured rather than inferred: I
ran the capture with reduced motion alone and read the written PNG. The cause is not the transition.
The capture's `stagePane` call repositions the tester iframe to the pane's own fixed corner and
resizes the viewport, which moves the document out from under a pointer that does not move with it,
so a host hovered before the call is no longer hovered at the shot and its paint transitions back
toward rest. Reduced motion only made that arrival instantaneous. A held host is unaffected, because
the press captures the pointer and `:active` survives the staging, which is why the active frames
were already carrying their settled mixes.

The fix is inside the owned files and uses the installed `stagePane` and `releasePane` exports: the
pane is staged before the pointer is placed, so the capture's own staging finds the pane already in
place and moves nothing, and the shot finds the host under the pointer. `releasePane` is called
after the placement because a run that places no frame never reaches the capture's own release, and
a pane left staged outlives the case.

Findings 1 and 3 landed as the brief prescribes, with no deviation.
