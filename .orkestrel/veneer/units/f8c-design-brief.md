## Objective

Rule on how the Tailwind proofs (`tests/tailwind/{profiles,shared,preflight}.test.ts`, run today by
the hand-authored `src:tailwind` browser project through `configs/src/vite.tailwind.config.ts`)
move into the workspace convention's `service` project (`tests/service/**/*.test.ts`, Node,
`tests/setupService.ts` for readiness, run from `test:service` and `prepublishOnly`), so that the
Tailwind compiler and the pinned Chromium are driven for real from Node the way the conformance
oracle drives Chromium, and nothing the F8 design proved is lost.

## Questions to rule on

1. **Readers.** After the move, where does each reading live and which browser-side readers are
   deleted? The candidates: structural readings (layer statement and order, the rules of one layer,
   filled layers, shared class names between two sheets, declared properties of a rule set,
   important names, inline `@source` directives) over the compiled CSS text through the `postcss`
   AST in Node, in `tests/setupServer.ts` or `tests/setupService.ts`; computed readings (per-tag
   reboot comparisons standalone against preflight, the shared-name snapshot equality with and
   without the exclusion line, the importance branch, `.px-8` winning) through `page.evaluate`
   returning raw computed values that Node compares. Name the export set, its home, and the
   `tests/setupService.test.ts` proof each pure leaf gets. State which `tests/setupBrowser.ts`
   exports lose their last consumer and go (a capability that moves is not a capability that must
   not exist; a reader kept for a browser proof stays). `readCascadeSheet`'s signature reading
   stays for the styles project.
2. **Readiness.** What `tests/setupService.ts` verifies and throws on: the compiler and the plugin
   importable and compiling a minimal input; the pinned Chromium resolvable; the built cascade
   present (naming `npm run build:src:styles`); the candidate list derived from the built cascade
   (ruling 5, floor included) and written where `tests/setup.css`'s `@source` names it, or
   elsewhere with the profile's `@source` following. Rule whether the derivation runs in the setup
   module (once per run) or in a proof's `beforeAll`.
3. **Scene.** One browser per proof file (`beforeAll`/`afterAll`) or per case; a scratch HTML file
   under `createScratch` (the oracle's way) or `page.setContent` with `addStyleTag`; how a case
   loads the standalone cascade and then a profile so the cascade's order line stays the first
   layer statement (ruling 7); how `prefers-reduced-motion` and viewport are irrelevant here.
   Name the driver helper's shape (an exported class in `tests/setupService.ts`, a manager the way
   `scene` is, or functions), under the single-word entity API law.
4. **Files and names.** `tests/service/tailwind/{profiles,consumer,preflight}.test.ts` or another
   arrangement; the fixtures' home; `tests/setup.css` stays at its conventional path as the
   `tailwind` profile source (the workspace row describes that file), read by the service project
   alone; the `?inline` and `?raw` imports become `readFileSync` of the fixtures.
5. **Scripts and configuration.** `test:service` exact; `prepublishOnly` extended;
   `test:src:tailwind` and its `test:src` clause removed; `configs/src/vite.tailwind.config.ts`
   deleted; the root `vite.config.ts` regenerated by `scaffold repair --groups configs` after
   `tests/setupService.ts` exists and the scripts are declared. State what else in `configs/` or
   `package.json` the move touches.
6. **The guide and the record.** § Tailwind's project and command sentences, the profile table's
   proof links, the wrapper paragraph, the § Files rows (drop the wrapper row; add `tests/service/`
   and `tests/setupService.ts`), the § Departures from the workspace rows (the `src:tailwind`
   project was a departure from the project table and is gone; the `tests/setup.css` row is
   reworded for the service project; the bare-import row stays), § Tests, § Scripts if it lists
   scripts, and `ROADMAP.md`'s F8 row. Rule on the F8b bundler sentence and the other F8b findings
   in the same text.
7. **Units.** One `opus` unit that moves, rehomes the readers, writes the readiness module and its
   proof, declares the scripts, and folds the F8b findings — or a split, with the dependency order
   and what each owns. The Orchestrator runs `scaffold repair --groups configs` between the script
   declaration and the proof run; say where in the unit's sequence that falls and how the unit
   proves its work before and after it.
8. **Exit criterion.** Restate F8's exit criterion for the amended shape.
