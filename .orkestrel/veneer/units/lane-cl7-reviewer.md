## Findings outside the claims

**12. Dead RTL axis in the container proof — does not force a fix round.**
`tests/src/styles/components/container.test.ts:16` wraps every case in `describe.each(['ltr','rtl'])`. Every property it asserts is direction-symmetric: `max-width`/`width` from logical `max-inline-size`/`inline-size` under `horizontal-tb`; `padding-left` and `padding-right` both asserted 12; `margin-left` and `margin-right` both asserted `(viewport - cap)/2`; `padding-inline-start` and `padding-inline-end` both asserted equal; `display`, `flex-wrap`, `align-items`, `justify-content`. Failure scenario: none — the `rtl` half cannot fail unless the `ltr` half already has, so it doubles ~41 `visitBreakpoint` calls (each two real `page.viewport` round-trips) for no reading. It is also the only direction axis anywhere under `tests/src/styles/`, so it diverges from every sibling partial proof, and it runs against the standing ruling that Veneer spends nothing on RTL variation. Right looks like: drop the `describe.each` wrapper and the `dir="${direction}"` attributes, keeping the cases as written.

**13. The cap loop is bound to the ramp; the container token set is not — does not force a fix round.**
`_container.scss:20-28` emits `max-inline-size: var(--vn-container-#{$name})` for every non-zero member of `breakpoints()`, but the only ramp/token assertion is one-directional: `tests/setupStyles.test.ts:296-297` checks that each `CONTAINER_WIDTH_CASES` boundary has a `BREAKPOINT_CASES` entry, never that each non-zero `breakpoints()` member has a `TOKEN_NAMES.container` key. Failure scenario: a later layout unit adds a ramp boundary; the loop emits a cap rule whose `var()` names an undeclared property, the declaration is invalid at computed-value time and `max-inline-size` falls back to `none`, so the new boundary silently caps nothing while `tokens.test.ts:42`, the presence scan, and the container proof all stay green. Right looks like: one assertion in `tests/setupStyles.test.ts` that the non-zero `breakpoints()` names and the `TOKEN_NAMES.container` keys are the same set.

Two cosmetic ordering slips, no gate, no failure scenario.** `app/browser/index.ts:7` and `app/browser/Showcase.ts:9` place `LayoutSection` after `LinkSection`, and `tests/setupStyles.test.ts:14-16` places `CONTAINER_*` before `CALIBRATED_TIERS`, breaking the alphabetical order the surrounding lines hold. `tests/setupConformance.test.ts:938` inserts `'container'` after `'engine'` in an unsorted position — harmless, the comparison is a `Set`.
