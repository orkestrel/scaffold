# RM-SCAFFOLD report — `opus` on Opus 5.5, native

The shared `mergeOverride` now returns the base in the invocation record's `mode`. Under
`--mode release`, a generated distribution proof fails on a refusing registry instead of skipping.
The replacement vendored case and the end-to-end case were red on baseline code, are green after
the fix, and redden under the forwarding-line mutation. Every gate in Execution step 5 exits 0.
Deviation state: none stopped. The mutation also reddens the compilers pinned-text case, which the
brief's "exactly" did not allow for (see Mutation).

## Changes

- `src/core/templates.ts`: `mergeOverride` in the `vite` template returns `{ ...base, mode: override.mode }` for the invocation record and throws `The project invocation carries no string mode` when that `mode` is not a string. Its comment states why Vitest needs the mode. The distribution template's `RELEASE` comment states that the root factories carry the mode into the project.
- `vite.config.ts`: the same span and comment, byte-identical to the template, which the compilers self-comparison requires.
- `tests/src/core/compilers.test.ts`: the pinned `mergeOverride` text follows the template.
- `tests/config.test.ts` (vendored): the cases `emits every project as a factory so the release mode reaches its proof` and `keeps Vitest invocation fields out of project configurations` are replaced by `runs every project in the mode Vitest was invoked with`. It drives every registered factory with a sentinel record and requires `mode: 'sentinel-mode'` with no leaked `command`, `isPreview`, `isSsrBuild`, or `sentinel`. Its controls, each pinned to its own reading and refused by the predicate, are an ignoring factory, a spreading factory, and an inline entry. It also requires every factory to throw on a record with no string `mode`. The file imports only `node:` modules and `vitest`, as before.
- `tests/distribution.test.ts`: adds `fails the release run of a generated distribution proof on a refusing registry and skips the ordinary run`. The case compiles `createBlueprint('proof', { src: ['core'] })` with the source compiler and materializes it with the raw checkout as host. It links the checkout's installed toolchain into the workspace and serves a `createUpstreamServer` fixture on `127.0.0.1` that answers `/-/ping` with 503. It then runs `RELEASE_PROOF_COMMAND` through `execute` (async, so the fixture keeps serving) with and without `--mode release`, and reads each run's JSON report. Release must exit 1 with the proof file failed on exactly `The release gate requires a reachable npm registry, and npm ping did not answer` and no collected case. Ordinary must exit 0 with the proof passed and its cases `passed` or `skipped`. Each of those runs must have pinged the fixture once, with no timeout and no signal. Rival controls run the release command against a configuration Vite cannot load, a proof failing collection on another import, a proof with an unrelated failing assertion, and a 1 ms timeout. None of them may match the release reading.
- `tests/src/core/templates.test.ts`: the comment in `declares every emitted project factory with the override parameter` stated that the record returns the base unchanged. It now states the projection.
- `guides/scaffold.md`: the release paragraph gains the sentence that the root project factories carry the invocation mode into each project, and why.
- `host.json`: regenerated by `npm run build`. See Tests the change made false.

and in `vite.config.ts` (`tmp/units/rm-mutation.diff.txt`). Deleting the line outright would fall

## Shared-file patch (report-only)

`src/core/compilers.ts` is outside the owned set. Its comment beside `projects.push('appBrowser')`
says Vitest reads the command line's mode inside any project it calls. That was false before this
change: the project must also return the mode. Proposed patch:

```diff
-		// The row is the factory itself, never a call of it. Vitest reads
-		// `import.meta.env.MODE` as the command line's `--mode` only inside a project
-		// it calls, so an evaluated row silently turns the release-mode publish gate
-		// into a skip.
+		// The row is the factory itself, never a call of it. Vitest hands the command
+		// line's `--mode` only to a project it calls, and `mergeOverride` returns it, so
+		// an evaluated row silently turns the release-mode publish gate into a skip.
```

## Observations

- The birth-owned journey wrapper (`configs/app/vite.journey.config.ts`, emitted from the `journey` wrapper template in `src/core/templates.ts` that begins `import type { JourneyVariant }`) registers `() => appJourney(variant, VARIANTS)`, which drops the invocation record. Journey projects therefore still run in `test` under any `--mode`. None of them reads the mode, and the file sits outside this brief's sites.
- The end-to-end case links the checkout's `node_modules` entries into the generated workspace rather than installing them. Its subject is the configuration and the proof, and the refusing registry could install nothing. `provisionNpm` reaches the network only where the ambient npm is beneath the generated floor.
- I tried removing inherited Vitest variables (`MODE`, `VITEST*`, `TEST`) from the child environment. Under an outer `npm run test:distribution -- --mode release -t …`, the case passed without the removal, so the case does not carry it.
- Timing: the end-to-end case took `tests 5.42s` on this host (`tmp/units/rm-green-distribution.log.txt`). The case timeout is 600 s, and each child run has a 240 s cap.
- `prove` receipt: none taken. The claims here rest on child processes, a listening socket, and npm, which that tool's stages do not model, so the runtime probe and the executed cases are the instruments.
