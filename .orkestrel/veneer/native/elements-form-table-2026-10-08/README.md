## Sorter contract items

The following items fix the sorter brief (catalog tier 2 row 3).

- Binding and scope. The host is a `table.table[data-vn-sort]`. The sorter reads exactly `host.tHead.rows` and `host.tBodies[0].rows`, and never a descendant `querySelectorAll`. A click resolves only when the header cell's `closest('table') === host`. The sorter refuses, and leaves untouched, a host with more than one `tbody`, a header cell with `colspan` or `rowspan` above 1, or a body cell with either span above 1, and the guide lists those refusals. It never sorts `thead` or `tfoot` rows. Why: Elements reads every `tbody` but sorts only `tBodies[0]` (table verdict correction 2; createTable.ts:771). It strips `aria-sort` from nested tables' headers through descendant queries (table correction 4; createTable.ts:742, 751). It applies a header's `cellIndex` to body cells, which misaligns under `colspan` and `rowspan` (table verdict missing item 5; createTable.ts:776-798). Surface: `COLUMN_LIMIT` = 256 (table index.d.ts:114-115); one `TableSchema.columns` list per document (1254-1260)
- Column keys and sortability. Each header cell gets one column. Its key is the cell's position in the header row as a decimal string, which stays under `NAME_LIMIT` and stays unique; the header cells are left without a `data-key` attribute. A column offers sorting when its `th` holds a `button`. The sorter listens to that button's `click` only. It adds no `tabindex` and no `keydown` handler to the `th`, and a click elsewhere in the `th`, or on another control inside it, does not sort. Why: Elements makes every target inside a sortable `th` toggle the sort, and adds `tabindex=0` plus a `keydown` path with no `event.repeat` guard (table mapping 'no interactive-descendant exclusion'; verdict missing item 10; createTable.ts:1324-1348, 361-363). Its positional seeding of `data-key` can put `aria-sort` on the wrong header (verdict missing item 4; createTable.ts:352-363). A native button carries focus, Enter, and Space. Tension: the subjective lane rules whether later filter and pager units need an authored column key instead of a positional one. Surface: No `sortable` member; whether a heading offers sorting is the host's decision (table index.d.ts:128-129); `NAME_LIMIT` = 128 (557-559)
- Row identity. The schema declares a `hidden` `text` key column. Each `tr` gets a string key held in a `Map` from key to row element. Either the sorter mints the key for the element at read time, or it uses the author's key, as the user's ruling in the questions decides. The key never derives from the row's index. Why: Elements falls back from `data-id` to `data-index` to `''`, which is positional, unstable, and click-unreachable (table verdict correction 1; helpers.ts:1930-1938). The package refuses positional and missing keys. Surface: `TableSchema.key` is required, and no positional fallback exists (table index.d.ts:1233-1237); `ColumnBase.hidden` (125-126); `rows.add` throws `KEY` (675-676)
- Cell values. A cell's sort value is the `value` of its `data` element, else the `datetime` of its `time` element, else its trimmed `textContent`. A value that is empty after trimming is absent: the row carries no key for that column. It is never `''`. Why: Elements reads an empty `data-sort-value` as `''` and does not fall back to the text (table verdict missing item 8; createTable.ts:799-800). It puts `''` first, which scatters blank cells and detail rows (missing item 6). The catalog fixes `data value` and `time datetime` as the key sources (catalog-2026-10-07-systems.md:60). Surface: Absence is a missing key, never `null` or `''` (table index.d.ts:964-972); absent cells sort first ascending and last descending (absorb README.md:21)
- Column cell kind, fixed once per column. A column is `number` when every present value matches a strict decimal grammar (optional sign, digits, optional fraction); its cells hold `Number(value)`. Every other column is `text`. A `text` column gets a `CellComparator` built on `Intl.Collator`, with the locale from the host's nearest `lang` attribute and `numeric: true`. That comparator places `undefined` first, and a tie falls back to store order. `time datetime` columns stay `text` and sort correctly only in one offset and precision; the guide states that limit. Why: Elements decides numeric or collator comparison per pair, so a mixed column is not transitive ('1e3', '1f', '20' form a cycle). `Number()` also accepts '0x1F', '1e3', and padded values (table verdict missing item 7; helpers.ts:1344-1354). Its `sensitivity: 'base'` collator equates accented and unaccented letters (table correction 5; helpers.ts:1342). The package's default text order is UTF-16 code units. Surface: `CellComparator` receives `undefined` for an absent cell and describes ascending order (table index.d.ts:40-58); `TableOptions.comparators` (1168-1171, 1188); a datetime is `text` (151-153); a `NaN` comparison is a tie (absorb README.md:20)
- Request flow. On a header button click, read `sort.order(column)`. The next state cycles from no term to `ascending` to `descending` and back to no term. Narrow the direction to `TableDirection` before any `set`. Dispatch a cancelable `sort.vn.sorter` on the host whose detail holds `column` and the next `direction`, where `direction` is absent when the next state has no term. When a listener cancels it, change nothing. Otherwise keep a single term: call `remove()` and then `set(order)` when the column changes, and `set(order)` alone when only the direction flips. Why: Elements' sort event is not cancelable and fires after the state and the DOM have moved (table hazard 'Cancelable / vetoable sort'; createTable.ts:296-299, 855-858). The package has no toggle verb and no veto. One term keeps `aria-sort` on one header. Surface: `SortManagerInterface.order`, `set`, and `remove` (table index.d.ts:838-904); `TableDirection` (989-995); events fire after commit with no veto (1027-1032)
- Redraw. On the table's `sort` event, schedule one redraw per synchronous batch, so the two emissions from `remove()` then `set()` move rows once. The redraw places each row element in `view` order with `moveBefore()`, moving only the rows that are out of place. Cycling back to no term redraws store order, which is the markup's original order. Add a proof that a focused button inside a moved row keeps focus under Chromium 141 and 153. Why: Elements re-appends rows with `appendChild`, which loses focus inside a moved row (table verdict missing item 11; createTable.ts:810). It never restores the original order after a sort is cleared (table mapping 'When no sort is active'; createTable.ts:773). The catalog names `moveBefore()` (catalog-2026-10-07-systems.md:60). Surface: `view` is recomputed on every read (table index.d.ts:1111-1117); `rows.rows()` keeps store order (656-669); replacing a column emits twice (absorb README.md:21)
- `aria-sort`. Write `ascending` or `descending` on the `th` of the single sorted column, and remove the attribute from every other sortable header. Write no `aria-sort="none"`, because the button conveys that the column sorts. At boot, read an author's `aria-sort` of `ascending` or `descending` as the initial term, seeded with `set` and no redraw. Ignore `none`, `other`, and an absent attribute. Write no `aria-rowindex` or `aria-rowcount`; the deferred pager owns both. Why: Elements removes the `none` advertisement it seeded (table contradiction; createTable.ts:341-343, 744). It puts `aria-sort` on several headers under multi-sort (verdict missing item 9). Its `aria-rowindex` goes stale after a sort, because a sort never refreshes (table correction 8). The pager row owns those attributes (catalog-2026-10-07-systems.md:129). Surface: `sort.orders()` gives the first term (table index.d.ts:860-865); `set` does not check `direction` at runtime (absorb README.md:21)
- Live markup. Observe the bound `tbody` with one `MutationObserver` covering `childList`, `characterData` across the subtree, and the `value` and `datetime` attributes. Reconcile through `rows.add`, `rows.remove`, and `rows.update`. Discard the records the sorter's own moves produce by calling `takeRecords()` after each redraw. Redraw only while a term is set. Why: Elements has no observer, never refreshes after a sort, and leaves inserted rows unsorted (table hazard 'Live DOM mutations'; verdict missing items 1 and 3; createTable.ts:455-503, 598-609). Surface: `RowManagerInterface.add`, `update`, and `remove` validate the whole batch before writing (table index.d.ts:670-739); a write that changes nothing announces nothing (1031-1032)
- Refusals and limits. A host whose cells or schema the package refuses (`SCHEMA`, `KEY`, or `CELL`; a cell longer than `STRING_LIMIT`, a key column with a duplicate) makes `createSorter` throw the `TableError`. The plugin skips that host and binds the others. Every package limit appears in the guide. Why: Elements accepts any string and has no refusal path, so it gives no lesson here; the package refuses whole payloads. Surface: `TableErrorCode` (table index.d.ts:1016-1025); `STRING_LIMIT` (918-919); `Table` constructor throws (927-935)
- Teardown. Remove listeners and disconnect the observer first, then cancel a pending redraw, then call `table.destroy()` alone. Restore each `th`'s author `aria-sort` and remove only the `aria-sort` values the sorter wrote. Leave rows in their last drawn order. Add a proof that a click after destroy changes nothing and throws nothing. Why: Elements' teardown strips author `aria-sort` and leaves the attributes it seeded (table hazard 'Teardown removes author aria-sort'; createTable.ts:1497-1520). After destroy, its sort still changes in-memory state (table correction 3; createTable.ts:823-855). The dispose test there counts listeners only (table contradiction; setupBrowser.ts:315-337). Surface: `destroy` is idempotent, later writes raise `DESTROYED`, and getters keep answering (table index.d.ts:1131-1139); `Table.destroy` destroys its emitter (absorb README.md:22)
- Multiple tables and nesting proofs. Under 141 and 153, prove that a `tbody` with a blank cell sorts it first ascending and last descending; that a mixed text and number column orders transitively; that a nested table inside a cell keeps its own `aria-sort`; and that a cancelled `sort.vn.sorter` leaves the order and `aria-sort` unchanged. Why: Elements pins no case that tells the numeric path from the collator path, and no case for the tie-break, nested tables, or `aria-sort` cleanup (table verdict correction 6; tests 'NOT PINNED'). Surface: `sortRows` is stable in both directions (table index.d.ts:906-916; absorb README.md:21)

## Binder items

The following lessons belong to the deferred form document binder, not the guard.

- The package already coalesces validation: project errors to the DOM on the package's `validate` event, which fires only when the error list's content changes. Never project on each DOM `invalid` event. Elements needed a pending flag and a microtask to collapse the `invalid` burst (createForm.ts:283-308); `FormEventMap.validate` (form index.d.ts:691, 698) makes that flag unnecessary.
- Choose one validity source: `form.errors` and `form.valid` from the package. Never mix them with `checkValidity()`. In elements, `valid` (input, select, and textarea only) and the native `checkValidity()` result disagree (form verdict missing item 8; helpers.ts:1850; createForm.ts:140-142).
- When a binder mirrors `invalidate(name, message)` into `setCustomValidity`, it must clear the native message on that field's next `fill` and on `clear`. Native custom validity survives `form.reset()` (form verdict correction 2; createForm.ts:239-250). The package holds an external failure until the field is filled again or the form is cleared (form index.d.ts:821-830).
- Map a control that is disabled, or inside a disabled `fieldset`, to the package's `disable(name)`, so the field is neither evaluated nor submitted. Elements reaches the same result through `willValidate` (helpers.ts:1839-1851; guides/w3c/elements/forms.md:1045-1056), and `disable` keeps the answer (form index.d.ts:831-841).
- Treat a radio group's validity as a group. Elements checks `willValidate` on the first member only (form verdict missing item 10; createForm.ts:231-232).
- Write `aria-invalid` only on the fields the binder marked, record them, and remove exactly those on every pass and at teardown. Elements writes an explicit 'false' after validation (createForm.ts:62-88). The Q2 ruling of 2026-10-08 seals CSS-only Bootstrap components (catalog-2026-10-07-systems.md:164). The binder's `.is-invalid` and `.was-validated` writes need a fresh ruling before the binder brief; the catalog row's shape predates that ruling (catalog-2026-10-07-systems.md:127).
- Focus: `reportValidity()` and `requestSubmit()` without `novalidate` move focus to the first invalid control natively (form verdict correction 3). A binder that runs its own first-error focus sets `novalidate` on the host, or focus moves twice.
- Decide validity before announcing a submit, and put that verdict in the event. Elements dispatches its submit before it vetoes an invalid submit (form verdict missing item 2; createForm.ts:322-323).
- Copy `validationMessage` strings, never `ValidityState` objects, because a `ValidityState` is live (guides/w3c/elements/forms.md:1058-1060).
- Reuse the guard's membership predicate (form owner, element class, name, and excluded types) and its document-level `form="ID"` listener, imported from `src/browser/guards/` under the sharing law, so the binder and the guard agree on which controls a form owns (catalog-2026-10-07-systems.md:68).

## Rejected

The following lessons do not transfer.

- A sticky `dirty` boolean set by any `input` or `change` event, with no baseline (createForm.ts:112-126). Because: The package derives `dirty` against a fixed `baseline` (form index.d.ts:759-766, 784-785). The Derive state law forbids a second flag that can drift.
- A values model built on `FormData` entries, raw strings or `File` objects (helpers.ts:1834-1837). Because: The package holds typed `FieldValue` answers (form index.d.ts:446). Building `FormData` fires `formdata` at the host on every read (form verdict correction 4).
- Cancelable re-dispatches of `submit` and `reset`, and a `submit.invalid` option (createForm.ts:316-333). Because: The guard announces state only (`dirty.vn.guard` and `clean.vn.guard` with no detail, guard-1-brief.md:15) and never cancels a submit or a reset. Cancelling is the page's decision (Mechanism, not product policy).
- Elements' `touched` tracking on `focusout`, `check()` and `report()`, `validity.*`, `aria-invalid`, and `data-form-validated` on the guard. Because: None of these move `dirty`, and the guard's API is `dirty`, `clean()`, and `destroy()` (guard-1-brief.md:17). These lessons belong to the binder (Minimal public API).
- The imperative `fields` surface: `field`, `fields`, `has`, `focus`, `enable`, and `disable` (createForm.ts:202-226). Because: No consumer for the guard, so the Minimal public API law forbids it. The package already offers `disable` and `enable` for the binder (form index.d.ts:831-880).
- The namespaced `elements:form:*` and `elements:table:*` event names (constants.ts:453-463, 512-520). Because: Veneer names events `NAME.vn.MODULE` in the Bootstrap style (`dirty.vn.guard`, `sort.vn.sorter`), and the single-word law governs those names.
- Reactive refs, `effectScope`, and the `useForm` and `useTable` Vue adapters (useForm.ts:62-74; useTable.ts:217-241). Because: Veneer's native modules are browser plugins with `ComponentContext` ownership (guard-1-brief.md:9). They have no Vue face, so the stale-options and ref-swap hazards there have no counterpart.
- `sort.toggle` with the `mandate`, `order`, `multiple`, and `auto` options (createTable.ts:107-114, 823-859). Because: The package exposes no cycle verb (table index.d.ts:841-844). The sorter owns the cycle internally and exposes no toggle. `auto: false` and `multiple` have no consumer, and `mandate` is product policy.
- The `data-sort-value` custom attribute (createTable.ts:794-800). Because: Veneer reads the standard `data value` and `time datetime` (catalog-2026-10-07-systems.md:60). A second custom attribute would give one concept two terms.
- Per-pair type inference in the comparator, with `Number()` or a base-sensitivity collator (helpers.ts:1333-1354). Because: It is not transitive on mixed columns (table verdict missing item 7). The package fixes one comparison per column through `ColumnCell` or a `CellComparator` (table index.d.ts:58, 160).

## Questions

The round raised the following questions; the Orchestrator took the recommendation of each pending the user's ruling (the first is ruled yes in the Guard 1 brief; the second waits on the sorter brief).

1. When page code prevents a submit (for example, to save through a fetch), does the guard treat that submit as a save and read clean? The running brief says no in its contract (guard-1-brief.md:14) and yes in its proofs, specimen, and journey (guard-1-brief.md:20-21; catalog-2026-10-07-systems.md:194), and no listener can see a later listener's veto before the page unloads. Recommendation: yes. Every `submit` event that reaches the form rebuilds the baseline. A page whose save then fails has no way to re-mark the form dirty, and the guide states that limit.
2. For the table sorter, may the sorter mint a row key for each `tr` element when it binds (held in a hidden key column and mapped to the element), or must every row carry an author key? `@orkestrel/table` refuses positional and missing keys (table index.d.ts:1233-1237), and elements' positional fallback is the hazard to avoid (helpers.ts:1930-1938). Recommendation: mint per element. The key names the row element, not its position, so any Bootstrap table qualifies without extra markup.
