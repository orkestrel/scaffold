# Veneer: the goals and constraints that define success

Use these tenets to judge the design and each implementation unit. They summarize the user's requirements. Use .orkestrel/veneer/plan.md for the implementation sequence and prompt.txt for the project and file map.

## Product tenets

- Build a proper Orkestrel package.
  Convert Veneer into @orkestrel/veneer with the same types-first contracts, package boundaries, public API conventions, documentation, and verification discipline as the Orkestrel ecosystem. Follow Scaffold's AGENTS.md and its governing rules. A renamed package with the old foundation left intact does not meet the goal.

- Preserve Bootstrap compatibility while owning the implementation.
  Make Veneer a drop-in replacement for Bootstrap's CSS and component markup contracts. Provide the corresponding interactive behavior through Veneer's own runtime. Prove the complete intended compatibility surface; do not quietly reduce it to the components that happen to work. Make any proposed incompatibility explicit and reconcile it with the user's requirements before accepting it.

- Ship Veneer's own JavaScript.
  Build the interaction engine from the useful mechanisms and lessons in Mailbox and Elements. Do not use Bootstrap JavaScript to implement Veneer or to make its demonstrations pass. Compatibility describes the behavior consumers receive; it does not authorize a dependency on Bootstrap's implementation.

- Allow Orkestrel runtime dependencies and forbid other runtime packages.
  Reuse appropriate @orkestrel/* packages, including Contract. Keep Vue, @vue/reactivity, Bootstrap, Popper, Tailwind, and every other non-Orkestrel package out of Veneer's runtime requirements. External packages may be devDependencies for tooling, testing, reference behavior, parity, and conformance. Do not hide a forbidden runtime behind a peer dependency or a bundled copy. Apply the independence requirement to the shipped CSS as well as JavaScript.

- Keep framework integration outside the engine.
  Make the engine usable without Vue or another framework. Provide Vue compatibility through an adapter over the owned engine, without making Vue a Veneer runtime dependency. Inspect Mailbox and Elements rather than assuming their existing implementations already meet this boundary.

- Make Elements the visual and interaction reference.
  Preserve the look and feel that the user values in Elements, including its interaction animations. Investigate how its CSS, JavaScript, and native elements produce those effects, then reproduce the intended experience in Veneer. Bootstrap compatibility must not replace this visual identity with an unexamined stock Bootstrap appearance.

- Give semantic tags useful defaults without inferring components.
  Apply semantic defaults to individual tags. Do not create component styling from combinations of tags or their surrounding structure. Reserve component composition for explicit classes. The meaning of a tag must not change unpredictably because it appears beside or inside another semantic tag.

- Preserve direct control through classes.
  Let consumers override semantic defaults and select component appearance with predictable classes. Do not require specificity battles, special markup tricks, or exceptions to escape semantic styling. Useful defaults and explicit control must coexist.

- Remain compatible with Tailwind CSS without requiring it.
  Let consumers combine Veneer with Tailwind while retaining deliberate control over resets, utilities, component classes, and tokens. Prove the supported combinations in the browser. Veneer must also work independently of Tailwind.

- Make CSS-variable tokens a supported customization and testing contract.
  Learn from the token systems in Mailbox and Elements. Expose clear representations of CSS variables and prove what changing them does to actual consumers. Test resolved styles and rendered effects; the presence of a token name or a generated value alone is insufficient.

- Let the rendered browser result decide UI correctness.
  Test what the browser actually displays and how the interface behaves during real interaction. Exercise user actions, state transitions, focus, keyboard use, and interaction outcomes. Static files, generated CSS, source inspection, or screenshots of an idle state cannot establish interactive correctness by themselves.

- Prove Bootstrap parity and Veneer's own additions.
  Maintain conformance coverage for the Bootstrap capabilities Veneer must replace and for every new capability Veneer supplies. Derive compatibility expectations independently of Veneer's implementation. Apply the same conventions and quality requirements to Veneer-specific features as to compatibility features. Use the independent implementation and conformance approach demonstrated by the MCP, Ollama, and LSP packages.

- Prefer the native browser platform.
  Use browser APIs available in Chromium and Chromium-based browsers such as Chrome and Edge where they satisfy the required behavior. Investigate native support before adding custom machinery. Verify the resulting behavior and animation rather than assuming a native element automatically supplies the complete component contract.

## Execution constraints

- Build incrementally and finish each component before advancing.
  Establish the necessary foundation, then work component by component. Close the active component's contracts, styling, interaction, token behavior, conformance, browser proof, and documentation together. Avoid broad unfinished implementations that defer correctness to a later campaign.

- Research the existing projects before designing replacements.
  Study Veneer, Elements, and Mailbox to understand the earlier philosophy and where it needs improvement. Carry forward the lessons from Roughnotes, the journey skill, and the enterprise Bootstrap skill. Inspect @orkestrel/test's real helpers, especially journey and statechart capabilities, before inventing equivalent infrastructure.

- Use ASTs only where they help answer a concrete question.
  Investigate CSS inspection and the tree/provenance approaches in Markdown and HTML. Treat an AST as a possible discovery or testing aid, not a requirement to build a new parser. Keep final rendered and interactive browser evidence decisive.

- Keep the work and its instructions efficient.
  Use Grok 4.6 to absorb, distill, and map bulk context. Keep plans direct, concise, actionable, and useful to another LLM: state what to do, where to look, and what proves completion. Follow Scaffold's agent and workflow instructions. Preserve necessary plans and evidence, then remove disposable .orkestrel and tmp artifacts safely.
