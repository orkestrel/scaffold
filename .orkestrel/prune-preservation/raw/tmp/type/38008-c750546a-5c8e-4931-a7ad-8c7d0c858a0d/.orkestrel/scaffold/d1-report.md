## What the generated workspace's gate chain actually runs

An app-only workspace declares **no `prepublishOnly`**. `blueprintToScripts`
(`src/core/compilers.ts:407`) emits that script only where `publishes` is true, which reads
`blueprint.src.length > 0`, and `CLI.ts:1008` names `['test']` as a private workspace's whole gate
set. So the brief's first unknown resolves as: the chain never reaches `test:config` through
`prepublishOnly`, because there is no `prepublishOnly` to run.

The new case therefore runs the chain from the scripts the workspace does declare, in the gate order
`AGENTS.md` fixes: `format:check`, `lint:check`, `check`, `build`, `test`. It asserts each is
declared before running it, and asserts `prepublishOnly` is absent — so a release that starts
emitting that script for a private workspace reddens here rather than leaving the case running a
chain the workspace no longer owns.

`test` expands to `npm run test:app && npm run test:policy && npm run test:config`, which is how the
proof reaches the vendored config project.

## The fix's mechanism, and why the alternatives lose

The case at `tests/config.test.ts:2153` did two jobs. It read one face project's resolved compiler
scope, and it read a set of pure helpers behind the roll-up — `parseProjectScope` refusals,
`isStringList`, `buildExtractorOverride`, `packageManifestName`, `rewriteCoreSpecifier`,
`isExtractorModule`. Only the first job needs a `src` axis.

**Chosen: split at that seam, and skip the face half on the axis.**

- `it.skipIf(!published)('reads the compiler scope a declaration roll-up requires', …)` keeps the
  face walk and the `The workspace declares no face project` throw intact inside it.
- `it('reads the fixed extractor override and the specifier rewrites a roll-up requires', …)` runs
  unconditionally and carries every host-independent reading.
- `const published = existsSync(resolve(root, 'src'))` at module scope is the condition.

Each of the brief's three requirements:

- **No `src` axis must not fail.** The scope case is skipped; the helper case runs and passes.
- **A `src` axis with no face wrapper must still fail.** The condition reads the `src` directory,
  not `configs/src/`, so a workspace carrying the axis enters the case and hits the unchanged throw.
- **No silent pass over nothing.** Vitest reports the skip. Measured in a real app-only workspace:

  ```text
   ↓ |config| tests/config.test.ts > configuration helpers > reads the compiler scope a declaration roll-up requires
  ```

  and the project's own counts move from `173 passed | 1 skipped (174)` in this checkout to
  `172 passed | 2 skipped (174)` there — one extra skip, no extra pass. Retained at
  `.orkestrel/scaffold/d1-skipreport.log.txt`, produced by `.orkestrel/scaffold/d1-instruments/d1-probe-skipreport-3.sh`.

**Guarding loses** — the mechanism unit M1 recommended. `if (existsSync(resolve(root, 'src'))) { … }`
leaves the case green in an app-only workspace with the scope reading never performed, and nothing in
the run output says so. That is the failure mode the brief's third requirement names, and this file's
own header comment already bans it: "Every checked population must exist and be non-empty; absence
fails instead of passing vacuously."

**Asserting the precondition loses** for the same reason plus one more. Some form of
`expect(published).toBe(existsSync(resolve(root, 'configs/src')))` reads one derived fact against
another derived fact, which passes for every workspace shape — and it still leaves the scope reading
either unperformed or throwing.

**Skipping the whole case loses** because it would take the host-independent helper readings with it.
An app-only workspace vendors `configs/helpers.ts` byte-identically, so those helpers ship there and
must stay proven there. That is what forced the split rather than a bare `skipIf` on the existing
case.

Two smaller rulings inside the fix:

- The compiler-refusal control moved from `configs/src/tsconfig.absent.json` to
  `configs/tsconfig.absent.json`. Its subject is the compiler's own refusal, and the path now names
  no workspace shape rather than a directory one shape genuinely lacks.
- The negative `parseProjectScope` readings take `resolve(root, 'tsconfig.json')` as their project
  argument. Each is refused by the text before the path is read, and the root project is the one file
  every workspace carries.

## The new case, and what it shares

`tests/distribution.test.ts` gained `installs the packed scaffold and passes one generated app-only
workspace through its gates [requires a reachable npm registry]`, placed directly after the
core/server install case, under the same `it.skipIf(!registry && !release)` guard and the same
1_200_000 ms budget.

It shares rather than restates. Two module helpers now carry what the two cases repeat, and both
cases call them:

- `installPackedScaffold(workspace, environment)` — packs this checkout, installs the archive into
  the consumer, returns the archive path.
- `installGeneratedWorkspace(workspace, archive, blueprint, environment)` — materializes the named
  blueprint, asserts the emitted self-pin, re-pins to the packed archive, provisions an npm at the
  manifest's declared floor, installs, asserts the lockfile resolved the archive, and returns the
  admitted environment.

What stays in each case is what differs: the core/server case keeps the build-time pin coherence
control and its mutation control, and runs `prepublishOnly`; the app-only case keeps the script
assertions and the assembled chain. The blueprint is
`createBlueprint('proof', { app: ['core', 'server'] })` — two app environments, no `src`, and no
`playwright` in the dependency set an `app: ['browser']` blueprint would pull.
